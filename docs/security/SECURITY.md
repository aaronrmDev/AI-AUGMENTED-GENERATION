# Security Model

This project has no application code yet — no FastAPI handlers, no Alembic migrations, no deployed cluster — so nothing described below is a control that is currently running and protecting anything. What follows is the security model this codebase is committed to building toward: CLAUDE.md's non-negotiable 20-point security checklist and the four areas it elaborates on separately (multi-tenancy, authentication, data protection, and rate limiting), rewritten as an explanation of what each control actually prevents, what breaks if it's skipped, and how it's meant to be verified once there's a system to verify. That last part matters as much as the rule itself: a checklist item nobody ever checks isn't a control, it's a wish. So every point below is written together with the concrete way — a unit test, an integration test against a real dependency, a scanner wired into a CI pipeline that doesn't exist yet, or a manual review of an infrastructure configuration — that this project intends to confirm it's actually true, rather than assumed true because it's written down.

## Secrets stay out of source control, and the supply chain is watched for known holes

An API key or database credential that's committed to a Git repository doesn't stop being a problem when the commit is reverted — Git history keeps it recoverable indefinitely unless the whole history is rewritten — so the practical rule this project follows is that no secret is ever typed into a source file in the first place: production credentials live in HashiCorp Vault, and anything that reaches a running process gets there through an environment variable Vault injects, never through a config file checked into the repo. The concrete way this gets verified is a secret-scanner — a Trivy secret-detection pass, or an equivalent tool like gitleaks — wired into the CI pipeline once one exists, run against every commit rather than trusted to a human remembering to check before a merge. A related but distinct failure is a credential that was never mistakenly committed but still ends up compromised some other way — a departing contractor's key, a log line that captured it by accident, a compromised CI runner — and stays valid forever because nothing forces it to change; that's what the documented secrets-rotation policy exists for, and because rotation is a process rather than a piece of application logic, its verification isn't a test but a recurring manual audit confirming the policy is written down and actually being followed on schedule.

The same "don't trust what you can't see" logic applies one layer up, to the third-party code this project depends on rather than the secrets it holds. A vulnerability disclosed in a transitive dependency — a sub-dependency pulled in by FastAPI, LangChain, or any other library in the stack — ships straight to production if nothing is watching upstream security advisories, and by the time anyone notices by accident it may have been exploitable for months. CLAUDE.md names the specific tools this project commits to for that: Snyk or Dependabot scanning the Python dependency tree, and Trivy scanning the built container images for OS-level and package-level vulnerabilities the dependency scanner wouldn't catch because they live below the Python layer. Both are meant to run as CI gates that fail the build once a vulnerability above a set severity threshold is found — not a one-time audit, but a check that reruns every time a dependency or a base image changes.

## Every query is scoped to a tenant, and every input is treated as hostile until proven otherwise

This system is multi-tenant — one deployment serves many separate customers' data side by side — which means the single worst thing that can happen at the data layer isn't a crash, it's tenant A silently reading or writing tenant B's rows. CLAUDE.md's multi-tenancy rules call for every table to carry a `tenant_id` and for PostgreSQL's row-level security (RLS) to enforce that filter at the database itself, with Qdrant's payload metadata and Redis's key prefixes (`tenant:{tenant_id}:`) carrying the same scoping into the vector store and the hot cache. The reason RLS matters specifically is that it's a second, independent layer of defense underneath the application code: even if a handler forgets a `WHERE` clause — the kind of bug that's easy to introduce and easy to miss in review — the database itself refuses to return or accept rows outside the calling session's tenant, so the mistake fails safely instead of leaking data. `docs/database/DATABASE.md`'s schema walkthrough found that an explicit `tenant_id` column shows up only on `Users`, `Sessions`, and `Documents`, with the rest of the schema scoped indirectly through a foreign key back to one of those; RLS policies are what make that indirect scoping actually hold at query time regardless of which path a row is reached through. Verifying this isn't something a unit test with mocked data can do, because the whole point is a database-level guarantee — it needs an integration test against a real PostgreSQL instance (this project's stated integration-testing approach already calls for TestContainers-backed Postgres) that seeds two tenants, deliberately runs a query missing its application-level tenant filter, and asserts RLS still returns zero cross-tenant rows.

RLS protects data that's correctly scoped from reaching the wrong query; it does nothing to stop a malicious query from being constructed in the first place, which is what parameterized queries are for. String-interpolating user input directly into SQL is how a single unescaped field turns into an attacker rewriting the query itself — reading other tenants' data, dropping tables, or worse — and it's exactly the failure mode CLAUDE.md's "no raw SQL in handlers" rule closes off by requiring parameterized queries or the ORM everywhere, with no exception carved out for convenience. That rule is checkable two ways: a static check (a linter, or a Bandit-style rule flagging string concatenation or f-strings built into a SQL call) catches the pattern before it ships, and a targeted test that feeds adversarial strings — a stray quote, a `; DROP TABLE`, a union-based probe — through a repository method and asserts the string is treated as inert data rather than executed as SQL catches anything the linter missed.

Input validation and output encoding sit on either side of that same request: one guards what comes in, the other guards what goes back out. Every request this API accepts is meant to pass through a Pydantic model before it touches any business logic, which means a malformed type, an oversized field, or an unexpected nested structure gets rejected with a validation error at the boundary instead of reaching a handler that wasn't written to expect it — the failure mode without this ranges from an unhandled crash to a downstream function silently operating on data it assumed was already clean. Because this project's testing rule requires a spec written before the implementation, verifying this is close to automatic: each endpoint's Pydantic schema gets a test asserting a set of invalid payloads is rejected and a set of valid ones is accepted, alongside everything else in the same unit-test suite. Output encoding addresses the mirror-image risk on the way out: if something a user typed — a chat message, a fact written into memory — is ever rendered into the React frontend without escaping, that string can carry an executable `<script>` tag into another user's browser session (stored cross-site scripting), potentially reading whatever that user's session has access to, including their own auth token. React escapes JSX content by default, so the practical risk is narrower than it sounds — it's really about never bypassing that default with `dangerouslySetInnerHTML` on anything user-supplied — and it's verified two ways: a component test that renders a known cross-site-scripting payload and asserts it appears as inert text rather than executing, and the dynamic scan described further down, which probes the running application from outside for exactly this class of bug.

## A stolen password or token should be close to worthless to whoever steals it

A database breach is treated in this project's design as a when, not an if, which is why the value of a stolen password depends entirely on how it was stored. A password hashed with Argon2id — the algorithm CLAUDE.md specifies rather than leaving the choice open — is memory-hard, meaning an attacker trying to crack it offline can't just throw commodity GPUs at the problem the way they could against a faster, lighter hash; storing it any other way, or worse, storing it reversibly, turns one database leak into every affected user's password being handed over in practice. Verifying this is a narrow, mechanical test: register a user, read back the stored hash, and assert it carries the `$argon2id$` identifier rather than plaintext or a different algorithm, plus a check that hashing the same password twice produces two different hashes because each carries its own salt.

Session tokens carry a version of the same risk with a different shape: a JWT that stays valid for a long time gives anyone who steals it a long window to use it. CLAUDE.md's answer is short-lived access tokens (15-minute expiry) paired with a longer-lived refresh token (7 days) kept out of reach of any script running on the page by storing it in an httpOnly cookie rather than somewhere JavaScript can read it, with OAuth2 and OpenID Connect layered on top for enterprise single sign-on and separate API keys — rotated through Vault — for service-to-service calls that aren't tied to a human session at all. The WebSocket path adds a wrinkle worth naming explicitly: CLAUDE.md's WebSocket convention authenticates over a `?token=...` query parameter rather than a header, and query parameters have a way of ending up somewhere a header wouldn't — a server access log, a browser's history, a referrer sent to a third party — so the short access-token lifetime is doing real work there, not just following convention. Verifying the token lifecycle needs two tests: one confirming a token issued more than 15 minutes ago is rejected, and one confirming that using a refresh token invalidates it for reuse — replaying the same refresh token a second time should fail, which is what actually makes rotation meaningful rather than just a longer-lived second secret.

Rate limiting and bot protection both defend against the same underlying risk — one actor consuming a disproportionate, disruptive share of the system's capacity — through different mechanisms aimed at different attackers. An unbounded request stream from a single account or IP can exhaust the vLLM serving layer or the database long before it looks like a deliberate attack; CLAUDE.md's specifics are a Redis-backed sliding-window limiter at 100 requests per minute per user for chat, a stricter 10 per minute for document uploads (a heavier operation), a 1,000-per-minute ceiling per IP address with tighter limits specifically on authentication endpoints, and `X-RateLimit-*` response headers so a client can see how much room it has left before being throttled. That's directly verifiable: an integration test against a real Redis instance that fires past each threshold and asserts the request is rejected with the right status and headers once the limit is crossed. Rate limiting alone doesn't stop an attacker who simply spreads the same abuse across many cheaply-created accounts or IPs, though, which is the gap CAPTCHA-style bot protection (reCAPTCHA v3 or hCaptcha) is meant to close at account creation and other high-value endpoints. Because that check depends on an external, live third-party service, it isn't something a unit test can fully simulate; the realistic verification is an end-to-end test confirming the endpoint rejects a request missing a valid challenge token.

## The network boundary is built on the assumption that something inside it is already compromised

The outer edge of this system is protected the ordinary way — HTTPS everywhere, TLS 1.3 specifically, terminated at the Traefik ingress with certificates issued and renewed automatically by cert-manager — because without it, every credential, token, and piece of user data crossing the public internet is readable to anyone positioned on the network path between client and server. That's an infrastructure property more than an application one, so it isn't proven by a unit test; it's confirmed by reviewing the Traefik and cert-manager configuration (ideally as part of the Terraform-managed infrastructure-as-code, so the check happens at the same point the setting is declared) and, once something is actually deployed, by an external TLS scan against the live endpoint confirming weaker protocol versions are refused.

CORS configuration guards a narrower but easy-to-get-wrong version of the same boundary: browsers block a page on one origin from reading a response from another origin unless that response explicitly grants permission via cross-origin resource sharing (CORS) headers, and an overly permissive `Access-Control-Allow-Origin` setting — a wildcard, or a whitelist that's too generous — removes that protection, letting a page hosted anywhere make an authenticated request against this API using a logged-in victim's own browser session and then actually read what comes back. The check is direct: send a cross-origin request from an origin that isn't on the whitelist and confirm the response doesn't grant it access.

Encryption in transit doesn't stop at the public edge, though, and that's the point of CLAUDE.md's separate requirement for mutual TLS (mTLS) on internal Kubernetes traffic: TLS 1.3 covers the path a browser takes to reach the API, but the API's own calls to vLLM, PostgreSQL, Neo4j, and every other internal service cross the cluster's internal network too, and without mTLS on those hops, anyone who's gained a foothold inside the cluster can read or tamper with that traffic in plaintext even though nothing outside the cluster ever could. Making that foothold hard to get in the first place is exactly what the checklist's deny-all Kubernetes network policy is for: rather than assuming every pod can be trusted to only talk to what it's supposed to, the network policy has to be updated deliberately to allow each specific pod-to-pod path — the API reaching Postgres, the API reaching Redis, and so on — so a pod compromised through some other flaw, a dependency vulnerability from the supply-chain controls above, for instance, doesn't automatically get a clear path to every other service in the cluster. Both mTLS and network policy are infrastructure-configuration properties rather than application behavior, so their realistic verification is a manifest review confirming the deny-all baseline and certificate validation are both actually in place, with an automated policy-as-code check — something like conftest or kube-linter run against the manifests in CI — as the more scalable version of that same review once there's a CI pipeline to run it in.

## Data that's unreadable at rest can't be walked back after a breach, and personal data that's already gone can't leak

Every other control in this document assumes the application layer behaves correctly; encryption at rest is what still matters when it doesn't, or when the breach doesn't go through the application at all — a stolen disk, an improperly secured backup, a cloud-storage misconfiguration that exposes a bucket. CLAUDE.md calls for that protection at each store specifically: transparent data encryption on PostgreSQL, field-level encryption on Qdrant, and server-side encryption on the MinIO object store holding uploaded documents. Because this is a storage-configuration property rather than something application code decides at runtime, it's verified by reviewing the infrastructure configuration that provisions each store — again, ideally the Terraform definitions, so the setting is checked at the same place it's declared — rather than by a test that runs against the application.

The other half of data protection is about not holding onto sensitive data longer than the system actually needs it, which matters because data that was never stored — or was stored in redacted form — can't be part of a future breach at all. This project's memory layer is meant to run incoming content through personally identifiable information (PII) redaction, using Presidio or a regex-based fallback, before anything is written into MAG's episodic or semantic stores, so a user's name, contact details, or anything else Presidio's detectors or the regex patterns are tuned to catch doesn't sit in the database or the logs in raw form. The concrete failure mode without this is that a single memory-store or log leak becomes a PII breach by default rather than by exception, since the PII would already be sitting there in the clear. On top of redaction, episodic memories are meant to auto-expire after 90 days unless they've already been consolidated into semantic memory — the process CLAUDE.md's memory-augmented-generation design describes as transforming raw episodes into distilled, durable facts — which keeps stale personal data from accumulating indefinitely just because no one deleted it. Verifying redaction is a direct unit test: feed a known PII pattern (an email address, a phone number) through the redaction step and assert the stored or logged value no longer contains it in raw form. Verifying the 90-day expiry needs a test against the scheduled consolidation/cleanup job itself, seeding an episodic memory older than the threshold and confirming it's either archived or already consolidated rather than still sitting in its raw form.

## When prevention fails, the system needs to say so — through a log, or through an attack simulation

Every control above this line is aimed at prevention, and prevention eventually fails somewhere — through a bug, a misconfiguration, or a genuinely novel attack nobody anticipated — which is why authentication events specifically get their own audit trail rather than relying on whatever generic request logging already exists. A login, a logout, a token refresh, and a permission-denied event are each meant to write a structured log entry (via structlog, the logging library CLAUDE.md's observability stack already commits to elsewhere) carrying who did it, when, and what the outcome was, because without that trail an incident-response investigation after a suspected breach has no way to reconstruct who accessed what — the failure mode isn't the breach itself, it's being unable to answer any question about it afterward. Verifying this is a unit test per auth-event type: trigger a login, a failed login, and a token refresh, and assert each produced a log entry carrying the fields an investigation would actually need.

The last checklist point is different in kind from everything before it: dynamic application security testing (DAST, via OWASP ZAP — the tool CLAUDE.md names directly) doesn't check a rule at all, it attacks a running instance of the system the way an actual adversary would, looking for the class of vulnerability that only exists once the pieces are assembled and running — the kind that static review and unit tests are structurally unable to see, because there's no running system for them to probe. That makes it the last line of defense for many of the failure modes described throughout this document: a reflected script-injection bug that slipped past output encoding, an authorization check missing on one specific live endpoint, a CORS misconfiguration nobody caught in review. It's meant to run as a CI stage, scanning a deployed test instance of the API and failing the build on findings above a set severity threshold — which, like the CI-gated dependency and container scans described earlier, doesn't exist yet because there's no CI pipeline or deployable instance yet to run it against.

None of the verification mechanisms described above have actually been run — there's no test suite, no CI pipeline, and no deployed instance for a dynamic scan to point at yet. What this document commits to is narrower, and for a pre-code repository, more honest: every one of CLAUDE.md's 20 security-checklist points, and each of the multi-tenancy, authentication, data-protection, and rate-limiting mechanisms it elaborates on, now has a stated, concrete way it's meant to be checked once there's a system to check it against, rather than being a bare rule someone has to trust was followed.
