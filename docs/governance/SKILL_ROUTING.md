# Skill Routing

This environment has a roster of specialized skills already installed and ready to invoke today. Each one was built to carry a particular kind of work through to a documented standard rather than have that work improvised fresh, from memory, inside whatever session happens to be doing it. The practical question this document answers is the one that comes up before any nontrivial task starts: does a piece of work already have a skill that owns its shape, and if so, does the session actually reach for it, or does it quietly freehand something a skill would have done more consistently? The rules below cover the shapes of work this project already knows it will hit repeatedly — creative and architectural decisions, security review, GitHub process work, schema design, and questions about how the codebase's pieces connect — and the closing section explains why routing to the matching skill is meant to be the default move, not a step reserved for the obviously large tasks.

## Creative or architectural work starts with brainstorming

Any work that creates something new — a feature, a subsystem, a change to how existing components fit together — starts with `superpowers:brainstorming` before any implementation attempt, design document, or code gets written. That skill's own purpose is to explore user intent, requirements, and design before implementation begins, and it's written as a hard "must," not a suggestion. The reason that front-loading matters is that an architectural question is cheap to answer before implementation starts, because answering it differently at that point costs nothing more than rewriting a paragraph. Once an implementation exists around one reading of the requirements — schema, migrations, endpoints, tests all built on it — changing that reading later means unwinding all of it, not just editing a sentence, which is exactly the cost every one of this project's own completed batches paid a design spec up front specifically to avoid. That's the same logic CLAUDE.md already applies one layer down, in its database-first rule that schema migrations must precede application code: get the foundational decision right deliberately, before anything else commits to it, rather than discovering the right answer through the more expensive process of refactoring around a wrong one. Brainstorming is that same discipline applied a step earlier, to the requirements and design choices that precede even the schema.

## Security or audit work routes to the security engineer

Work that hardens, audits, or pentests any part of this system — checking it against the OWASP Web and API Top Ten lists, reviewing an authentication flow, verifying that a data-protection control actually works — routes to `fullstack-e2e-security-engineer` rather than an ad hoc read-through. That skill runs what it describes as a 360-degree matrix audit across the data layer, the UI layer, and the integration layer, which matters because security review is exactly the kind of task where a review that looks finished can still be badly incomplete: a freehand pass checks whatever vulnerability classes the reviewer happens to think of in the moment, and the categories nobody thought to check don't announce their own absence — they just stay open. CLAUDE.md already commits this project to a twenty-point security checklist for exactly that reason, covering everything from parameterized queries to encryption in transit; routing security work to a skill built to execute a systematic audit rather than an associative one is how that checklist's coverage actually gets delivered, instead of being reconstructed from memory — and narrowed a little more each time — by whoever happens to be doing the review that day.

## Task, issue, and board work routes to the project-management orchestrator

Any GitHub-process work — filing an issue, standing up a project board, defining custom fields, wiring status automation, setting branch protection, or even creating one single task or bug — routes to `github-project-management-orchestrator`. That skill is explicitly meant to be invoked for single work-item requests too, "so hierarchy and field conventions are applied," and that phrasing matters: the Epic → Story → Task → Bug hierarchy and the Definition-of-Done rules it enforces only stay consistent across a repository if every entry into the system passes through the same gate. An issue filed by hand "just this once, it's a small one" skips precisely the convention-application step the skill exists to provide, and that kind of one-off exception is how a project management system quietly drifts out of agreement with its own stated hierarchy — the same failure mode as an unreviewed, ad hoc schema change, just one layer up. That coverage extends to the process artifacts themselves, not only the issues filed against them: writing an issue template or a pull-request template is GitHub-process work like any other, not a plain-file exception to the rule, because a template is the actual mechanism through which the hierarchy and field conventions reach every future issue anyone files against it. A template built freehand, outside the skill, bakes an unreviewed convention into every issue that follows it.

## Schema design or database-contract work routes to the schema architects

Any work that designs, extends, or reviews a relational schema — or the API surface built directly on top of it — routes to one of two installed skills, `data-contract-architect` and `db-architect-holistic`. Both describe the same underlying discipline: the schema and its API contract are designed as one binding, cross-layer package — DDL, junction and reference tables, migration plans, and the full CRUD endpoint spec produced together — rather than the schema designed first and an API bolted on afterward as an independent pass that can quietly drift out of sync with it. That's the same commitment CLAUDE.md's database-first rule already makes for this project: schema as the source of truth, with migrations written before the application code that depends on them. Either of the two skills applied to a piece of schema work satisfies this routing rule; the point of naming both is that a session reaching for schema work has no excuse to skip past this step to a hand-written `CREATE TABLE` and a separately hand-written endpoint, since a skill built for exactly that combined package is already available.

## Mapping and "how does this connect" questions route to graphify

Any question about how this codebase's pieces relate to each other — which module depends on which, how a concept document maps to the architectural layer it describes, or "how does this all fit together" in the general sense — routes to `graphify`, which turns code, docs, and other project material into a persistent, queryable knowledge graph with community detection and query/path/explain tools. This project's own token-economy policy (`docs/governance/TOKEN_ECONOMY.md`) already flags that re-reading source material defensively, "just to be sure," is one of the easiest ways a session burns through its context budget in this repository specifically, because the concept documents under `docs/inputs/concepts/` are long and re-reading several of them to answer one structural question is expensive every single time it happens. Graphify is the answer to that same problem applied to connection-mapping questions: build the graph once, persistently, and query it — trace a path, ask what a node connects to, get an explanation — instead of re-reading and re-summarizing the same files by hand whenever a "how does X relate to Y" question resurfaces in a later session.

## Rebasing a branch onto its Gitflow target routes to smart-rebase

Bringing a `feature/*`, `release/*`, or `hotfix/*` branch up to date with the branch it was cut from — a `feature/*` branch onto `develop`, a `release/*` or `hotfix/*` branch onto `main`, per the Gitflow model `docs/governance/GIT_WORKFLOW.md` establishes — routes to `smart-rebase` rather than a freehand `git rebase` run straight from the terminal. The reason isn't that `git rebase` is hard to invoke; it's what happens the moment it hits a conflict: git stops and hands back raw `<<<<<<< HEAD` markers with no opinion about which side is right, and resolving that correctly by hand means reconstructing, from a diff alone, what two people were each trying to accomplish before merging their intent back into one file. `smart-rebase` does that reconstruction explicitly — reading both sides of every conflicting hunk, reasoning about each side's intent, and proposing a resolution with its reasoning — instead of leaving that judgment call to whoever happens to be running the rebase that day, under time pressure, with no record of the reasoning behind whichever resolution they picked. The case for routing here is sharper than most of the others in this document, because a rebase carries a risk none of this project's other routed work does: it rewrites commit history, and a wrong resolution pushed over a shared branch is a genuinely hard thing to undo cleanly. That's exactly why `docs/governance/INTELLIGENT_REBASE.md` — the contract `smart-rebase` implements — holds the line so firmly on a human approving every resolution before it's applied: routing to this skill doesn't just make conflict resolution more consistent the way the other rules in this document do, it's the difference between that judgment call being made with reasoning a human can actually check, or being made silently by whoever's hands are on the keyboard in the moment.

## Why routing is the default, not an exception

Every rule above points at the same underlying reason, even though the standard being encoded doesn't always come from the same place. Three of the six rules route to a skill that carries out something this project already wrote down for itself: the twenty-point security checklist and the database-first schema discipline both trace directly to CLAUDE.md's own rules, and so does the requirements-before-implementation sequencing that brainstorming enforces. The project-management rule is different in origin, not in kind — the Epic → Story → Task → Bug hierarchy and the Definition-of-Done rules aren't something CLAUDE.md specified first and `github-project-management-orchestrator` merely carries out; that hierarchy is the skill's own domain expertise, and routing to it is how this project adopts a coherent standard instead of inventing a slightly different, less consistent one from scratch each time an issue gets filed. The rebasing rule sits closer to the project-management rule than to the first three: the Gitflow branch model `smart-rebase` operates within was adopted from outside this project at the repo owner's explicit request, the same way the Epic → Story → Task → Bug hierarchy was, while the human-approval gate `docs/governance/INTELLIGENT_REBASE.md` holds it to is this project's own governance pattern — the same one already established for `claude-md-sync` — applied a second time, to a higher-stakes kind of write. Either way, the skill is where the standard actually lives, encoded once in a place built to apply it consistently, rather than left to be reconstructed from memory inside whichever session happens to be doing the work that day. Freehanding a piece of work a skill already covers rarely looks wrong in the moment; a hand-written security check or a manually filed issue can look entirely reasonable in isolation, which is exactly what makes the habit risky — the gap between the freehand version and the actual standard only shows up later, as an inconsistency between sessions, or as a category of check that quietly got skipped just this once. Treating routing as the default, rather than as a step reserved for work that's obviously large or obviously in-scope, is what keeps that gap from opening in the first place. The question worth asking before starting any nontrivial task in this repository isn't "is this big enough to justify a skill" — it's "does a skill already cover this shape of work," and when the answer is yes, that skill is where the work starts, not where it gets escalated to after a freehand attempt runs into trouble.
