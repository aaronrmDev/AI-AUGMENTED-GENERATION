# Git Workflow: The Gitflow Branch Model

CLAUDE.md's git-native section fixes what an individual commit and branch look like — Conventional Commits, `feat/123-short-desc` naming — without saying how multiple branches are supposed to relate to each other once more than one is alive at a time. A single branch cut from `main` and merged straight back can't hold more than one thing at once — it can't let two features build in parallel, let a release stabilize without blocking the next batch of feature work, or let an urgent production fix land without either branch getting in the other's way — which is exactly the situation this project hit the moment real implementation work began. Those are exactly the situations Atlassian's Gitflow model was built to handle, and at the repo owner's explicit request this project adopted it before any of that implementation work started: five branch types with defined roles — `main`, `develop`, `feature/*`, `release/*`, `hotfix/*` — layered on top of the naming and commit conventions CLAUDE.md already states, not replacing them. This document is that layer: what each branch type is actually for, the deliberate ruling that settled real merge commits as the practice for every branch type here, how the model has actually played out in practice since, and where versioning and the existing commit/PR conventions fit in.

## The branch types, and why each one exists

`main` keeps the property it already has today: everything on it is production-ready, and it only ever receives code through a release or a hotfix landing, never through day-to-day work committed straight to it. Its history is meant to read as a release history — walking `main`'s commits back should show the sequence of things that actually shipped, not the full mess of everything anyone tried along the way to shipping them.

`develop` is the branch Gitflow adds underneath `main`: the integration branch where finished feature work accumulates before anyone has decided it's ready to ship. It exists because "production-ready" and "done with the current batch of work" are genuinely different states — `develop` can sit ahead of the last release, carrying several finished features nobody has cut a release for yet, without ever putting `main` in a state that isn't safe to deploy. Nothing deploys from `develop` directly; it is the staging ground `main` gets cut from once a release is actually ready.

`feature/*` branches are where the actual day-to-day work happens. Each one is cut from `develop`, scoped to a single feature or piece of work, and merged back into `develop` — never into `main` directly — once that work is done. They're meant to be short-lived and numerous: several can be in flight from `develop` at once without interfering with each other, which is the entire point of pulling feature work off `main` in the first place. Naming follows Gitflow's own type prefix — `feature/123-short-desc` — rather than the pre-Gitflow `feat/123-short-desc` form CLAUDE.md's git-native section named on its own before this project adopted Gitflow; see the naming ruling below for why that's a deliberate supersession, not a second, conflicting convention.

`release/*` branches exist for the narrow window between "`develop` has enough finished features to ship" and "it's actually shipped." A release branch is cut from `develop` at that point, and nothing new gets built on it — no new features, only the stabilization a release actually needs: bugs surfaced by final testing, documentation fixes, a version-number bump. That isolation is the point: `develop` keeps absorbing the next batch of feature work in parallel while the release branch is held to a stricter "fix only what's broken" standard. Once it's stable, a release branch merges twice — into `main`, where the merge point gets tagged as the new release, and back into `develop`, so any fix made during stabilization isn't silently lost the next time `develop` ships.

`hotfix/*` branches cover the case a release branch can't: a production bug on `main` that needs a fix now, before the next planned release is anywhere near ready. A hotfix branch is cut directly from `main` — not `develop`, since whatever `develop` currently holds may be far from release-ready — carries the minimal fix and nothing else, and merges back into both `main`, tagged as a new patch release, and `develop`, for the same reason a release branch does: without that second merge, the next regular release would silently overwrite the hotfix the moment it shipped.

## Reconciling Gitflow with this repo's existing conventions — rulings, not givens

Naming is the first place Gitflow and this project's prior rules collide. CLAUDE.md's git-native section names `feat/123-short-desc` as this project's branch-naming convention, written before this project adopted Gitflow at all. Gitflow's own branch types, established above, are literally named `feature/*`, `release/*`, and `hotfix/*` — a different prefix, `feature/`, not `feat/` — and that's the form this project's own governance already uses consistently everywhere else Gitflow branches come up: `docs/governance/SKILL_ROUTING.md`, `docs/governance/INTELLIGENT_REBASE.md`, and the `smart-rebase` skill's own frontmatter all describe the type as `feature/*`. A `feature/*` glob does not match a `feat/123-short-desc` branch name, so applied literally, CLAUDE.md's `feat/123-short-desc` and Gitflow's `feature/*` describe two different, incompatible prefixes for what was supposed to be the same branch — not a stylistic variance, a genuine contradiction. Here is the ruling: adopting Gitflow's branch types supersedes the pre-Gitflow `feat/123-short-desc` convention for exactly the branches Gitflow now governs. A feature branch cut from `develop` is named `feature/123-short-desc`, not `feat/123-short-desc`, from this document forward. CLAUDE.md's `fix/456-bug-desc` form is untouched by this ruling, since Gitflow has no `fix/*` branch type for it to collide with — that prefix stays available for ad hoc work outside the feature/release/hotfix model.

Squash-merging raised a second conflict, on a different axis, when this document first reconciled Gitflow with this project's prior rules. Atlassian's Gitflow model, as it's commonly documented, doesn't specify squash merging anywhere; the traditional description assumes ordinary merge commits throughout, on the reasoning that Gitflow's own guarantees depend on that merge structure being visible in history. CLAUDE.md's git-native section, independently, named squash-merging into `main` as this project's existing convention. This document's first ruling on that conflict held `feature/*` branches to a squash merge into `develop` and reserved real merge commits for `release/*` and `hotfix/*` landing on `main`. Practice has gone the other way ever since: every branch merge that has actually happened since Gitflow was adopted — `feature/*` into `develop`, and `release/*` and `hotfix/*` into both `main` and `develop` — has landed as a real, non-squashed merge commit, and no squash merge is identifiable anywhere in that history. This document now revises its first ruling to match: `feature/*` branches merge into `develop` with a real merge commit, the same way `release/*` and `hotfix/*` branches merge into `main` and `develop`.

The reason to keep it that way is the same reason Gitflow wanted real merge commits on `main` in the first place: they make a release tag traceable back to the branch that produced it, and let `main`'s history show which release a given hotfix landed in. That reasoning extends to `feature/*` merging into `develop` too. A `merge: feature/<n>-<desc> -- <summary>` commit on `develop`'s first-parent line already reads as one entry per finished feature — exactly the readability a squash merge was meant to buy, without the squash's cost: this project's plans cite task commits by hash in their execution notes, and issue closing comments do the same, so squashing a `feature/*` branch would orphan every one of those citations the moment the branch is deleted, where keeping the real merge preserves them. So `develop` and `main` now share the same rule — every branch type lands with a real merge commit — for reasons that turn out to be the same reason in both places: history that stays traceable and citable once the branch that produced it is gone.

## Where this stands today

This model is in active use, not just design intent. `develop` was cut from `main` once real implementation work began, and every batch through the first release — the full RAG pipeline (6 batches), the full MAG memory system (7 batches), three of CAG's nine techniques, and all three cross-paradigm synthesis pairings — landed through its own `feature/*` branch, cut from `develop`, merged back into it as a real merge commit once that batch's own adversarial review passed. `develop` sat ahead of `main` by 185 commits before this first release, which is exactly the "several finished features nobody has cut a release for yet" state this section describes as the reason `develop` exists. This document's own fix is itself an example of the "stabilization only" work a `release/*` branch is meant to carry — a documentation correction caught during release preparation, landing on `release/1.0.0` rather than as a new `feature/*` branch, per the ruling above. That branch went on to merge as planned, tagged as `v1.0.0`, and the `hotfix/*` lifecycle described above has since been exercised five times, not twice: five hotfix branches, cut from `main` and merged back into both `main` and `develop` per the ruling above, shipped as `v1.0.1` through `v1.0.5`. Work on `develop` kept going after that fifth hotfix, through the same `feature/*`-branch-and-real-merge pattern: CAG's remaining techniques and combinations, the orchestration meta-layer batches, and the unified API endpoint have each landed through their own `feature/*` branch merged into `develop`. `develop` is now 107 commits ahead of `main`, with no release cut since `v1.0.0`.

## Versioning and tagging

Releases are tagged on `main` using semantic versioning (`MAJOR.MINOR.PATCH`), at the point a `release/*` branch merges in — that merge is what a tag actually marks, and it's the mechanism that turns `main`'s commit history into a readable sequence of shipped versions rather than an undifferentiated stream of merges. A hotfix that merges into `main` outside the normal release cycle gets its own patch-version tag at that same merge point, for the same reason.

## Commit messages and pull requests

Commit format is already specified by the template at [.gitmessage](.gitmessage), and what a pull request has to include before merge is already specified by [.github/PULL_REQUEST_TEMPLATE.md](.github/PULL_REQUEST_TEMPLATE.md); both apply unchanged on every branch type described above, exactly as they did before this document existed, so neither is restated here.
