# Intelligent Rebase Contract

`docs/governance/GIT_WORKFLOW.md` fixes the shape this project's branches take once real implementation work begins: `feature/*` branches cut from `develop`, `release/*` and `hotfix/*` branches cut from and merged back into `main` and `develop`, with a deliberate ruling on which of those merges squashes and which keeps real merge commits. What that document doesn't need to cover, because it's a different problem, is the moment that happens *before* any of those merges — the point where a `feature/*` branch that's been alive for a few days needs to catch up with a `develop` that kept moving without it, or a `release/*` branch needs to absorb a `hotfix/*` that landed on `main` while stabilization was still underway. Catching a branch up with its target that way, without merging it yet, is exactly what `git rebase` is for, and it's exactly the git operation most likely to leave a contributor staring at a file full of raw `<<<<<<< HEAD` / `=======` / `>>>>>>>` markers with no explanation of which side to keep. This document specifies the contract for a skill named `smart-rebase`, whose job is to make that specific moment easier to get through correctly without making it any less supervised: it reads a conflict, reasons about it, and proposes a resolution — but deciding what actually happens to the branch's history stays with the human, every single time, with no exception carved out for confidence or convenience. What follows is meant to be precise enough that whoever builds `smart-rebase` — in this case, the same work that produces this document — has no ambiguity left to fill in on their own, following the same discipline `docs/governance/AUTOLEARNING.md` sets for `claude-md-sync`: the behavior described here is the behavior the skill needs to have, not a rough sketch for someone to improve on later.

## When it runs

`smart-rebase` is on-demand, the same way `claude-md-sync` is: nothing schedules it, and nothing runs it automatically in the background. It's invoked when a human — or an agent working in this repository, asked to bring a branch up to date — needs a `feature/*`, `release/*`, or `hotfix/*` branch (per `GIT_WORKFLOW.md`'s model) rebased onto the branch it was cut from: a `feature/*` branch onto the current tip of `develop`, or a `release/*` or `hotfix/*` branch onto the current tip of `main`. It is not a substitute for the final merge step `GIT_WORKFLOW.md` already specifies — squash-merging a finished `feature/*` branch into `develop`, or the real merge commits that land `release/*` and `hotfix/*` work on `main` and `develop` — it exists for the narrower moment before that, when a branch that isn't finished yet needs to stay current with a target that kept moving while it was being worked on. As `GIT_WORKFLOW.md` itself notes, this repository has only `main` today; there is no `develop` and no `feature/*`, `release/*`, or `hotfix/*` branch yet for this skill to operate on. That doesn't make the contract premature — it makes it ready: the first time a real rebase against a live `develop` or `main` is needed, the skill this document specifies is already built and already scoped, rather than being designed under the time pressure of an actual conflict.

## What "intelligent" means here

Run without help, `git rebase` replays a branch's commits one at a time onto a new base and stops cold the instant one of them touches a line the target branch also touched — at which point the contributor is looking at raw conflict markers stacked in a file, with git offering no opinion at all about which side is right, only that both sides changed something. `smart-rebase` exists to close that gap between "git detected an overlap" and "a person understands what the overlap actually means." For every conflicting hunk, it reads both sides in full — the commit being replayed and the commit already on the target branch that it collides with — and asks what each side was actually trying to accomplish: was this a rename that the other side's edit didn't know about, a bugfix layered onto code the other side refactored, two independent additions to the same list that both belong in the result, or a genuine disagreement about what the code should do. From that reasoning it proposes a specific resolution — the actual merged text, not a description of one — together with the reasoning that produced it, stated in enough detail that a human reviewing the proposal can tell whether the skill understood the conflict correctly without having to re-derive the answer from scratch themselves. That per-hunk reasoning is the entire difference between this skill and running `git rebase` with a blanket `--strategy-option=ours` or `theirs`: a blanket strategy discards one side's intent uniformly and calls whatever's left correct, where `smart-rebase` treats each hunk as its own question with its own answer, because two conflicts three lines apart in the same file can easily need opposite resolutions.

## What it does when it isn't confident

Not every conflict resolves into a clean story about intent. Some hunks are genuinely ambiguous even after reading both sides closely — the two changes contradict each other at the level of what the code should do, not just how it's phrased, and no amount of re-reading turns that into a confident answer. When that happens, `smart-rebase` says so plainly and escalates the hunk to the human instead of picking a side and presenting it with the same confidence as a clear-cut case. A wrong conflict resolution is worse than no resolution at all: an unresolved conflict is visibly unresolved and stops the rebase where anyone can see it, where a wrong resolution that reads smoothly can slip through review and land silently in `develop` or `main`, undetected until whatever it broke shows up somewhere else entirely. The same rule applies to a whole rebase, not just a single hunk — if the number or nature of the conflicts suggests the two histories have diverged too far for hunk-by-hunk reasoning to be trustworthy (a long-abandoned branch, a target that's been substantially restructured since the branch split), `smart-rebase` says that too, rather than working through dozens of hunks at declining confidence and presenting all of them with equal certainty.

## The hard constraint: it proposes resolutions, it never finalizes them

**`smart-rebase` never force-pushes, never finalizes a rebase, and never rewrites branch history that's already been pushed or shared, without the human explicitly reviewing and approving each proposed resolution first.** It presents a proposed resolution for a human to look at — it does not stage it, does not edit the conflicted file, does not run `git add`, does not run `git rebase --continue` on its own judgment, and does not run `git push --force` (or `--force-with-lease`) under any circumstance the skill itself decides. This is not a softer version of the constraint `claude-md-sync` operates under — it is a stricter one, because a rebase is a fundamentally more dangerous action than a proposed documentation edit. A `claude-md-sync` proposal that goes wrong is a wrong sentence sitting in a markdown file until someone corrects it; a rebase that goes wrong is rewritten commit history, and once that history has been force-pushed over a branch other people have already pulled from, undoing it well enough that everyone's local copy converges again is a genuinely hard problem, not a one-line fix — reflogs expire, collaborators' local branches diverge further with every commit they make on top of the bad state, and "just revert it" doesn't apply cleanly to history that's already been rewritten and shared. That asymmetry — a wrong edit that's trivially reversible on one side, a wrong rewrite that may not be cleanly reversible at all on the other — is exactly why this gate has to be stricter here than anywhere else `claude-md-sync`'s pattern has been applied so far. Concretely: `smart-rebase` walks the human through each conflicting hunk's proposed resolution one at a time and stops — leaving the rebase paused, mid-flight, exactly where git would leave it — the moment it hits a hunk it isn't confident about or a resolution the human hasn't yet reviewed. Applying an approved resolution — editing the conflicted file to match it, running `git add`, and running `git rebase --continue` once every conflict in the current step is resolved — is something the human does themselves, in their own shell, outside this skill entirely; it is never an action this skill takes on the human's behalf, even for a resolution the human has already approved. Finishing the rebase and publishing it (`git push`, force or otherwise, to a branch other people can see) are, likewise, both actions a human takes deliberately, never actions this skill takes because it judged the moment was right. As with `claude-md-sync`'s own hard constraint, this is not a preference weighed against convenience — if there is ever tension between making `smart-rebase` faster or more automated and this constraint, the constraint wins outright, with no exception.

## Where it belongs

`smart-rebase` is specified as a project-level skill, living under `.claude/skills/` and committed to the repository the same way `claude-md-sync` is, rather than as a personal skill available only in one contributor's local environment. The branch model it operates within is a shared, repository-wide convention — every contributor rebasing a `feature/*` branch onto `develop`, or a `release/*` or `hotfix/*` branch onto `main`, is working inside the same Gitflow model `GIT_WORKFLOW.md` establishes for everyone — so the tool that makes that operation safer has to be equally available to everyone doing it, not a safeguard one person happens to have installed while everyone else on the same branch model rebases unaided.
