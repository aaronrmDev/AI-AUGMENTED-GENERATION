# MAG Batch G: Combinations — Live Measurement Report

**Scope:** #19/#78 (Living Agent), #22/#79 (Context Wizard), #24/#80 (Self-Improving Agent), #26/#81 (Relationship-Aware Agent) — the "MAG: Combinations" milestone, four story+task pairs, no single parent issue. See `docs/superpowers/specs/2026-08-29-mag-combinations-design.md` for the design and why this batch verifies through MAG's own narrative convention rather than RAG Batch E's scenario-script one.

## What these four issues actually asked for

Every constituent technique (Episodic, Semantic, Consolidation, Procedural, Memory Hierarchy, Retrieval Strategies, Memory Gating, Memory Graphs) already existed from Foundation through Batch F. What remained was narrower: prove the *composition* MAG.md describes for each archetype genuinely produces the emergent behavior it claims, not just that the pieces work in isolation — each already covered by its own batch's test suite. Three of the four archetypes needed no new production code at all; only Self-Improving Agent did, because `ConsolidateEpisodes` never had a path to procedural memory.

## Living Agent (#19/#78) — knowledge compounding across sessions

`CaptureEpisode` and `ConsolidateEpisodes` were already fully wired; the report needed to prove the *loop*, not one pass of it. Two separate sessions for the same user, consolidating after each: session 1 (two reinforcing episodes about a Python preference) reliably extracted at least one fact across every live run (`favorite_programming_language` / `preferred_programming_language`, phrasing varied run to run against the live, unseeded qwen3.5 model). Session 2 (two reinforcing episodes about an AWS deployment preference — a second, unrelated preference, not a restatement) extracted a new fact every run (`preferred_cloud_provider` / `primary_cloud_provider` = "AWS"). After session 2 ran, every one of session 1's facts was re-fetched by its own `fact_key` and its value checked byte-for-byte against what session 1 originally produced — proving the fact survived session 2's entirely separate consolidation pass unmodified, not merely that *some* fact with a matching key still existed.

Two real bugs surfaced and were fixed before any of this was trustworthy. First, an early fixture had the *assistant* state the Python preference rather than the user — the consolidation prompt correctly declined to extract it, since it only attributes preferences to self-reports. Second, the first version of the survival check compared a bare `"python"` substring against the retrieved fact pool, which can't distinguish session 1's fact surviving from session 2 independently producing an unrelated fact that happens to share a word — and a follow-up review round caught that switching to a fact_key-membership check *still* wasn't enough, since `RecordSemanticFact`'s id is deterministic on `(user_id, fact_key)` alone: a coincidental key collision between two independent LLM calls would silently overwrite session 1's value while the key itself stayed present. Only a direct value comparison against session 1's own recorded output closes that gap.

## Context Wizard (#22/#79) — gating over real retrieved data

`GateMemories` (Batch E) already consumes exactly the return types Batch C's retrieval strategies and Batch D's spreading activation produce. The report ran retrieval across two tiers — a captured episode and a directly-recorded fact, both about the same Python topic — through real `search_by_similarity` reads, then fed both candidates through `GateMemories`. Across two live runs the episode scored 0.6482 and the fact 0.7073; `GateMemories` returned `[fact, episode]` both times, reproducing MAG.md's "places user preferences and task-critical facts first" example end to end.

An earlier draft of this test tried to force the episode to score *above* the fact, reusing the trick `RecordSemanticFact`'s own review-driven fix relies on for facts (setting content to the query text verbatim). It doesn't transfer: `CaptureEpisode` embeds the whole JSON-encoded content dict, not a bare string, so identical text doesn't maximize cosine similarity the same way. The design spec originally described this section as needing a "measurable improvement... concrete before/after" comparison — a fix-wave review round caught that this claim was never actually deliverable through `HierarchicalAssembly`, whose fact-before-episode ordering is unconditional on either candidate's raw score by design (already proven at the unit and Batch E/F integration level). The spec was corrected to describe what the test actually proves: the full retrieval-to-gating chain holding together against real, not hand-built, retrieved data.

## Self-Improving Agent (#24/#80) — the one new command

MAG.md's claimed mechanism for this archetype ("Consolidation analyzes which episodes succeeded and which failed, and extracts reusable Procedural memories") had no implementation anywhere in this codebase — `ConsolidateEpisodes` only ever writes semantic facts. `ConsolidateProcedures` (`src/mag/application/commands/consolidate_procedures.py`) is the new command this batch adds: structurally mirroring `ConsolidateEpisodes`'s retry/validate/dedupe shape, but reflecting on a batch for a *repeated* task pattern rather than a single durable fact, and taking its episode batch as an explicit parameter rather than owning its own `consolidated_at` lifecycle (procedural extraction has no one-shot semantics the way fact extraction does — the same episode can legitimately contribute to more than one future pattern detection).

Two episodes recording the same FastAPI deployment succeeding via the same three-tool workflow (Docker, Gunicorn, Nginx) reliably produced a `ProceduralMemory` row across every live run: task_pattern "Deploy FastAPI app to production", workflow containing all three tools, positive success_rate — reproducing MAG.md's five-deployments-to-one-procedure example structurally with the minimum repeat count a "pattern" can mean.

## Relationship-Aware Agent (#26/#81) — graph traversal, no LLM judgment needed

The most directly demonstrated archetype: `CaptureEpisode` already writes `MENTIONS` edges from `content["entities"]`, so a one-off booking episode mentioning "Paris" is reachable from the entity alone via `SpreadingActivationRetrieval`, without ever searching the episode's raw text. Every run reached exactly one `Episode` node, one hop from the entity, whose content genuinely contained the booking. Deliberately does not depend on `ConsolidateEpisodes` succeeding — MAG.md's own episodic-memory definition treats a single instance-specific event as legitimately episodic, not something an LLM should be expected to generalize into a semantic fact, so a decline to extract is a valid outcome, not a test failure.

## What two full review rounds caught

**Round one** (four-dimension adversarial review) confirmed 9 of 14 raw findings. The most consequential:

- **A silent composition-starvation hazard between the two consolidation commands.** `ConsolidateEpisodes.execute()` unconditionally marks every episode it fetches as consolidated, regardless of whether a fact was extracted. A caller building `ConsolidateProcedures`'s episode batch via the obviously-named `get_unconsolidated_by_session` *after* `ConsolidateEpisodes` has already run over that window gets `[]` back — silently, no exception, no log — permanently skipping procedure extraction for a session that may have a genuine repeated pattern sitting right there. The design spec had gestured at this coupling in one sentence without naming the actual failure mode or a workaround. Fixed by documenting the hazard directly on `get_unconsolidated_by_session`'s docstring and `ConsolidateProcedures`'s own class comment, with the concrete fix: build the batch via the unfiltered `get_by_session` instead, whose result is unaffected by `mark_consolidated`.
- **`_validate_and_dedupe_procedures` checked `workflow`'s type but not its emptiness**, unlike `task_pattern`'s explicit non-empty check — an LLM returning `workflow={}` for a genuinely repeated pattern would silently persist a stepless "procedure," defeating the entire point of the extraction.
- **The Living Agent test's original survival check was a bare substring match**, and it never asserted the spec's other compounding claim (a new fact appearing in session 2) at all — session 2's original fixture was also a request/recommendation exchange with nothing for the extraction prompt to attribute to the user, the identical fixture-authorship bug already fixed once for session 1.
- **Two byte-for-byte duplicate prompt-formatting functions**, one in each consolidation command's own prompt module, with no shared helper the way this codebase already extracts `strip_markdown_fence` — a future formatting fix to one would silently never propagate to the other.
- The Context Wizard spec's overclaimed "measurable improvement" language (above), and generic non-emptiness assertions in the Self-Improving Agent test that couldn't distinguish genuine two-episode synthesis from a hypothetical single-episode bug.

**Round two** (a scoped re-review of round one's own fix wave) confirmed all 5 raw findings it produced — every one of them a defect *in the first fix wave's own fix*, not new ground:

- The new empty-workflow guard only rejected a literal `{}` — `{"steps": []}`, the system prompt's own documented shape, sailed through untouched, since a dict containing a `"steps"` key is truthy regardless of that list's contents.
- The new composition-safety integration test fetched its "safe" batch via `get_by_session` *before* `ConsolidateEpisodes` ran, so it never actually exercised the fetch-after ordering the hazard describes — `ConsolidateProcedures` takes episodes as a plain in-memory parameter, so a list fetched before the poisoning behaves identically regardless of which repository method built it. Restructured so `ConsolidateEpisodes` runs first and both the poisoned and working fetches happen after it.
- The switch to fact_key-identity for the Living Agent survival check still couldn't rule out a same-key overwrite (described above under Living Agent) — closed with a direct value comparison instead.
- The newly-added `assert len(facts_from_session_2) >= 1` rested on a single-episode fixture against a live, unseeded (temperature=1) model whose own system prompt explicitly authorizes declining low-confidence extractions — a real, if unobserved, flakiness risk. Mitigated with a second reinforcing episode, mirroring session 1's own repetition and this codebase's established precedent for keeping live-model confidence high.
- The strengthened Self-Improving Agent workflow assertion couldn't actually distinguish genuine two-episode synthesis from a single-episode echo, because both fixture episodes already embed the full three-tool workflow verbatim — closed as fully as a black-box narrative test can (requiring all three tools, not just one) with the comment corrected to stop overclaiming what output-content checking alone can prove.

## An honest observation, not a defect

The composition-safety test's two FastAPI-deployment episodes carry no explicit preference language, yet `ConsolidateEpisodes` extracted several facts from them across live runs (as many as 5 in one run) — the live model reading technical deployment content (tools, outcome) as durable characteristics worth recording, not just the philosophical-preference statements the Living Agent fixtures use. Not asserted on by any test in this batch (nothing here claims a specific fact count), but worth recording as a real, observed behavior of this system's consolidation prompt against technical episode content.

## Deliberately not written by this batch

- **No new production classes for Living Agent, Context Wizard, or Relationship-Aware Agent** — all three compose already-built primitives exactly as designed to compose.
- **No scenario-script harness, no LLM-judge quality scoring, no latency/token comparison tables** — MAG's own narrative-verification convention, not RAG Batch E's.
- **No automatic trigger for when consolidation (of either kind) should run** — a caller decides when to consolidate, matching every prior MAG batch's explicit-parameters convention.
- **`ConsolidateProcedures` does not attempt cross-user or cross-tenant pattern generalization** — task-pattern matching operates per-user, per-session-batch.
- **No production caller composes `ConsolidateEpisodes` and `ConsolidateProcedures` together yet.** The composition-starvation hazard above is real and now documented with a proven-safe pattern, but nothing in this codebase currently exercises that composition outside the dedicated test — the fix is a documented contract for whoever writes that caller next, not a currently-firing bug.
