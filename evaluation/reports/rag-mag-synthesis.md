# Cross-Paradigm Batch E: RAG+MAG Synthesis — Live Measurement Report

**Scope:** #45 (story, umbrella validation), #6 (story, State-Aware RAG), #20 (story, warm/cold tiering boundary), #34 (story, Sync Mixer tiebreak), #59/#71/#83/#86 (their four tasks). See `docs/superpowers/specs/2026-09-02-cross-paradigm-rag-mag-design.md` for the design, and `docs/architecture/OVERVIEW.md`'s "State-Aware RAG," "Tiered Knowledge Hot-Cold Architecture," and "The sync mixer's tiebreak rule: RAG wins" for the source material.

## What OVERVIEW.md asks for

Three named mechanisms under the RAG↔MAG pairing: **State-Aware RAG** (read MAG's state before retrieval runs, rewrite the query to be personal instead of generic, boost ranking for results matching the user's known context, write back what came back), the **RAG↔MAG warm/cold tiering boundary** (promote frequently-accessed cold data into MAG's personal warm tier, demote rarely-accessed warm data back to cold), and the **Sync Mixer's RAG-vs-MAG tiebreak** (RAG wins when MAG's session state disagrees with RAG's current index).

This batch deliberately does not reuse Batch D's (RAG+CAG) tenant-only `AccessFrequencyTracker`/`FrozenCache`/`TieringPolicy`: MAG's warm tier is inherently personal (every MAG table is `user_id`-keyed), so reusing tenant-only ports would conflate different users' access patterns for the same document — a real correctness bug, not a simplification. New, user-scoped ports (`UserScopedAccessFrequencyTracker`, `WarmStore`) were built instead, while `sync_mixer.reconcile` (genuinely paradigm-agnostic) was generalized and reused directly across both pairings.

## `src/orchestration/` — this batch's real content

`domain/`: `WarmEntry` entity (MAG's warm-tier analogue of `CacheHit` — a real string, not an opaque KV-cache handle, since MAG's warm tier is a semantic fact); `UserScopedAccessFrequencyTracker`/`WarmStore` ports (both `(tenant_id, user_id, document_id)`-scoped); `sync_mixer.reconcile` generalized from `CacheHit | None` to a plain `str | None` content hash. `application/`: `StateAwareRetrieve`, `MagTieringPolicy`, `MagSyncCycle`. `infrastructure/`: `InMemoryUserScopedAccessFrequencyTracker` (same retention-based pruning design as Batch D's tracker), `SemanticMemoryWarmStore` (wraps this project's existing real `PostgresSemanticMemoryRepository` + `QdrantSemanticMemoryIndex`).

Every real measurement below runs on already-established infrastructure: Qdrant/Postgres/Neo4j/Redis via testcontainers, `sentence-transformers` on CPU, and real Ollama (`qwen3.5`) — the same stack MAG's own seven merged batches already use. No GPU or vLLM anywhere.

## Real measured numbers

**State-Aware RAG (#6/#59):** a 3-document corpus, each document about a different Python visualization library (matplotlib, seaborn, plotly), deliberately worded so none names the other two — a real, live-measured run against an earlier draft caught seaborn's own honest "built on matplotlib" phrasing giving it undeserved keyword-overlap credit against a "prefers matplotlib" fact, a genuine corpus confound fixed by removing cross-references between documents. A real semantic fact ("strongly prefers matplotlib for all data visualization tasks") was recorded via `RecordSemanticFact` (existing MAG command, unmodified). Against the generic query "How do I visualize this data?":

> **Bare-query RAG's top result was NOT the matplotlib document — genuinely ambiguous, as the corpus was designed to be. State-Aware RAG's top result WAS the matplotlib document.** The real, honest answer to #6's Definition of Done ("does enrichment actually improve retrieval relevance over bare-query RAG?"): yes, measured directly, not assumed.

The real Ollama (`qwen3.5`) rewrite of "How do I visualize this data?" given that fact was "How do I visualize this data using matplotlib" — a clean, single-line rewrite with no extra explanation, confirmed by direct spike against the real model before writing any implementation. A real write-back episode was confirmed present in Postgres after the call, via `CaptureEpisode` (existing MAG command, unmodified).

**Warm/cold tiering boundary (#20/#71):** a real `InMemoryUserScopedAccessFrequencyTracker` + real `SemanticMemoryWarmStore` (real Postgres + Qdrant). A document given 10 real accesses under one user promoted (`TierDecision.PROMOTED`, crossing `promote_threshold=5`); the promoted content was confirmed actually readable back out of real Postgres via `warm_store.lookup`, not merely present in an in-memory dict. Once that user's traffic genuinely dried up in a later window, the same document demoted (`TierDecision.DEMOTED`). A second user's identical zero-traffic evaluation against the SAME `document_id` under the SAME tenant stayed `TierDecision.UNCHANGED` and was confirmed absent from that user's own warm tier — real, direct proof that this batch's whole reason for not reusing Batch D's tenant-only tracker (avoiding cross-user promotion) actually holds against real infrastructure, not just in a unit test with fakes.

**Sync Mixer RAG-vs-MAG tiebreak (#34/#83):** a real content change (a method name swapped in the promoted document's text, the same "$100 to $80" shape as OVERVIEW.md's own worked example) written into the warm store's authoritative-content comparison. Polling `MagSyncCycle.run` on a real 50ms interval:

> **Real measured detection-to-correction latency: 22.3ms** — against OVERVIEW.md's own explicitly "illustrative, not an SLA" five-minute figure. This measures the mechanism's own real overhead once triggered on a synchronous poll, the same disclosure Batch D's own report already established for the RAG-vs-CAG case: not a claim about production batch-cycle cadence, which is a separate, unrelated scheduling decision.

**Combined Capability Validation (#45/#86):** the State-Aware RAG comparison above IS this pairing's baseline-vs-combined delta — a real corpus where bare RAG measurably fails to disambiguate and state-aware retrieval measurably succeeds, plus the tiering and sync mechanisms independently confirmed against real infrastructure. This replaces OVERVIEW.md's "targets, not results" status for the RAG+MAG combination with an actual measured comparison.

## A real design bug caught and fixed during implementation, not by review

`StateAwareRetrieve`'s first implementation asked the fallback retriever for exactly `top_k` results before applying the ranking boost — with `top_k=1` (a realistic caller value), the boost step never got a chance to promote a better-but-lower-ranked document, since it was never in the 1-result candidate set to begin with. A real integration run against the (deliberately ambiguous) visualization corpus caught this directly: both baseline and state-aware retrieval returned the same wrong document. Fixed by adopting this project's own established over-fetch-then-rerank shape (`RerankingRetriever`'s `candidate_k`, `src/rag/infrastructure/reranking_retriever.py`): fetch `max(top_k, candidate_k=20)` candidates, boost, then truncate to the caller's actual `top_k`. Re-verified against the real corpus afterward — the fix directly produced the real measured result reported above. The corresponding unit test was strengthened to run at `top_k=1` specifically (it previously used `top_k=5` with only 2 canned candidates, which never actually exercised the code path this bug lived in) and a new dedicated test pins the over-fetch behavior directly.

A second, unrelated correctness bug was caught before any test ran at all: `SemanticMemoryWarmStore.lookup` originally treated any non-`None` `valid_until` as "invalidated," but the real `search_by_similarity` SQL's actual filter is `valid_until IS NULL OR valid_until > now()` — a future-dated `valid_until` means "valid until then," not "already invalid." Fixed to match the real comparison exactly, caught by reading the real Postgres implementation before writing the new code, not discovered later. A third, also caught pre-test: `SemanticMemoryRepository.invalidate`'s real implementation raises (`scalar_one()` on zero matching rows) rather than silently no-op'ing, so `WarmStore.demote` on a never-promoted document needed an explicit existence check first, matching `FrozenCache.evict`'s own established safe-no-op precedent.

## What adversarial review caught

A four-dimension review (correctness, test fidelity, honesty-and-scope, architecture-and-conventions) confirmed 5 of 6 raw findings; correctness and honesty-and-scope both found nothing, a real signal that the two bugs already caught and fixed during implementation (above) plus this batch's from-the-start per-user isolation discipline held up under scrutiny. The one refuted finding (a claimed `MagTieringPolicy` tenant-isolation coverage gap) was correctly refuted: `tests/unit/test_in_memory_user_scoped_access_tracker.py` already covers that exact axis at the tracker layer directly.

- **`MagSyncCycle`'s tests only exercised per-user isolation, not per-tenant** — unlike its Batch D sibling `test_sync_cycle.py`. Added `test_a_conflict_for_one_tenant_does_not_touch_anothers_warm_entry`, parallel to the user-isolation test already there.
- **`SemanticMemoryWarmStore.demote()`'s existence-check guard (the one guarding `invalidate()`'s real crash-on-zero-rows behavior) had zero test coverage anywhere** — not even indirectly: `FakeSemanticMemoryRepository.invalidate` silently no-ops on a missing key instead of raising like the real Postgres implementation does, so no fake-backed unit test could ever have caught a regression here. Added a real integration test, `test_demote_on_a_never_promoted_document_is_a_safe_no_op_against_real_postgres`, that demotes a document that was never promoted (and, separately, demotes an already-demoted one) against real Postgres and asserts no exception — the only kind of test that can actually prove this guard works.
- **No unit test asserted the actual `user_id`/`tenant_id` values `StateAwareRetrieve` passes into `find_semantic_facts.by_similarity`** — `FakeSemanticMemoryRepository` ignores both for filtering, so a positional argument swap would have passed every existing test unnoticed. Added a spy-backed test (`test_facts_are_looked_up_with_the_real_user_id_and_tenant_id_not_swapped`); verified it has teeth by deliberately swapping the two arguments and confirming the new test — and only the new test — failed, then reverting.
- **`InMemoryUserScopedAccessFrequencyTracker` duplicated `InMemoryAccessFrequencyTracker`'s sliding-window/retention logic near line-for-line**, with no sync/async or physical-realization justification (unlike the genuinely-justified `TieringPolicy`/`MagTieringPolicy` and `SyncCycle`/`MagSyncCycle` splits, which differ because `WarmStore` does real I/O and `FrozenCache` doesn't). Extracted a shared, generic `SlidingWindowCounter[K]` (`src/orchestration/infrastructure/_sliding_window_counter.py`) that both trackers now delegate to, removing the duplication without changing either port's public interface — re-verified both trackers' full existing test suites pass unchanged against the refactored implementation.
- One real lint violation (a 104-character line in the new integration test file, this project's own `ruff` limit is 100) — fixed.

## What this batch does not do

- **Does not modify RAG's `Retriever` ABC.** `StateAwareRetrieve` is deliberately its own use case (`execute(tenant_id, user_id, session_id, query, top_k)`) rather than a forced, contract-breaking `Retriever` implementation — `Retriever.execute` has no `user_id`/`session_id` slot, and MAG's schema requires both.
- **Does not modify MAG's own domain layer, ports, or schema.** Every MAG read/write in this batch goes through existing, unmodified MAG application classes (`FindSemanticFacts`, `RetrieveWorkingMemory`, `CaptureEpisode`, `RecordSemanticFact`) and existing, unmodified MAG infrastructure.
- **Does not reuse Batch D's tenant-only `AccessFrequencyTracker`/`FrozenCache`/`TieringPolicy`.** Disclosed at length above and in the design spec: MAG's tier is inherently personal, and reusing tenant-only ports would be a real correctness bug.
- **Does not touch CAG.** CAG+MAG is a separate, later batch.
- **Does not require GPU or vLLM anywhere.**
