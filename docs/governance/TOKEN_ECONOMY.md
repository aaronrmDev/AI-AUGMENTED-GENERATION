# Token Economy

This project's own reference material was already unusually large before a line of application code existed, and has only grown since: the five source documents under `docs/inputs/concepts/` — the RAG, CAG, and MAG concept papers plus the two architecture-synthesis documents — run from roughly 850 to just over 1,000 lines apiece, and CLAUDE.md's governance layer already draws directly from them. The architecture docs under `docs/architecture/` this policy anticipated — written since, and drawing from those same five source documents just as directly — now sit alongside a much larger body of material this policy predates: a full `src/` implementation across RAG, CAG, MAG, and cross-paradigm orchestration, its 796-test suite, and roughly three dozen narrative evaluation reports under `evaluation/reports/`. A session that re-reads two or three source files or evaluation reports defensively, "just to be sure," burns a meaningful slice of a context window before any actual work has started, and that cost has grown exactly the way this document originally anticipated it would. Treating context as a budget rather than an afterthought isn't a generic best practice bolted on here for form's sake — it's a direct response to how large this specific codebase's source material already was and how much larger it has since become.

## Check usage while a session is still running, not after it's gone

The `/usage` command exists precisely so that context pressure doesn't have to announce itself the hard way, through an automatic compaction landing in the middle of a train of thought. During a long or research-heavy session — reading several concept documents back to back, tracing a decision across multiple ADRs, working through a multi-file rewrite — check `/usage` periodically rather than waiting for the system to compact on its own. The value of checking early is that it turns a hard cutoff into a choice: rising usage partway through a session is a signal to wrap up whatever sub-task is currently in flight and commit the progress that's already solid, then start the next piece from a clean context, rather than pushing further into one giant session and hoping an automatic compaction lands somewhere convenient. An agent that only discovers it's out of room when compaction actually fires has already lost the chance to decide where to stop; an agent that checks periodically gets to choose a natural breakpoint instead.

## Trust what the conversation already knows

Once a file's contents or a decision has already been established earlier in a conversation — a document was read in full, a design choice was made and explained — re-reading that same file defensively "just to confirm" spends exactly the budget the `/usage` habit above is trying to protect, for no new information. The better instinct is to trust the context that's already there: if a later step genuinely needs to check something specific, ask for the specific piece — a `git diff`, one changed section, a targeted search — instead of reloading the whole file from scratch. This matters more here than in a typical repository, for the same reason described above: a full re-read of `advanced_cag_concepts.md` costs about the same whether it's the first read of a session or the fourth, and repeating it out of caution rather than necessity is one of the easiest ways to run a session out of room before the actual work is done. The same logic applies to compaction itself, once it happens — whether triggered automatically or requested deliberately: treat the resulting summary as authoritative rather than as a cue to go re-verify everything it just summarized. Re-reading to double-check a compaction defeats the reason compaction exists in the first place.

## When repeated work earns its own skill

Some procedural knowledge is worth capturing once and reusing indefinitely, rather than re-explained in a paragraph every time it comes up. When the same piece of procedural knowledge — a recurring check, a recurring generation task — would otherwise have to be re-explained inline across multiple separate conversations, that repetition is the signal to package it as a skill with `skill-creator` instead of writing it out again from scratch every time. A skill pays for itself exactly when the tokens it saves across its future invocations end up exceeding the tokens it cost to build in the first place, which means a one-off task that will never recur isn't worth the overhead of formalizing, while a check the project will keep needing is. This repo's `claude-md-sync` skill is a concrete example already living here: instead of re-explaining, session after session, how to compare CLAUDE.md and its linked documentation against the actual state of the repository and work out what's drifted, that procedure was captured once as an on-demand skill instead. By design, it inspects CLAUDE.md and its linked docs against the repository's current state, and wherever it finds a mismatch, it proposes specific, itemized edits — file paths and reasoning included — for a human to review and approve, rather than applying anything on its own. Any future recurring task that fits the same shape — something that would otherwise mean explaining the identical procedure fresh in every conversation that needs it — is a candidate for the same treatment.

## A policy, not a permissions change

Everything above is a convention an agent follows because it understands the reasoning behind it, not a restriction imposed from outside: the `/usage` habit, the preference for trusting context over re-reading, and the skill-creator threshold all describe how a session should behave, and that behavioral scope is where this document stops — it doesn't modify `.claude/settings.json`, add or remove any tool permission, or gate any action behind a rule the system enforces mechanically. A future need to enforce token discipline structurally rather than by convention would be a distinct, deliberate decision made on its own terms, not something this document already implies.
