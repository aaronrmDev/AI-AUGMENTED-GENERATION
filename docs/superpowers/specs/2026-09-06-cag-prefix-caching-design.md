# CAG Batch D: Prefix Caching — Design Spec

**Scope:** #32 (story), #127 (task) — one technique, validated rather than reimplemented. See `docs/architecture/CAG.md`'s "How the five pipeline stages fit together" (Prefill paragraph) and `docs/testing/TESTING.md`'s own stated commitment for why this batch's shape differs from every CAG batch before it.

## Why this batch validates instead of implements

Every prior CAG batch (Compression, Speculative Decoding, Eviction) built the actual caching mechanism as real project code, because none of those techniques exist inside vLLM itself — this project had to write H2O's heavy-hitter scoring, KIVI's quantization, Medusa's draft heads, from scratch. Prefix Caching is different in kind: vLLM's own PagedAttention block manager already implements it, block-table sharing and copy-on-write included. There is no algorithm here for this project to author — CAG.md itself frames Prefix Caching as "the highest-ROI single optimization in the whole pipeline" precisely because the serving engine already does the work. What this batch owns instead is validation: does the real behavior underneath match what CAG.md claims, on this project's own hardware.

`docs/testing/TESTING.md` names this technique specifically as the one CAG correctness question that cannot be honestly answered without a real vLLM instance, and says why: the Latency-Adaptive Fallback Cascade is designed to trust a CAG cache hit unconditionally — return immediately, no MAG or RAG double-check — which only holds if a hit is actually correct. The two failure modes that matter (a genuinely different prefix incorrectly served a stale hit; eviction under memory pressure dropping the wrong blocks) are properties of vLLM's real PagedAttention implementation, not of any code this project could hand-roll around a `transformers` `past_key_values` object. A mock or a stand-in cache client, told to return "hit," returns "hit" regardless of whether the real block manager would have.

## What gets built

Since the caching mechanism itself isn't this project's to build, the real deliverable is a small, real HTTP boundary a future orchestration layer's CAG tier would actually use, plus the test that validates real behavior through it:

- **Domain** (`src/cag/domain/ports.py`): `CompletionServer(ABC)` — `complete(prompt: str, max_tokens: int) -> str`. One method, because the interesting behavior (cache hits, invalidation, eviction) lives entirely server-side and isn't observable through a completion's return value at all — only through the server's own `/metrics`.
- **Infrastructure**:
  - `src/cag/infrastructure/vllm_completion_client.py` — `VLLMCompletionClient`, a real client against vLLM's OpenAI-compatible `/v1/completions` endpoint, implementing `CompletionServer`. `temperature=0.0` for deterministic output. A `complete_timed()` convenience method returns real wall-clock request latency alongside the text — disclosed honestly as a proxy for TTFT rather than a true streamed measurement, since this client uses the non-streaming endpoint; the proxy stays tight because prefill (what a hit skips) happens before any output token regardless of streaming, and `max_tokens` is kept small (5) in every test so decode time stays a small, roughly constant addition on top of it.
  - `src/cag/infrastructure/vllm_metrics_client.py` — `VLLMMetricsClient`, parses vLLM's Prometheus-format `/metrics` text for `vllm:prefix_cache_queries_total` and `vllm:prefix_cache_hits_total`, summing every labeled series and matching both the with- and without-`_total` spelling a metric's name might appear under. This is the only honest source of "did a real cache hit happen" — the completions response itself carries no such signal.
- Both infrastructure classes accept an injectable `httpx.Client` (a real one by default, a `httpx.MockTransport`-backed one in unit tests) — the same dependency-injection shape this project already uses elsewhere to keep unit tests fast and CI-safe while the real behavior stays honestly verified against a live server.

## Testing plan — the first CAG batch whose real validation can't run in CI

Two tiers, but a genuinely different split from every prior batch:

1. **Unit tests** (`tests/unit/test_vllm_completion_client.py`, `test_vllm_metrics_client.py`), fast and CI-safe: exercise the HTTP client and metrics parser against a stubbed transport — request shape, deterministic-temperature payload, error handling, and the metrics text parser's own correctness (multiple labeled series summed, both metric-name spellings matched, a missing metric raising rather than silently returning zero). These tests validate the CLIENT code this project wrote; they cannot and do not validate real caching behavior, since a stub returns whatever it's told to.
2. **One integration test** (`tests/integration/test_cag_prefix_caching_against_real_vllm.py`) against a real vLLM server running with `--enable-prefix-caching` (`cd ~/cag-vllm && source .venv/bin/activate && vllm serve Qwen/Qwen2.5-0.5B-Instruct --port 8001 --enable-prefix-caching --gpu-memory-utilization 0.5`, per `project_gpu_infra` memory, adjusted down from 0.8 since ~5GB of this run's GPU was already in use by another process). This is the one CAG.md/TESTING.md actually commits to needing real vLLM: it sends a long shared prefix with one continuation (cold), the same shared prefix with a *different* continuation (proving real prefix-level reuse, not exact-string caching — the highest-ROI claim's whole point is that *different* requests share a prefix), and a prefix that genuinely diverges in its first sentence (proving no stale hit gets served). Real, disclosed finding from the first empirical run: a naive cold/warm/miss comparison with no warm-up call measured cold=0.215s slower than a later miss=0.045s purely from one-time GPU/kernel warm-up order, not real caching — fixed by adding a throwaway warm-up request on unrelated content before the three measured requests, after which cold=0.211s, warm=0.094s, miss=0.138s: warm now genuinely fastest, as it should be.

   **This test cannot run in CI, a first for this project's CAG batches.** GitHub Actions has no ROCm GPU; the test skips itself cleanly (`pytest.mark.skipif`, checked via a real reachability probe against the configured base URL) with a message naming exactly why, rather than failing CI or silently passing. It is also not run from this project's Windows-side `.venv`: this machine's WSL2 "mirrored" networking mode does not make the vLLM server's port reachable from the Windows host side (confirmed empirically — `Test-NetConnection` from native PowerShell returns `False` even though `curl` from inside WSL2 to the same IP succeeds immediately), so the test runs from inside WSL2 itself, using the `~/cag-vllm/.venv` Python that already has `httpx`/`pytest` installed alongside `vllm`/`torch`, invoked directly against the test file (not through the project's own `tests/integration/conftest.py`, which requires `alembic` and the rest of this project's full dependency set that the vLLM venv deliberately doesn't carry).

"Real result documented" for #127 means the actual hit-delta and latency numbers from this run, pasted into the issue's closing comment, the same disclosure standard every prior CAG batch already holds itself to.

## What this batch does not do

- **Does not reimplement vLLM's own prefix-caching or PagedAttention mechanism** — that's vLLM's job; this batch validates it against this project's own hardware rather than assuming CAG.md's description holds.
- **Does not wire into the (still unbuilt) Latency-Adaptive Fallback Cascade** — matches every prior batch's own "no application layer yet" disclosure; `CompletionServer` is a real, usable boundary for a future orchestration layer, not that layer itself.
- **Does not test eviction under real memory pressure** — filling a real vLLM cache to the point of forced eviction, then confirming a previously-cached-but-now-evicted prefix correctly misses again, is a real, valuable next validation but a separately scoped one; this batch's Definition of Done (hit reuse across different prompts, correct non-reuse on a genuinely different prefix) is met without it.
- **Does not run in CI** — disclosed above as a genuine first for this project, not smoothed over: this is local-hardware-dependent validation, the same category CAG.md previously (incorrectly) claimed applied to six techniques instead of the four (PagedAttention, Cache-Aware Batching, Hybrid Offloading, Multi-Turn Caching) that remain queued for implementation now that both Eviction and Prefix Caching have shipped.
