# Cross-Paradigm Batch D: RAG+CAG Synthesis — Design Spec

**Scope:** #10 (story, umbrella validation), #2 (story, Cache-Warmed RAG), #3 (story, hot/cold tiering boundary), #8 (story, Sync Mixer tiebreak), #18/#21/#25/#27 (their four tasks). See `docs/architecture/OVERVIEW.md`'s "Three named synthesis techniques this system commits to" and "The sync mixer's tiebreak rule: RAG wins" sections, and the orchestration meta-layer section above them, for the source material.

## Why this is the next batch

MAG's seven batches and CAG's first three batches (Alternative Attention, KV Cache Compression, Speculative Decoding) are complete and merged. Everything left in the CAG-only backlog needs real GPU/vLLM serving to measure honestly and is deliberately paused behind that infrastructure being set up with the user present. The cross-paradigm backlog — RAG+CAG (this batch), RAG+MAG, CAG+MAG — needs no GPU at all: it composes RAG's already-real Qdrant/embedding stack, CAG's already-real CPU/HF KV-cache methodology (proven out in CAG Batches B and C), and, for the other two pairings, MAG's already-real Redis/PostgreSQL/Neo4j stack. `src/orchestration/` is the one module named in OVERVIEW.md's Phase 1 blueprint that has never been started — these three cross-paradigm milestones are its first real content, not a detour from the blueprint.

RAG+CAG goes first because its issue numbering is lowest and because both paradigms it composes are individually furthest along (RAG has a working pipeline since Auth Foundation; CAG has three merged batches of real CPU-measurable technique work to build on).

## What OVERVIEW.md asks for, and the honesty boundary this batch draws

Three named mechanisms, all under the RAG↔CAG pairing:

- **Cache-Warmed RAG** — track which documents RAG retrieves most often, pre-load the most-retrieved into CAG's frozen cache, check cache first at query time, fall through to RAG on a miss, re-warm periodically.
- **Hot/cold tiering, CAG↔RAG boundary only** — promote cold (RAG-only) data whose access rate exceeds expectation up into CAG's hot tier; demote hot data whose access rate falls below expectation back down to RAG-only, freeing the resource the cache entry was occupying.
- **Sync Mixer, RAG-vs-CAG case** — when RAG's index has already picked up a changed fact and CAG's cache hasn't invalidated yet, RAG wins: the mixer detects the mismatch and evicts the stale cache entry, on some invalidation cycle, rather than serving the stale one indefinitely.

All three assume a real "CAG frozen cache" to warm, tier into, and invalidate. This project has no production vLLm-resident prefix cache (that specific claim — real eviction-under-memory-pressure behavior a genuine serving engine has to demonstrate — is deliberately deferred to the GPU-dependent Prefix Caching story per `docs/testing/TESTING.md`). What this batch measures instead is narrower and honestly in reach: **does actually reusing a precomputed KV cache for a document's content skip real prefill computation** — the literal mechanism `CLAUDE.md`'s paradigm table calls "near-zero TTFT on a hit" — **compared to recomputing that prefix from scratch, on a real small model run on CPU.** That's the same real-`transformers`-`past_key_values` methodology CAG Batch B's integration test already proved out (real `distilgpt2`, real `DynamicCache`, no mocks), applied here to a document-level cache instead of a token-level compression buffer. It is a genuine, honestly-measured cache-hit latency advantage at small scale — not a claim about GPU VRAM capacity, concurrent-request eviction pressure, or production-scale timing, which stay explicitly out of scope and are named as such below.

## Approach

New module, hexagonal like `rag/`, `cag/`, and `mag/`: `src/orchestration/`.

### Domain (`src/orchestration/domain/`), framework-free

`entities.py`:
- `CacheHit(content_hash: str, kv_cache: object)` — `kv_cache` is an opaque handle; only the infrastructure layer that produced it knows its real shape (a `DynamicCache` in this batch's one implementation). The domain layer never inspects it, only passes it through — the same "opaque payload, typed at the infrastructure boundary" shape CAG Batch B's `CompressedKV.payload` established.
- `SyncConflict(document_id: uuid.UUID, cached_content_hash: str, authoritative_content_hash: str)` — a real, detected disagreement between what CAG's cache holds and what RAG's index currently says, and the fact that it was resolved (by eviction — see Sync Mixer below).
- `TierDecision(str, Enum)`: `PROMOTED`, `DEMOTED`, `UNCHANGED` — what one tiering evaluation actually did.

`ports.py`:
- `AccessFrequencyTracker(ABC)`: `record_access(document_id: uuid.UUID, at: datetime) -> None`; `access_count(document_id: uuid.UUID, window: timedelta, now: datetime) -> int`; `most_accessed(n: int, window: timedelta, now: datetime) -> list[uuid.UUID]`. One shared tracking primitive behind both Cache-Warmed RAG (top-N snapshot) and tiering (threshold-based promote/demote) — OVERVIEW.md's own text makes these the same underlying signal ("an analytics process tracks which documents RAG retrieves most often" for Cache-Warmed RAG; "access-pattern tracking for RAG-retrieved data" for tiering), so this batch implements the tracking once and lets two different policies consume it, rather than duplicating access-counting logic per mechanism. `now` and `at` are explicit parameters rather than wall-clock reads inside the tracker, so tests can exercise real promotion/demotion decisions over a controlled time window without sleeping through it — the counting and threshold logic under test is real either way; only the clock is injected, the same testing discipline this project already applies to fakes for ports (real logic, controlled inputs).
- `FrozenCache(ABC)`: `preload(document_id: uuid.UUID, content: str) -> None`; `lookup(document_id: uuid.UUID) -> CacheHit | None`; `evict(document_id: uuid.UUID) -> None`; `contains(document_id: uuid.UUID) -> bool`.

`sync_mixer.py` (a plain module-level function, no I/O — matches `ngram_search.py`'s precedent of a framework-free domain algorithm that application-layer callers reuse rather than a stateful class):
- `reconcile(cached_hit: CacheHit | None, authoritative_content: str, document_id: uuid.UUID) -> SyncConflict | None` — hashes `authoritative_content`, compares against `cached_hit.content_hash`; returns `None` if nothing is cached or the hashes already match (nothing to reconcile), a `SyncConflict` if they differ. Pure comparison logic; the caller (an application-layer use case, since it owns the `FrozenCache` port) is responsible for actually evicting on a real conflict — keeping the domain layer free of the side effect matches this project's established application/domain split.

### Application (`src/orchestration/application/`)

- `warm_cache.py` — `WarmCache`: `execute(n: int, window: timedelta, now: datetime, content_provider: Callable[[uuid.UUID], str]) -> list[uuid.UUID]`. Asks the tracker for the top-N most-accessed documents in the window, preloads whichever aren't already cached, returns what it warmed. This is the periodic re-warming step Cache-Warmed RAG's Definition of Done calls for; called on a cadence by whatever schedules it (a test calls it directly on a controlled clock — no Celery/worker scaffolding in this batch, see "What this batch does not do").
- `cache_warmed_retrieve.py` — `CacheWarmedRetrieve`, implementing this project's own `Retriever` port (`src/rag/domain/ports.py`) so it's a drop-in for anywhere a plain RAG retriever is used today: `execute(tenant_id, query, top_k) -> list[SearchResult]`. Holds its own small in-memory embedding index — a plain `dict[uuid.UUID, list[float]]` — that starts empty and is populated by an explicit `note_warmed(document_id: uuid.UUID, content: str) -> None` method, which the caller invokes once per document immediately after `WarmCache.execute(...)` warms it (the caller already has `content_provider` and `WarmCache`'s return value, so this needs no new coupling between the two use cases). On `execute`: embeds the query, checks it against whatever's currently in that small index (cheap, since the candidate set is small by construction); above a similarity threshold, that's a *candidate* hit — look the matched document up in `FrozenCache` as the source of truth. If `FrozenCache.lookup` still returns a `CacheHit`, record a real hit and return a result built from the cached content with no vector-store round-trip. If `FrozenCache.lookup` returns `None` (the document was demoted/evicted by `TieringPolicy` or `SyncCycle` since it was indexed), that counts as a miss — the small index is a fast pre-filter, never trusted on its own, so it needs no eager invalidation when a document leaves the cache. Any case that isn't a confirmed `FrozenCache` hit falls through to the real `SearchDocuments.execute(...)`, recording a miss. Records hit/miss counts (exposed via a small `stats() -> tuple[int, int]` method, `(hits, misses)`) so the umbrella validation (#10/#27) can report a real hit rate against this project's own document/query corpus, honestly answering OVERVIEW.md's own caveat that the 80/20 split "is not a number this project has measured against its own corpus."
- `tiering_policy.py` — `TieringPolicy`: `evaluate(document_id, content_provider: Callable[[uuid.UUID], str], promote_threshold: int, demote_threshold: int, window: timedelta, now: datetime) -> TierDecision`. Requires `promote_threshold >= demote_threshold` (a hysteresis band, not a single crossing point — a document with an access count strictly between the two thresholds stays `UNCHANGED` regardless of its current cache state, so a count hovering right at one number can't flap the document in and out of the cache every evaluation). Reads `access_count` from the tracker; if it meets `promote_threshold` and the document isn't already cached, preloads it (`PROMOTED`); if it's cached and access count has fallen below `demote_threshold`, evicts it (`DEMOTED`, freeing whatever the cache entry was occupying — disclosed below as a real eviction of this batch's real cache resource, not a simulated VRAM figure); otherwise `UNCHANGED`. Reuses the same `AccessFrequencyTracker`/`FrozenCache` ports `WarmCache` uses — the promotion half of tiering and Cache-Warmed RAG's warming step are, honestly, the same mechanism (preload driven by access frequency) with two different trigger policies (threshold-crossing vs. top-N snapshot), and this batch's design says so rather than pretending they're unrelated.
- `sync_cycle.py` — `SyncCycle`: `run(document_ids: list[uuid.UUID], authoritative_content: Callable[[uuid.UUID], str]) -> list[SyncConflict]`. The batch invalidation trigger Sync Mixer's Definition of Done calls for: for each currently-cached document, look it up, call `sync_mixer.reconcile(...)`, and if a conflict comes back, evict it from `FrozenCache` (RAG wins) and collect it. A test drives this on a real, short interval (see Testing plan) to produce a real, honestly-measured detection-to-eviction latency, compared against OVERVIEW.md's own "illustrative, not an SLA" five-minute figure — not assumed to hit it, not tuned to hit it.

### Infrastructure (`src/orchestration/infrastructure/`)

- `in_memory_access_tracker.py` — `InMemoryAccessFrequencyTracker(AccessFrequencyTracker)`: a real, correct sliding-window counter (a dict of document_id → list of access timestamps, pruned to `window` on each read) — no fakery here; this is the actual tracking algorithm, not a test double, exercised for real by every mechanism in this batch. `tests/unit/cag_fakes.py`-style fakes are for ports OTHER code depends on and this batch doesn't own; this is this batch's own real implementation of its own port, same as `InMemoryAccessFrequencyTracker`'s counterparts in RAG/CAG/MAG (e.g. `qdrant_vector_store.py` is real, not a fake, despite being infrastructure).
- `hf_frozen_cache.py` — `HFFrozenCache(FrozenCache)`: wraps one real `transformers` `AutoModelForCausalLM` + tokenizer (CPU, `distilgpt2` — the same model this project's CAG integration tests already use). `preload`: tokenizes `content`, runs one real forward pass with `use_cache=True`, stores the resulting `DynamicCache` plus a content hash keyed by `document_id`. `lookup`: returns a `CacheHit` wrapping the stored `DynamicCache` and hash, or `None`. `evict`/`contains`: dict operations against the same store. A companion method, `prefill_latency_ms(document_id: uuid.UUID, content: str) -> tuple[float, float]`, returns `(cold_ms, warm_ms)` — real wall-clock time to run the same forward pass from scratch versus reusing whatever `DynamicCache` is already stored for that `document_id` (via `isolated_cache = copy.deepcopy(cached.kv_cache)` before reuse, matching the existing integration test's own precedent for not letting cache mutation contaminate a second call) — this is the batch's one real, measured "near-zero TTFT on a hit" number.

### Wiring into RAG

`CacheWarmedRetrieve` implements the existing `Retriever` ABC, so it slots into `src/rag/application/answer_question.py` (or whichever call site is under test) exactly where `SearchDocuments` does today, with zero changes to `Retriever`'s own contract. No change to `src/rag/domain/` or `src/rag/infrastructure/` is needed — this batch is additive from RAG's side.

## Testing plan

Unit tests, fast and deterministic:
- `InMemoryAccessFrequencyTracker`: recording, windowed counting (accesses outside the window don't count), `most_accessed` ordering and ties, an empty-tracker floor.
- `sync_mixer.reconcile`: no cached entry → `None`; matching hash → `None`; mismatched hash → a `SyncConflict` with both hashes recorded correctly.
- `TieringPolicy`: promotion when the threshold is crossed and the doc isn't yet cached; no double-promotion once cached; demotion when access falls below threshold on an already-cached doc; `UNCHANGED` in between; an explicit test that promotion and demotion thresholds don't fight each other on the same evaluation (hysteresis — a document exactly between the two thresholds stays `UNCHANGED`, not flapping).
- `WarmCache`: warms exactly the top-N, skips docs already cached, real interaction with a fake `FrozenCache` (a fake here is appropriate — this test is about `WarmCache`'s own orchestration logic, not `FrozenCache`'s real behavior, which `HFFrozenCache`'s own unit tests below cover).
- `CacheWarmedRetrieve`: hit path (after `note_warmed`) returns cached content with no fallback-retriever call; miss path (nothing indexed yet, or similarity below threshold) calls the fallback retriever and records the miss; the demoted-since-indexed case — `note_warmed` was called, the small index matches, but the fake `FrozenCache.lookup` now returns `None` — falls through to the fallback retriever rather than raising or returning stale content; `stats()` accounting is correct across a mixed sequence — all against fakes for `FrozenCache`/`Retriever`/`EmbeddingModel`, matching this project's own established fakes-for-ports convention.
- `HFFrozenCache` (real `distilgpt2`, CPU, no network beyond the one-time model download already cached from CAG Batches B/C): `preload` then `lookup` returns a hit with the correct content hash; `evict` then `lookup` returns `None`; two different documents don't collide; `prefill_latency_ms` returns `cold_ms >= warm_ms` on repeated calls for the same document (the direction the mechanism exists to produce) — this is a unit test, not the integration test, because it needs no cross-module wiring, only the one real model this project already downloads for CAG's own tests.

One integration test, real RAG + real CAG-style cache, no vLLM/GPU:
- Build a small real document corpus (reusing this project's existing RAG integration-test fixture pattern — real Qdrant via testcontainers, real embeddings), simulate skewed query traffic favoring 2-3 of the documents (matching OVERVIEW.md's own "return policy, shipping, account setup" shape), run `WarmCache` to warm the real top-N into a real `HFFrozenCache`, then run traffic through `CacheWarmedRetrieve` and report the real, measured hit rate for this project's own corpus and query mix (the honest answer to Cache-Warmed RAG's Definition of Done: "does this corpus actually show an 80/20-like skew").
- Update one of the warmed documents' content in RAG's store (a real change, the same "$100 to $80" shape as OVERVIEW.md's example), run `SyncCycle` on a real short interval, and report the real, measured wall-clock detection-to-eviction latency against the illustrative five-minute figure.
- Report `HFFrozenCache.prefill_latency_ms`'s real cold-vs-warm numbers for at least one of the warmed documents, as the batch's one real "near-zero TTFT on a hit" measurement.
- This is the Combined Capability Validation Story's (#10/#27) actual content: a real baseline (plain `SearchDocuments`, no warming) vs. combined (`CacheWarmedRetrieve` + `TieringPolicy` + `SyncCycle` together) comparison, run once the three mechanism Stories are in and reported with real numbers rather than OVERVIEW.md's stated expectations restated as fact.

"Real result documented" for each of the four Stories means the actual measured number from this integration test, pasted into that Story's closing comment, same disclosure standard as every prior batch — including if the measured cache-hit skew, invalidation latency, or TTFT delta falls short of OVERVIEW.md's stated figures.

## What this batch does not do

- **Does not build a production, GPU-resident, multi-tenant KV cache with real eviction-under-memory-pressure behavior.** That specific claim is deliberately deferred to the GPU-dependent Prefix Caching CAG story per `docs/testing/TESTING.md`'s own commitment. `HFFrozenCache` measures a real cache-hit prefill-latency advantage on CPU at a scale this project can actually run — a genuine instance of the same mechanism, not a stand-in for the production one.
- **Does not build `src/workers/cache_warmup_worker.py` or `src/workers/sync_worker.py` or any Celery/RabbitMQ scaffolding.** `WarmCache` and `SyncCycle` are real, directly callable use cases; a test (or a future batch, if a real scheduler becomes part of scope) drives them on a controlled or short-real interval. Standing up Celery is a separate, later concern OVERVIEW.md's own Phase 1 blueprint already tracks under `src/workers/`, not something this batch's four Stories ask for.
- **Does not build `src/orchestration/router.py`, `budget_allocator.py`, or `latency_cascade.py`.** Those are the Paradigm Router, Context Budget Allocator, and Latency-Adaptive Fallback Cascade — real orchestration-meta-layer components, but not ones any of this batch's four Stories name. This batch adds `src/orchestration/`'s Sync Mixer piece plus the two RAG↔CAG synthesis techniques; the rest of the meta-layer stays exactly as unbuilt as OVERVIEW.md currently records it.
- **Does not touch MAG.** RAG+MAG and CAG+MAG are separate batches (separate GitHub milestones, separate `paradigm:` labels) queued after this one.
- **Does not require GPU or vLLM anywhere.** Every real measurement in this batch runs on CPU: Qdrant via testcontainers (already this project's own established RAG integration-test pattern) and `distilgpt2` via `transformers` on CPU (already CAG Batches B and C's own established pattern).
