# Kanban Automation Across the Six Project Boards

`github-project-management-orchestrator`'s workflow model calls for a six-stage board — Backlog → Ready for Dev → In Progress → Code Review → QA/Testing → Done — with status transitions driven by GitHub itself rather than hand-moved cards, on the reasoning that a manually maintained board decays within a sprint while an automated one stays truthful at zero ongoing cost. This document records what that model actually required on the six boards this project runs (`rag-management` #5, `cag-management` #6, `mag-management` #7, `rag-mag-management` #8, `rag-cag-management` #9, `cag-mag-management` #10), what turned out to be reachable through the GitHub API, and what the API's own schema rules out — verified by querying it directly rather than assumed from familiarity with the product.

## What the API confirms it can and cannot do

Before touching any board, the GraphQL schema was queried directly for two things this task needed: whether a single-select field's existing options can be edited in place, and whether a Projects v2 built-in workflow's trigger-to-action mapping can be created or changed programmatically. `updateProjectV2Field`'s `singleSelectOptions` input accepts an optional `id` per option — passing an existing option's id along with a new `name` renames that option without disturbing anything that already points to it; omitting `id` creates a new option. That much is fully scriptable. The `ProjectV2Workflow` type, by contrast, exposes only `id`, `name`, `number`, `enabled`, and two timestamps — no field carries a workflow's trigger condition or its target status, and the mutation list contains `deleteProjectV2Workflow` but no `createProjectV2Workflow` or `updateProjectV2Workflow`. A workflow can be read by name and toggled on or off through the API; what it actually *does* when it fires is configurable only through each board's Workflows settings panel in the web UI. This is a real gap in GitHub's public API as of this writing, not an oversight in this project's scripting — confirmed by introspecting the live schema (`gh api graphql` against `__schema.mutationType.fields` and `__type(name: "ProjectV2Workflow")`), not inferred from documentation or memory.

## What was done through the API

Each of the six boards ships, by default, with the same three-option Status field (`Todo`, `In Progress`, `Done`) and the same six built-in workflows enabled: Auto-add sub-issues to project, Auto-close issue, Item added to project, Item closed, Pull request linked to issue, and Pull request merged. Querying `rag-management` before any change confirmed all 39 of its items already carried `Status = Todo` — set by the "Item added to project" workflow at creation time, not left blank as earlier planning here had assumed.

Given that, the option carrying the id GitHub had already wired every existing item to was renamed in place rather than replaced: `Todo`'s option id became `Backlog`, `In Progress` kept its id and name, and `Done` kept its id and name, while three new options — `Ready for Dev`, `Code Review`, and `QA/Testing` — were inserted between them via `updateProjectV2Field`. Because the rename preserves the option's id rather than issuing a new one, every item already pointing at the old `Todo` option resolved to `Backlog` automatically the moment the mutation returned — confirmed on `rag-management` before repeating the same mutation, with the same three preserved ids, on the other five boards. A post-change count across all six boards showed 143 items total, all reading `Backlog`, matching the 143-issue count from this project's original board population: 39 on `rag-management`, 43 on `cag-management`, 39 on `mag-management`, 8 on `rag-mag-management`, 8 on `rag-cag-management`, and 6 on `cag-mag-management`. No item required an individual status edit.

Because the rename preserved option ids rather than replacing them, the two default workflows whose target status matters most kept working without any reconfiguration: "Item added to project" still points at the option that is now named `Backlog`, and both "Item closed" and "Pull request merged" still point at the option now named `Done`. A new issue filed on any of the six boards today lands in `Backlog`; closing an issue or merging its linked PR moves it to `Done`, exactly as the six-stage model intends for those two transitions.

## What still needs a human, and the exact steps

The three finer-grained transitions the six-stage model calls for — a linked PR being opened moving its issue to `In Progress`, a review request moving it to `Code Review`, and a PR merge landing on `QA/Testing` rather than jumping straight to `Done` — are not achievable through today's API and were not applied. GitHub's default "Pull request linked to issue" workflow already exists and is enabled on all six boards, but its target status was not read back through the API (the schema does not expose it), so whether it currently points at `In Progress` or somewhere else is unverified and worth checking rather than assuming. The remaining two transitions (review-requested → `Code Review`, merged → `QA/Testing`) have no default workflow to repurpose at all; each needs its target status picked explicitly in the UI.

The concrete fix is the same six-step pass repeated once per board — Settings (the "..." menu on the project) → Workflows:

1. Open "Item added to project" and confirm its target is `Backlog`. This should already be correct from the id-preserving rename above; the check is to catch the case where it wasn't.
2. Open "Item closed" and confirm its target is `Done`, for the same reason.
3. Open "Pull request merged" and confirm its target is `Done` (both defaults agree with the two-stage model for now) or repoint it at `QA/Testing` if this project wants merge and done kept visibly distinct rather than collapsed together.
4. Open "Pull request linked to issue" (or "Pull request opened," depending on which trigger name the UI offers on the account this runs under) and set its target to `In Progress`.
5. If the Workflows panel offers a "Pull request review requested" trigger, enable it and set its target to `Code Review`. If it does not — GitHub has changed the available trigger list before, and this project has not verified the current list beyond the six confirmed enabled above — the closest available substitute is worth noting back into this file once checked, rather than left silently unautomated.
6. Repeat all five checks above on the other five boards; nothing here is shared state between boards, so a change made on `rag-management` has no effect on `cag-management`.

Until that pass runs, the practical state of the six boards is: creation, closing, and merging are fully automated to the correct stage; the two mid-pipeline transitions (`In Progress` on PR-open, `Code Review` on review-request) require a card to be dragged by hand, which is a real gap against the "automate status, never hand-move cards" rule this model is built on, named here rather than left implicit.
