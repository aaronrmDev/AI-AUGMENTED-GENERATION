# Cross-Paradigm Batch F: CAG+MAG Synthesis — Design Spec

**Scope:** #14 (story, umbrella validation), #1 (story, hot/warm tiering boundary), #5 (story, Sync Mixer tiebreak — investigate-first), #23/#28/#30 (their three tasks). See `docs/superpowers/specs/2026-09-02-cross-paradigm-rag-cag-design.md` and `docs/superpowers/specs/2026-09-02-cross-paradigm-rag-mag-design.md` for the two sibling batches this one completes the set with, and `docs/architecture/OVERVIEW.md`'s "Tiered Knowledge Hot-Cold Architecture" for the source material — CAG+MAG has no dedicated named technique the way State-Aware RAG or Cache-Warmed RAG do; both Stories here are this project's own inference from the general architecture, exactly as #1 and #5 themselves say.

## Why this is the last cross-paradigm batch

RAG+CAG (Batch D) and RAG+MAG (Batch E) are both merged. This batch completes the cross-paradigm backlog: CAG↔MAG is the one boundary neither prior batch touched (#1's own framing note: "OVERVIEW.md does not name a dedicated CAG+MAG technique the way it names State-Aware RAG or Cache-Warmed RAG... This Story is this project's own inference from the general tiering architecture's two-tier boundary"). No GPU is needed here either — this batch composes CAG's already-real `FrozenCache`/`HFFrozenCache` (Batch D) with MAG's already-real Postgres-backed semantic memory (seven merged MAG batches, reused again from Batch E).

## What this batch reuses, and the one new design decision it makes

Three things are reused directly, extending the same pattern Batch E already established for Batch D's own primitives:

- **`FrozenCache`/`HFFrozenCache` (Batch D, unmodified)** — CAG's real hot tier. Promoting MAG content into it means literally calling `HFFrozenCache.preload` with that content's text, the same mechanism Batch D's Cache-Warmed RAG already uses for RAG documents.
- **`UserScopedAccessFrequencyTracker`/`InMemoryUserScopedAccessFrequencyTracker` (Batch E, unmodified)** — tracking how often a specific user accesses a piece of MAG content is exactly the personal-access-frequency question Batch E's tracker already answers; CAG's own tenant-only `AccessFrequencyTracker` would be the wrong port here for the same reason Batch E gave for not reusing it: the content being promoted is inherently personal.
- **`sync_mixer.reconcile` (Batch D, generalized by Batch E, unmodified again)** — reused a third time. Its signature (`cached_content_hash: str | None, authoritative_content: str, document_id`) never assumed which paradigm supplies "authoritative" — Batch D used it for RAG-vs-CAG, Batch E for RAG-vs-MAG, and this batch uses it for CAG-vs-MAG with **MAG playing the authoritative role instead of RAG** (see the Sync Mixer section below for why that's the correct, reasoned choice here, not an arbitrary swap).

One new decision, made once and applied consistently rather than discovered mid-implementation: **`FrozenCache` is tenant-only, but the content this batch promotes into it is personal (a MAG semantic fact), so reusing it unchanged would create the exact same cross-user leak Batch E's whole `WarmStore` design exists to avoid** — a different user's identical query could read another user's promoted personal content out of the shared, tenant-only cache. Rather than introduce a fourth parallel port (a `UserScopedFrozenCache` nearly identical to `FrozenCache`, extending the run of near-duplicate ports this project has now built three times), this batch resolves it with **key namespacing**, applied differently on each side because the two reused ports don't have the same shape:

- **Against `FrozenCache`** (no `user_id` parameter at all): the key itself carries the user, `cache_key = uuid.uuid5(uuid.NAMESPACE_OID, f"{user_id}:{mag_content_key}")`. Two different users promoting "the same" conceptual MAG content get two different, non-colliding cache keys, so `FrozenCache`'s own tenant-only contract is never violated.
- **Against `UserScopedAccessFrequencyTracker`** (already takes a real `user_id` parameter of its own): no compound key is needed or correct — folding `user_id` into the key here too would double-scope it redundantly and, worse, make `tracker_key` and `cache_key` different UUIDs for the same conceptual content, which would just be confusing. The tracker gets a content-only key, `tracker_key = uuid.uuid5(uuid.NAMESPACE_OID, mag_content_key)`, passed alongside the tracker's own real `user_id` argument exactly as Batch E's port already expects.

Two different derived UUIDs, not one, each matching the actual shape of the port it's used against — a real design detail worth stating explicitly here rather than leaving it to be discovered (or gotten wrong) during implementation. User isolation is enforced by which key gets used and which port parameter carries `user_id`, not by adding a parameter to `FrozenCache` itself. This is why `CagMagTieringPolicy` below is sync (no new async port, no I/O CAG's side doesn't already have) despite promoting inherently personal content.

## What OVERVIEW.md asks for (via #1 and #5's own inference from it)

- **Hot/warm tiering boundary, CAG↔MAG only** — promote MAG warm data (a user preference, a scratchpad entry) whose access rate exceeds the warm-tier expectation up into CAG's hot tier; demote CAG hot data whose access rate falls below the hot-tier expectation back down into MAG's warm tier, freeing the GPU VRAM (in this batch's real CPU proxy: the real `HFFrozenCache` entry) it was occupying.
- **Sync Mixer, CAG-vs-MAG case** — #5's own scope is explicitly investigate-first: "it's possible the architecture's own data-placement rules prevent this scenario from ever occurring... if such a conflict can arise, define a resolution rule for it (with explicit reasoning, since the source provides none for this case)."

### The investigation #5 asks for

A genuine CAG-vs-MAG-only conflict — CAG's frozen cache and MAG's session state disagreeing directly, with no RAG update anywhere in the picture — **can** arise, and this batch's own hot/warm tiering mechanism (#1) is exactly what creates the opportunity: `CagMagTieringPolicy.evaluate` promotes a MAG semantic fact's content into `FrozenCache` as a frozen, point-in-time copy. MAG's own live data can keep changing after that — `UpdateMemory`, `RefineMemory`, `InvalidateMemory`, and `ArchiveMemory` (all existing, unmodified MAG commands from earlier batches) all mutate a fact's live state — while the CAG-side copy stays exactly what it was at promotion time. That's a real, reachable divergence, not a hypothetical: it needs no RAG involvement at all, and it needs no external actor — MAG's own normal write path is sufficient to cause it.

**Resolution rule, with its own reasoning since the source gives none: MAG wins.** RAG wins in the other two pairings because RAG is the external, ground-truth source neither CAG nor MAG can update directly. In THIS pairing, CAG's hot-tier entry isn't an independent paradigm holding its own competing fact — it's a cached acceleration of a specific MAG record, promoted BY this batch's own tiering mechanism FROM MAG. MAG is the one paradigm in this conflict that actually owns the data; CAG's copy is derived, not authoritative, by construction. So the natural resolution is the mirror image of RAG-vs-CAG's rule, with the roles reversed to match which paradigm is genuinely upstream here: MAG's current live content wins, and the stale CAG hot-tier entry gets evicted.

## Approach

### Domain (`src/orchestration/domain/`) — one small addition, no new ports

`cag_mag_keys.py`, a plain module of pure functions (no I/O, no state), matching `sync_mixer.py`'s own precedent for where this project puts small, genuinely domain-level logic that isn't tied to any one port: `cache_key(user_id: uuid.UUID, mag_content_key: str) -> uuid.UUID` (`uuid.uuid5(uuid.NAMESPACE_OID, f"{user_id}:{mag_content_key}")`, used against `FrozenCache`) and `tracker_key(mag_content_key: str) -> uuid.UUID` (`uuid.uuid5(uuid.NAMESPACE_OID, mag_content_key)`, used against `UserScopedAccessFrequencyTracker`, which already takes a real `user_id` argument of its own and so needs no compound key). Defined once and imported by both application classes below, rather than duplicated per-file.

### Application (`src/orchestration/application/`) — no new domain ports needed

- `cag_mag_tiering_policy.py` — `CagMagTieringPolicy`: the same promote/threshold/demote/hysteresis shape as `TieringPolicy`/`MagTieringPolicy`, built on `UserScopedAccessFrequencyTracker` (Batch E) and `FrozenCache` (Batch D) directly — no new port. `evaluate(tenant_id: uuid.UUID, user_id: uuid.UUID, mag_content_key: str, content_provider: Callable[[str], str], promote_threshold: int, demote_threshold: int, window: timedelta, now: datetime) -> TierDecision`. Reads the access count via `tracker.access_count(tenant_id, user_id, cag_mag_keys.tracker_key(mag_content_key), window, now)`; promotes/demotes/checks containment against `FrozenCache` via `cag_mag_keys.cache_key(user_id, mag_content_key)`. Sync, not async, unlike `MagTieringPolicy` — `UserScopedAccessFrequencyTracker` and `FrozenCache` are both pure in-memory/local-CPU with no I/O; the content this batch promotes originates from MAG, but by the time `content_provider` hands it to this class it's just a string, and nothing this class itself does touches Postgres or Qdrant directly (a real caller wiring this up is responsible for fetching that string from MAG first, the same "caller owns the fetch" shape `WarmCache`'s own `content_provider` callable already established in Batch D).
- `cag_mag_sync_cycle.py` — `CagMagSyncCycle`: the CAG-vs-MAG batch invalidation trigger, built on `FrozenCache` and the same `sync_mixer.reconcile` Batch D and Batch E already share. `run(tenant_id: uuid.UUID, user_id: uuid.UUID, mag_content_keys: list[str], authoritative_content: Callable[[str], str]) -> list[SyncConflict]`. For each key, looks up `FrozenCache` via `cag_mag_keys.cache_key(user_id, mag_content_key)`, reconciles against `authoritative_content(mag_content_key)` (the caller's real, current MAG read — "MAG wins" per the investigation above), and evicts on a real conflict. Sync, matching `CagMagTieringPolicy` and `FrozenCache` above, unlike `MagSyncCycle` (which is async because `WarmStore` does real I/O) — this class's own I/O-free shape is a direct consequence of promoting content INTO CAG's already-sync cache rather than reading FROM MAG's own store.

## Testing plan

Unit tests, fast and deterministic, fakes for `FrozenCache`/`UserScopedAccessFrequencyTracker` (both already have established fakes from Batch D/E):
- `CagMagTieringPolicy`: promotion/demotion/hysteresis (same shape as `TieringPolicy`/`MagTieringPolicy`'s own tests), plus a dedicated test proving two different users promoting content under the SAME `mag_content_key` never collide in `FrozenCache` (the namespacing this batch's whole design depends on) — verified by checking both promoted entries are independently readable and independently demotable.
- `CagMagSyncCycle`: conflict detection and eviction against a fake `FrozenCache`, including a per-user isolation test (parallel to `MagSyncCycle`'s own).

One real integration test, no vLLM/GPU, reusing this project's already-established real infrastructure (real Postgres via testcontainers, real `distilgpt2` on CPU):
- **Hot/warm tiering:** record a real MAG semantic fact (`RecordSemanticFact`, existing/unmodified), drive real access data through `CagMagTieringPolicy` to promote it into a real `HFFrozenCache`, confirm the promoted content is genuinely readable back out (a real KV cache, not a stub), then confirm demotion once traffic dries up. Also report `HFFrozenCache.prefill_latency_ms`'s real cold-vs-warm numbers for the promoted MAG content specifically — the same "near-zero TTFT on a hit" mechanism Batch D measured for RAG documents, now measured for MAG-sourced content, honestly disclosing whether the same real advantage holds (it should, since the underlying mechanism is identical — but this batch measures it directly rather than assuming it transfers).
- **Sync Mixer investigation, made concrete:** promote a real MAG fact into the real hot tier, then call the real `UpdateMemory` command (existing, unmodified) to change that same fact's live value in MAG, then run `CagMagSyncCycle` on a real short interval and report the real, measured detection-to-eviction latency — the same disclosure shape Batch D and Batch E's own Sync Mixer reports already use, extended to prove the investigation's own claim (a real conflict really does arise from this batch's own promotion mechanism, and the MAG-wins rule really does resolve it) against real infrastructure, not just reasoned about in prose.
- **Combined Capability Validation (#14/#30):** baseline (CAG and MAG operating independently, no cross-tiering, no conflict handling) vs. combined (`CagMagTieringPolicy` + `CagMagSyncCycle` together) — the real delta is the tiering lifecycle actually working end-to-end against real infrastructure plus the sync mechanism actually catching and correcting the real divergence the investigation identified, reported honestly either way per this project's established disclosure standard.

"Real result documented" for each Story/task means the actual measured number from these tests, pasted into that issue's closing comment.

## What this batch does not do

- **Does not add a new domain port.** `CagMagTieringPolicy`/`CagMagSyncCycle` compose Batch D's `FrozenCache` and Batch E's `UserScopedAccessFrequencyTracker` directly, using key namespacing (not a new port) to keep per-user isolation on an otherwise tenant-only cache — disclosed at length above as this batch's one real design decision, not a shortcut.
- **Does not modify `FrozenCache`, `HFFrozenCache`, `UserScopedAccessFrequencyTracker`, `InMemoryUserScopedAccessFrequencyTracker`, or `sync_mixer.reconcile`.** Every one of them is reused completely unmodified — the third and final reuse of `sync_mixer.reconcile` across all three cross-paradigm batches.
- **Does not modify MAG's own domain layer, ports, or schema.** Every MAG read/write goes through existing, unmodified MAG application classes (`RecordSemanticFact`, `UpdateMemory`).
- **Does not require GPU or vLLM anywhere.**
