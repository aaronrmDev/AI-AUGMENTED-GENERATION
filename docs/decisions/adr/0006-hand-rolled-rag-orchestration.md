# ADR-0006: Hand-Rolled RAG Orchestration, Not LangChain/LangGraph

Status: Accepted

## Context

[ADR-0005](0005-langchain-langgraph-rag-orchestration.md) committed this project to LangChain for RAG pipeline assembly (chunking, embedding, hybrid search, reranking) and to LangGraph specifically for CRAG and Self-RAG's agentic control flow, reasoning that a mature framework would reduce glue code for the pipeline's linear stages and that LangGraph's graph-based execution model mapped directly onto CRAG and Self-RAG's loops and conditional branches.

That's not what got built. Across six RAG implementation batches — Chunking Strategies, Hybrid Search + Reranking, Parent Document + Context Compression, Multi-Query + HyDE + Self-RAG, CRAG, and RAG Combinations — every technique ADR-0005 named, including CRAG and Self-RAG, was implemented as a plain Python class under `src/rag/domain/`, `application/`, and `infrastructure/`, the same hexagonal layering every other module in this codebase (Identity, MAG, CAG, the cross-paradigm orchestration layer) already uses. Neither `langchain` nor `langgraph` appears in `pyproject.toml`, is imported anywhere under `src/`, or is mentioned in any of the seven RAG design specs (`docs/superpowers/specs/2026-08-2[2-6]-rag-*.md`) or in any of the 228 commits on this branch. This ADR exists because that gap between the recorded decision and the actual implementation needed to be closed one way or the other — either by actually adopting LangChain/LangGraph at this late stage, or by formally recording what was actually built as the real decision. Retrofitting LangChain and LangGraph onto six already-built, already-tested, already-measured batches would mean rewriting working code to fit a framework's abstractions for its own sake, not because any concrete problem with the hand-rolled version had surfaced — no such problem has. This ADR takes the second path.

It's worth being direct about one thing this Context section cannot honestly supply: a recorded reason the original decision wasn't followed. No design spec, no commit message, no prior architecture-doc revision states that ADR-0005 was reconsidered, or explains why implementation diverged from it. This ADR does not invent one. What follows is a decision made now, in the present, to ratify the architecture that already exists and is already working — not a reconstruction of reasoning that happened at the time.

## Decision

This project uses hand-rolled Python classes, under the same hexagonal domain/application/infrastructure layering as every other module in this codebase, for all RAG orchestration — both the linear pipeline stages (chunking, embedding, hybrid search, reranking, parent-document retrieval, context compression) and the non-linear control flow (CRAG's retrieve-evaluate-correct loop, Self-RAG's retrieval-gating decision). It does not use LangChain or LangGraph, or any other RAG orchestration framework, anywhere in `src/`.

Concretely: a chunking strategy, a reranker, or a retriever is a class implementing one of `src/rag/domain/ports.py`'s interfaces (`Chunker`, `Reranker`, `Retriever`, and similar), the same shape MAG's memory operations and CAG's compressors already take. CRAG's corrective loop (`src/rag/infrastructure/corrective_retriever.py`) is an ordinary method with an `if`-branch on whether retrieved documents pass relevance review, not a LangGraph `StateGraph`. Self-RAG's retrieval gate (`src/rag/application/self_rag_answer_question.py`) is a regex-parsed yes/no classification followed by a plain conditional, not a LangGraph node.

## Consequences

Every RAG technique is now the same testable shape as every other module in this repository — a domain port, an infrastructure implementation, a unit test against a fake, and (where a real dependency's actual behavior is what's under test) an integration test against real Postgres, Qdrant, or a real small HF model. There is no second architectural vocabulary a contributor has to learn on top of this project's own hexagonal convention, and no risk of a LangChain or LangGraph version bump changing behavior underneath code this project didn't write. The dependency surface stays smaller: `pyproject.toml` never took on either framework or their own transitive dependency trees.

The cost is real and specific, not just hypothetical. LangChain's pre-built document loaders, vector-store adapters, and chain-composition utilities are given up in favor of writing and maintaining each integration by hand — every one of the 24 files under `src/rag/infrastructure/` is bespoke code this project owns and tests itself, rather than a thin wrapper around a maintained library's version. More concretely, CRAG's real implementation is single-shot: one re-search attempt on a failed evaluation, then whatever comes back, rather than the multi-iteration correction loop the source concept material and ADR-0005's own reasoning about LangGraph's "graph-based execution model" both envisioned. A hand-rolled `if`-branch was simpler to build and ship than a genuine looping construct would have been, and that's a real capability this project's own CRAG (`docs/architecture/RAG.md`'s roadmap section, which separately recommends capping any such loop at two iterations) doesn't have. Any future RAG technique needing genuine multi-step, stateful agentic control flow — something closer to what LangGraph is actually built for — will face the same choice ADR-0005 originally settled and this ADR now unsettles: build it by hand again, in this project's own established style, or take on the framework dependency this decision has twice now declined.
