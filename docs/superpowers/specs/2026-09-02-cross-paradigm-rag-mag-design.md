# Cross-Paradigm Batch E: RAG+MAG Synthesis — Design Spec

**Scope:** #45 (story, umbrella validation), #6 (story, State-Aware RAG), #20 (story, warm/cold tiering boundary), #34 (story, Sync Mixer tiebreak), #59/#71/#83/#86 (their four tasks). See `docs/superpowers/specs/2026-09-02-cross-paradigm-rag-cag-design.md` for the sibling RAG+CAG batch this one deliberately parallels and reuses from, and `docs/architecture/OVERVIEW.md`'s "State-Aware RAG," "Tiered Knowledge Hot-Cold Architecture," and "The sync mixer's tiebreak rule: RAG wins" sections for the source material.

## Why this is the next batch, and what it reuses from RAG+CAG

RAG+CAG (Batch D) is merged: `src/orchestration/` now has real `AccessFrequencyTracker`/`FrozenCache` ports, `sync_mixer.reconcile`, and `WarmCache`/`TieringPolicy`/`SyncCycle`/`CacheWarmedRetrieve`. RAG+MAG needs no GPU either — it composes RAG's existing Qdrant/embedding/Ollama stack with MAG's already-real Redis/PostgreSQL/Neo4j stack (seven merged MAG batches), so it's the natural next cross-paradigm pairing in issue-number order.

This batch is NOT a drop-in reuse of Batch D's classes, though, for one real reason stated up front rather than discovered mid-implementation: **MAG's warm tier is inherently personal (every MAG table is keyed by `user_id`), while CAG's frozen cache is a tenant-wide shared resource with no user concept at all.** Reusing Batch D's `AccessFrequencyTracker`/`FrozenCache`/`TieringPolicy` unchanged for MAG's tiering would silently conflate different users' access patterns for the same document — user A's heavy traffic would promote a document into user B's personal memory too. That's a real correctness bug, not a style choice, so this batch defines its own user-scoped tracker and warm-store ports rather than forcing MAG through CAG's tenant-only shapes. Two things genuinely ARE shared, though, and this batch reuses them directly:

- **`sync_mixer.reconcile`** — RAG-wins conflict detection is paradigm-agnostic (it only needs a content hash to compare against, not a CAG-specific cache entry). This batch generalizes its signature from `cached_hit: CacheHit | None` to `cached_content_hash: str | None`, updating `SyncCycle` (Batch D, already merged) to pass `cached_hit.content_hash if cached_hit else None` instead of the whole `CacheHit`. This is a small, behavior-preserving refactor of already-merged code, done because the alternative (a near-duplicate `mag_sync_mixer.reconcile`) would violate this project's own established "same underlying mechanism, don't duplicate" principle for no real benefit — `SyncCycle`'s own unit tests (Batch D) are the regression guard that this refactor doesn't change RAG-vs-CAG's behavior.
- **The general shape** of "track access → threshold-driven promote/demote with a hysteresis band" from `TieringPolicy` — reused as a pattern, not as shared code, since the actual port shapes differ (see above).

## What OVERVIEW.md asks for

Three named mechanisms under the RAG↔MAG pairing:

- **State-Aware RAG** — read MAG's state (user preferences, conversation history, task context) before retrieval runs, rewrite the query to be personal instead of generic, boost ranking for results matching the user's known context, and write whatever comes back back into MAG so the next turn has it too.
- **Warm/cold tiering, RAG↔MAG boundary only** — promote cold (RAG-only) data whose *personal* access rate exceeds expectation up into MAG's warm tier; demote warm data whose access rate falls below expectation back down to RAG-only.
- **Sync Mixer, RAG-vs-MAG case** — when RAG's index has already picked up a changed fact and MAG's session state still remembers the old value, RAG wins: the mixer detects the mismatch and corrects MAG's stored state rather than leaving it stale.

## Approach

### Domain (`src/orchestration/domain/`), extending the module from Batch D

`entities.py` additions:
- `WarmEntry(content_hash: str, content: str)` — MAG's warm-tier analogue of `CacheHit`. Unlike `CacheHit.kv_cache` (an opaque tensor handle only infrastructure understands), `WarmEntry.content` is a real string: MAG's warm tier is a semantic fact, not a KV cache, so there's no opaque payload to hide — the domain layer can see and use the real text (needed for State-Aware RAG's ranking boost and query enrichment to actually read it).

`ports.py` additions:
- `UserScopedAccessFrequencyTracker(ABC)`: `record_access(tenant_id: uuid.UUID, user_id: uuid.UUID, document_id: uuid.UUID, at: datetime) -> None`; `access_count(tenant_id: uuid.UUID, user_id: uuid.UUID, document_id: uuid.UUID, window: timedelta, now: datetime) -> int`; `most_accessed(tenant_id: uuid.UUID, user_id: uuid.UUID, n: int, window: timedelta, now: datetime) -> list[uuid.UUID]`. Structurally close to Batch D's `AccessFrequencyTracker` but genuinely a different port, not a subtype or a reused implementation — the extra `user_id` dimension is load-bearing, not decorative.
- `WarmStore(ABC)`: `promote(tenant_id: uuid.UUID, user_id: uuid.UUID, document_id: uuid.UUID, content: str) -> None`; `lookup(tenant_id: uuid.UUID, user_id: uuid.UUID, document_id: uuid.UUID) -> WarmEntry | None`; `demote(tenant_id: uuid.UUID, user_id: uuid.UUID, document_id: uuid.UUID) -> None`; `contains(tenant_id: uuid.UUID, user_id: uuid.UUID, document_id: uuid.UUID) -> bool`. Same four-verb shape as `FrozenCache` (promote≈preload, demote≈evict) because the underlying idea — place content in a fast personal store, check it, remove it — really is the same idea Batch D already named; the port is separate because the physical realization (a Postgres+Qdrant semantic fact, not a GPU-resident KV cache) and the required scoping (`user_id`) both genuinely differ.

`sync_mixer.py` change (backward-compatible refactor of Batch D's merged code):
- `reconcile(cached_content_hash: str | None, authoritative_content: str, document_id: uuid.UUID) -> SyncConflict | None` — was `reconcile(cached_hit: CacheHit | None, ...)`. `SyncCycle.run` (Batch D) updates its one call site to `sync_mixer.reconcile(cached_hit.content_hash if cached_hit else None, ...)`; Batch D's own `test_sync_cycle.py` and `test_sync_mixer.py` are re-run unmodified as the regression check that RAG-vs-CAG behavior is unchanged by this generalization.

### Application (`src/orchestration/application/`)

- `state_aware_retrieve.py` — `StateAwareRetrieve`. **Does not implement RAG's `Retriever` ABC** — disclosed explicitly, not silently: `Retriever.execute(tenant_id, query, top_k)` has no `user_id`/`session_id` slot, and MAG's entire schema requires both, so forcing this into the existing port would mean either fabricating a user identity or breaking the ABC's contract for every other implementer (`SearchDocuments`, `HyDERetriever`, `CacheWarmedRetrieve`, ...). Its own signature: `execute(tenant_id: uuid.UUID, user_id: uuid.UUID, session_id: uuid.UUID, query: str, top_k: int) -> list[SearchResult]`. Steps, each real:
  1. Embed the raw query; call `FindSemanticFacts.by_similarity` (existing MAG query, unmodified) for the user's most relevant known facts, and `RetrieveWorkingMemory` (existing MAG query, unmodified) for the session's recent turns.
  2. Real query rewrite via `ChatModel.complete(prompt)` (RAG's existing port; `OllamaChatModel` against a real local model, matching MAG's own established real-Ollama-in-tests convention, e.g. `test_capture_episode_command.py`'s salience scoring) — given the facts and recent turns, ask the model to rewrite the raw query into one that reflects what's known about the user, the same transformation OVERVIEW.md's own worked example describes ("How do I visualize this?" → a matplotlib/pandas-specific query for a user MAG knows prefers those).
  3. Retrieve using the enriched query via a real fallback `Retriever` (`SearchDocuments`).
  4. Ranking boost: a real, cheap (no second LLM call) keyword-overlap rescoring of the fallback's results against the fetched facts' text — a result whose content shares more terms with the user's known preferences/stack ranks higher.
  5. Write-back: `CaptureEpisode` (existing MAG command, unmodified) records the query and what was retrieved as a new episode, so the interaction itself becomes part of the user's history for the next turn — MAG makes RAG personal, RAG gives MAG something external to be personal about, in OVERVIEW.md's own words.
- `mag_tiering_policy.py` — `MagTieringPolicy`: the same promote/threshold/demote/hysteresis shape as Batch D's `TieringPolicy`, built on `UserScopedAccessFrequencyTracker`/`WarmStore` instead of `AccessFrequencyTracker`/`FrozenCache`. `evaluate(tenant_id, user_id, document_id, content_provider, promote_threshold, demote_threshold, window, now) -> TierDecision` (`TierDecision` reused directly from Batch D — the three-way outcome is genuinely paradigm-agnostic, unlike the tracking/storage ports).
- `mag_sync_cycle.py` — `MagSyncCycle`: the RAG-vs-MAG batch invalidation trigger, built on `WarmStore` and the now-generalized `sync_mixer.reconcile`. `run(tenant_id, user_id, document_ids, authoritative_content) -> list[SyncConflict]`. On a real conflict, calls `WarmStore.demote(...)` — MAG's "state correction": the next lookup falls through to a fresh RAG retrieval rather than serving the stale value. `MagSyncCycle` itself only ever talks to the abstract `WarmStore` port, the same posture Batch D's `SyncCycle` holds toward `FrozenCache` — it has no MAG-specific knowledge of what "demote" does underneath; that responsibility belongs entirely to `SemanticMemoryWarmStore`'s own real implementation of `demote` (see Infrastructure below), which is also where MAG's OTHER read paths (`FindSemanticFacts`, direct queries) get to stop surfacing the stale value too, not just this batch's own `WarmStore.lookup`.

### Infrastructure (`src/orchestration/infrastructure/`)

- `in_memory_user_scoped_access_tracker.py` — `InMemoryUserScopedAccessFrequencyTracker(UserScopedAccessFrequencyTracker)`: the same real sliding-window-with-retention design as Batch D's `InMemoryAccessFrequencyTracker` (fixed `retention` horizon decoupled from any individual call's `window`, the same reasoning Batch D's own review established), keyed by `(tenant_id, user_id, document_id)` instead of `(tenant_id, document_id)`.
- `semantic_memory_warm_store.py` — `SemanticMemoryWarmStore(WarmStore)`: wraps real `SemanticMemoryRepository` + `SemanticMemoryIndex` (`PostgresSemanticMemoryRepository` + `QdrantSemanticMemoryIndex`, this project's own real MAG infrastructure) + `EmbeddingModel`. `promote`: derives a deterministic `fact_key` from `document_id` (`f"rag_promoted:{document_id}"`, matching `RecordSemanticFact`'s own deterministic-id-by-key precedent so re-promoting the same document overwrites rather than duplicates), saves a `SemanticMemory` fact via the repository and index. `lookup`: `find_by_key`, returns a `WarmEntry` with the fact's real `fact_value` and its content hash, or `None` if absent or invalidated (`valid_until`/`archived_at` set — reusing MAG's own existing "excluded from retrieval" semantics rather than inventing a second one). `demote`: calls `invalidate` (MAG's own existing mechanism for "stop surfacing this," matching `MagSyncCycle`'s own reasoning above) rather than a hard delete — demoted data isn't wrong, just no longer warm, and MAG's history-preserving conventions (Batch F) already treat invalidation as the right operation for that. `contains`: `lookup(...) is not None`.

## Testing plan

Unit tests, fast and deterministic, fakes for every port (matching Batch D's own established convention):
- `InMemoryUserScopedAccessFrequencyTracker`: the same coverage shape as Batch D's tracker (windowed counting, retention pruning decoupled from query window, ties), plus per-user isolation (the same `document_id` under two users in the same tenant counts independently — the specific bug this batch's whole design exists to avoid).
- `sync_mixer.reconcile`'s NEW signature: re-run its existing test file with `cached_content_hash: str | None` in place of a `CacheHit`, confirming behavior is unchanged; add one test asserting `SyncCycle` (Batch D) still passes its own existing test file unmodified after the refactor, as the regression guard.
- `MagTieringPolicy`: promotion/demotion/hysteresis (same shape as Batch D's `TieringPolicy` tests), plus per-user isolation.
- `MagSyncCycle`: conflict detection and demotion against a fake `WarmStore`, matching `SyncCycle`'s own test shape.
- `StateAwareRetrieve`: against fakes for `SemanticMemoryRepository`-via-`FindSemanticFacts`, `WorkingMemoryStore`-via-`RetrieveWorkingMemory`, `ChatModel`, and the fallback `Retriever` — the rewrite step is called with the real facts/turns it fetched; the ranking-boost step measurably reorders results toward fact-matching content on a constructed case where the naive fallback order would NOT already put it first; write-back calls `CaptureEpisode.execute` with the real query/result content.

Real integration tests, no vLLM/GPU, using this project's already-established real infrastructure (real Qdrant, real Postgres, real Neo4j via testcontainers; real `sentence-transformers` embeddings; real Ollama `qwen3.5`, matching `test_capture_episode_command.py`'s own convention):
- **State-Aware RAG**: seed a small real corpus of near-identical "how to visualize data" documents, each written for a DIFFERENT library (matplotlib, seaborn, plotly) — deliberately ambiguous to bare keyword/embedding retrieval alone, directly mirroring OVERVIEW.md's own worked example. Record a real semantic fact for one test user ("prefers matplotlib for visualization"). Ask the same generic query ("How do I visualize this data?") through both a bare `SearchDocuments` baseline and `StateAwareRetrieve`. Report the real, measured result: does state-aware enrichment retrieve/rank the matplotlib-specific document more reliably than the bare-query baseline — the honest answer to #6's Definition of Done ("does enrichment actually improve retrieval relevance over bare-query RAG?").
- **Warm/cold tiering**: real access data drives a real promote → demote lifecycle through `MagTieringPolicy` and a real `SemanticMemoryWarmStore`, confirming the promoted content is actually readable back out of real Postgres/Qdrant (not just present in an in-memory dict), and that a second user's identical access pattern for the same `document_id` doesn't cross-promote into the first user's memory.
- **Sync Mixer**: a real content change, `MagSyncCycle` polled on a short real interval, reporting real detection-to-correction latency against the same illustrative five-minute figure Batch D's report already contextualizes.
- **Combined Capability Validation** (#45/#86): baseline (RAG-only, no MAG enrichment) vs. combined (`StateAwareRetrieve` + `MagTieringPolicy` + `MagSyncCycle` together), real numbers, honestly reported either way — including if the enrichment or latency result doesn't clearly favor the combined system, the same disclosure standard Batch D's own report already set.

"Real result documented" for each of the four Stories means the actual measured number from these integration tests, pasted into that Story's closing comment.

## What this batch does not do

- **Does not modify RAG's `Retriever` ABC.** `StateAwareRetrieve` is deliberately its own use case rather than a forced, contract-breaking `Retriever` implementation — disclosed above, not hidden.
- **Does not modify MAG's own domain layer, ports, or schema.** Every MAG read/write in this batch goes through existing, unmodified MAG application classes (`FindSemanticFacts`, `RetrieveWorkingMemory`, `CaptureEpisode`) and existing, unmodified MAG infrastructure (`PostgresSemanticMemoryRepository`, `QdrantSemanticMemoryIndex`) — this batch is additive from MAG's side, the same posture Batch D held toward RAG.
- **Does not reuse Batch D's `AccessFrequencyTracker`/`FrozenCache`/`TieringPolicy` for MAG's tier.** Disclosed at length above: MAG's tier is inherently personal, and reusing tenant-only ports would be a real correctness bug, not a simplification.
- **Does not touch CAG.** RAG-CAG conflicts (the case Batch D's `SyncCycle` already handles) are out of scope here; this batch's `MagSyncCycle` handles the RAG-vs-MAG case only, per #34's own explicit scope note.
- **Does not require GPU or vLLM anywhere.** Every real measurement in this batch runs on already-established infrastructure: Qdrant/Postgres/Neo4j via testcontainers, `sentence-transformers` on CPU, and real Ollama (`qwen3.5`) — the same stack MAG's own seven merged batches already use for salience scoring, consolidation reflection, and fact evolution.
