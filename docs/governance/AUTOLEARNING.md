# Autolearning Contract

CLAUDE.md and the documents it points to describe this project's intended structure, its rules, and its architecture — the folder layout under `docs/`, the routing table that sends particular kinds of work to particular skills, the ADRs that record why one technology was chosen over its alternative, the way the RAG, CAG, and MAG layers are supposed to talk to each other. All of that is a description, not the thing itself, and a description only stays true for as long as nobody changes the thing it describes. Every commit that lands after these words are written is a chance for that description to fall a little further out of step with what the repository actually contains: a file gets renamed and a doc map entry keeps pointing at the old path, a routing rule gets superseded by a decision recorded only in a commit message, an architectural choice written down as settled gets revisited later and the write-up never catches up. Staleness, in this repository, means exactly that gap — the distance between what CLAUDE.md and its linked docs currently assert and what `git log` and the actual directory tree would show. That gap is easier to live with while the repository stays pre-code, because most of what's being described is intent rather than implementation, and intent drifting from intent is a smaller problem than intent drifting from a running system. It stops being easy once Phase 1 code work begins: at that point CLAUDE.md's claims about module layout, database schema, and API shape stop describing a plan and start describing something that exists and can diverge from the plan on its own, commit by commit, without anyone deciding that it should. This document specifies the contract for a skill named `claude-md-sync`, whose job — once it is built — is to catch that gap before it grows large enough that the governing document stops being trustworthy. What follows is meant to be precise enough that whoever builds it later has no ambiguity left to fill in on their own: the behavior described here is the behavior the skill needs to have, not a rough sketch for someone to improve on.

## When it runs

`claude-md-sync` is on-demand, not scheduled: it is invoked either by being called directly, or by the agent working in this repository judging, on its own, that a significant piece of work has just finished and the documentation is worth checking against it. "Significant" here does not mean every commit — a typo fix, a formatting pass, or a one-line clarification doesn't move the ground CLAUDE.md is standing on, so it doesn't warrant a check. What does: standing up a new module or package, changing an architectural decision (adopting a different library, reversing an ADR, altering how two layers talk to each other), or adding a new document that the doc map doesn't yet account for. The test an agent applies before invoking it, on its own judgment, is whether the work just completed changed something CLAUDE.md or a linked doc makes a claim about — if it did, that claim is now unverified until this check runs against it.

## What it checks

This contract does not include a separate mechanism for `claude-md-sync` to keep its own run log, so "since the last known sync point" is anchored to something already discoverable from git itself: the most recent commit that touched `CLAUDE.md` or anything under `docs/`, on the reasoning that the last time those files changed is the last time someone — a human, or an agent acting on an already-approved proposal — actually reconciled them with reality. Every commit after that point is unaccounted for by definition, and that stretch of git history is the skill's primary input, read alongside the current text of `CLAUDE.md` and the current shape of the `docs/` tree exactly as they stand at invocation time. Against that input, the check looks for concrete mismatches, not a general sense that things might have moved on: a rule stated in CLAUDE.md or a governance doc that recent commits no longer follow in practice, a doc map entry that names a file which has since been renamed, moved, or deleted, or an architecture description that no longer matches what the corresponding code or document actually does now. Each of those is a specific, checkable claim that either holds up against the diff or doesn't — not a vibe about staleness in general.

## What it produces

The output is a numbered list of proposed edits, and every entry names the exact file and location the edit applies to, states what the document currently says, cites the piece of git history that contradicts it, and proposes specific replacement text or a specific addition — never a summary that says some things might be out of date without saying which things. A finding that can't be pinned to a file path and a reason isn't finished; it gets investigated further or dropped, it doesn't get reported as a vague hunch. To make the expected shape concrete: an entry might read something like "`CLAUDE.md` doc map, skill-routing row — points to `docs/governance/SKILL_ROUTING.md`, but a later commit renamed that file to `docs/governance/ROUTING.md`; update the pointer," or "`docs/decisions/adr/0002-qdrant-over-milvus.md` — status recorded as Accepted, but a later commit's message records the team reversing this decision in favor of Milvus; this ADR needs a Superseded status and a follow-up ADR recording the reversal." Both of those are illustrations of the required level of specificity, not findings from an actual run — nothing in this repository has been renamed or reversed as described. Every real proposal `claude-md-sync` produces is expected to match that same granularity: a path, a claim, a piece of evidence, and a concrete fix.

## The hard constraint: it proposes, it never applies

As specified here, `claude-md-sync` never writes to `CLAUDE.md` or to any file under `docs/`, and it never commits anything, under any circumstance — its entire output is the itemized list described above, handed to a human to read and accept, reject, or amend one item at a time. Only after that explicit approval does an edit get applied, and even then it is applied as a deliberate, reviewed change like any other, not as an automatic side effect of the check having run. This constraint matters more here than it would for an ordinary linting tool, because of what CLAUDE.md is for: every other convention in this repository — the token-economy guidance that tells a session to trust already-established context instead of defensively re-reading it, the routing rules that send work to a skill without re-justifying the choice every time — depends on CLAUDE.md and its linked docs being trustworthy without constant re-verification. That trust only holds if nothing can rewrite the governing document without a human actually looking at the change first. A process that "fixed" its own staleness finding by editing CLAUDE.md unsupervised would be the exact failure this mechanism exists to guard against, just moved up one level: instead of the docs silently drifting from the repository, the repository's own source of truth would be silently drifting from itself, and the one thing designed to catch that kind of drift would have quietly become its source instead. Keeping a human in the loop on every single proposed edit is what keeps `claude-md-sync` a check on drift rather than one more way for it to happen.

## Where it belongs

Because its whole purpose is watching over documentation that every session in this repository is expected to rely on, `claude-md-sync` is specified as a project-level skill — to live under `.claude/skills/` and be committed to the repository itself, the same way CLAUDE.md is — rather than as a personal skill available only in one contributor's local environment. A governing document that's shared has to be checked by tooling that's equally shared; a staleness check that only one person happens to have installed would leave every other session working from the same CLAUDE.md without the same safety net.
