# CAG: Cache-Augmented Generation

This document is the detailed reference behind CLAUDE.md's CAG paradigm — the five-stage pipeline that groups nine distinct caching and serving techniques by where in a request's lifecycle each one acts; the eviction algorithms and compression methods the original project brief's compressed bullet list named only one example of each for (H2O/SnapKV for eviction, KIVI/KVQuant for compression), while the source documents six and five respectively; the Hybrid Memory Offloading tier, which the original project brief's §5.2 listed as a single unsupported word inside its Storage bullet with nothing explaining what it does; the multi-turn caching methods and speculative decoding variants the source names that CLAUDE.md never mentions at all; vAttention as PagedAttention's alternative; and the corrected compatibility claim about alternative attention that ADR-0003 (`docs/decisions/adr/0003-standard-attention-cache-optimization.md`) establishes, which this document restates identically in place of the original project brief's overstated claim that alternative attention is incompatible with every cache-based method. Everything below traces to `docs/inputs/concepts/advanced_cag_concepts.md`, the nine-concept extraction the original project brief's CAG section compressed into a five-line pipeline list and three "Key Combinations" bullets — this page restores what that compression left out.

## The nine concepts at a glance

| Concept | Stage | Core Value | Best Combined With |
|---------|-------|-----------|---------------------|
| KV Cache Eviction | Decoding | Memory reduction | Compression, PagedAttention, Multi-Turn |
| KV Cache Compression | Storage | Footprint shrink | Eviction, Hybrid Offloading, PagedAttention |
| Prefix Caching | Prefill | Eliminate redundant prefill | PagedAttention, Cache-Aware Batching |
| PagedAttention | Allocation | Fragmentation elimination | Prefix Caching, Batching, Eviction |
| Hybrid Offloading | Storage | Beyond-GPU capacity | Compression, PagedAttention, Multi-Turn |
| Multi-Turn Caching | Session | Conversation persistence | Eviction, Compression, Hybrid Offloading |
| Speculative Decoding | Decoding | Latency reduction | Prefix Caching, PagedAttention |
| Cache-Aware Batching | Scheduling | Throughput maximization | Prefix Caching, PagedAttention |
| Alternative Attention | Architecture | Eliminate cache | Standalone (incompatible with cache methods) |

(`docs/inputs/concepts/advanced_cag_concepts.md`, closing Summary table)

The last row reproduces the source's own summary framing for Alternative Attention exactly as it's stated there — "Standalone," "incompatible with cache methods" — which is a broader, looser claim than what this project actually relies on. The section on alternative attention below states the precise four-and-four split this project uses instead, taken word for word from ADR-0003.

## How the five pipeline stages fit together

RAG's pipeline stages are steps a single request passes through in sequence; CAG's five stages are different instead — they're the different points in a serving engine's lifecycle where a caching technique can act, some before a request even arrives, some at the exact moment prefill would otherwise happen, some describing where cached data lives once it exists, one during the token-by-token decoding loop, and one describing the attention mechanism underneath everything else. The original project brief's own §5.2 already drew this same five-way split, and the source's pipeline-stage diagram lines up with it almost exactly (`docs/inputs/concepts/advanced_cag_concepts.md`, §3.2).

**Scheduling** is where Cache-Aware Batching runs, before generation starts, when the serving engine decides how to group incoming requests. Rather than treating every request as independent, requests that share a prefix get batched together so that shared prefix is computed once for the whole group instead of once per request. Continuous, in-flight batching extends this further: new requests can join a batch that's already running mid-flight, as long as they share that batch's prefix, which keeps GPU utilization high without ever waiting for a batch to fill up completely (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 8).

**Prefill** is where Prefix Caching runs. If an incoming request's leading tokens match a prefix whose KV tensors were already computed for an earlier request, prefill is skipped for that whole leading stretch and only the new tokens after it need computing. The source calls this the highest-ROI single optimization in the whole pipeline, precisely because prefill is typically the most expensive part of serving a request — one prefill, reused indefinitely (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 3).

**Storage** is the busiest of the five stages, and it covers where the cache physically or logically lives once it's been computed rather than a decision made at request-arrival or token-generation time. The source's own pipeline diagram places KV Cache Compression, PagedAttention, Hybrid Offloading, and Multi-Turn Caching all here (`docs/inputs/concepts/advanced_cag_concepts.md`, §3.2) — the original project brief's §5.2 Storage bullet named the first three of those explicitly, but its stage-by-stage list omitted Multi-Turn Caching even though its separate "Key Combinations" bullet referenced Multi-Turn Caching without stating which stage it belonged to. All four are covered in full in the sections below.

**Decoding** is where KV Cache Eviction and Speculative Decoding act, both during the token-by-token generation loop itself, after prefill has already finished. Eviction continuously trims which tokens' KV pairs stay resident as generation proceeds; speculative decoding proposes several candidate tokens per step so the target model can verify multiple tokens in a single forward pass instead of one at a time (`docs/inputs/concepts/advanced_cag_concepts.md`, Concepts 1 and 7).

**Architecture** is the foundational stage everything else sits on top of — a decision, not a per-request technique, about whether the model produces a conventional per-token KV cache in the first place. CLAUDE.md commits to standard attention here per ADR-0003, and the alternative-attention section below covers exactly what that commitment does and doesn't rule out.

## KV Cache Eviction: finding, and keeping, the heavy hitters

The KV cache grows linearly with sequence length — a 1M-token context can consume 100+ GB of GPU memory — but most tokens in that cache are never attended to strongly once they're past. Storing every token's KV pair regardless is wasteful, "like keeping every book you've ever skimmed on your desk" (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 1). Eviction fixes this by tracking which tokens matter and discarding the rest, keeping only "heavy hitters" — tokens with high accumulated attention — plus a recent window.

**H2O (Heavy-Hitter Oracle)** is the baseline approach: greedy dynamic eviction driven by each token's accumulated attention score across the whole generation so far, on the premise that heavy-hitter tokens are essential and losing them measurably degrades output quality. **SnapKV** differs by selecting tokens through an observation window plus 1D pooling instead of a running accumulated score — it keeps the important prefix tokens, the context immediately around them, and a recent window, rather than tracking attention history over the full sequence.

The four additional algorithms the source documents each depart from H2O and SnapKV in a different way. **NACL** is single-shot rather than continuous: it scores token importance using end-of-input tokens as proxies and then discards low-scoring tokens — plus some random eviction — in one pass, rather than accumulating attention scores as decoding proceeds the way H2O does. **MorphKV** bases its decisions specifically on recent attention patterns rather than the full accumulated history, using what the source calls Sum/Max Fusion over those recent patterns to decide which older tokens still matter — its retained set keeps adapting as generation continues, unlike NACL's one-time scoring pass. **HASHEVICT** moves the eviction decision earlier still: instead of computing attention scores first and deciding what to evict afterward, the way H2O and SnapKV both do, it uses locality-sensitive hashing — specifically SimHash — to estimate which tokens are similar to each other before the full attention computation ever runs, which is what makes it lighter-weight than the attention-score-based methods. **InfiniPot** differs in kind rather than just mechanism: rather than a binary per-token keep-or-evict call, it treats the cache as a "pot" that gets distilled once it overflows, using what the source labels its CaP and NuC metrics to identify and discard the least essential material while keeping the rest intact — closer to selective compression of the whole cache than to per-token selection.

Eviction's trade-off is direct: memory saved rises together with accuracy risk, since aggressive eviction saves more memory but risks dropping tokens that turn out to matter. Its role across all six variants is the same — turning an ever-growing cache into a fixed-size reservoir holding only what each method judges to be the most important tokens (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 1).

## KV Cache Compression: shrinking without losing the mind

Even after eviction, the remaining cache is still large — each surviving token stores Key and Value tensors for every layer and every head, and at FP16 precision a 1M-token context can still need 50+ GB. Compression attacks this from a different angle than eviction: instead of storing fewer tokens, it stores each token's KV pair more cheaply, by reducing precision, dimensionality, or cross-layer redundancy (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 2).

| Category | Method | Compression |
|----------|--------|--------------|
| Quantization | KIVI | ~4x |
| Quantization | KVQuant | Up to 8x |
| Low-Rank | PALU | ~4x |
| Cross-Layer | MiniCache | ~2-3x |
| Hybrid | ShadowKV | ~6x |

(`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 2)

**KIVI** and **KVQuant** are both quantization approaches — they reduce the numeric precision used to store KV tensors rather than changing what's stored. KIVI applies per-channel quantization to keys and per-token quantization to values, with dynamic grouping: concretely, it groups tokens (32 per group, in the source's example), quantizes keys per channel and values per token, keeps the most recent tokens in full precision as "residuals" so accuracy near the generation frontier doesn't degrade, and merges those residuals into a group once a threshold is crossed. KVQuant compresses further, up to 8x, by quantizing before the RoPE positional transform is applied, using non-uniform quantization levels, and explicitly preserving outlier values that a uniform scheme would otherwise clip.

**PALU** takes a different approach entirely: dimensionality reduction rather than precision reduction. It decomposes each KV projection matrix W into two smaller matrices via singular value decomposition (SVD), caches only the compact latent representation H = X × A rather than the full projection, and reconstructs the actual KV tensors as H × B only when they're needed, fusing the reconstruction matrix offline for efficiency. Its roughly 4x reduction comes from storing a low-rank approximation of the projection, not a lower-precision copy of the full one.

**MiniCache** exploits a different kind of redundancy again — not within a single layer's tensors, but across layers. Its cross-layer compression uses SLERP (spherical linear interpolation) to represent similar KV states shared between adjacent layers with one interpolated representation instead of storing each layer's cache independently, for a more modest 2-3x reduction.

**ShadowKV** combines several of the above ideas into a single hybrid strategy: it offloads value tensors elsewhere, keeps a low-rank representation of keys, and layers sparsity and quantization on top of both — reaching roughly 6x compression by stacking mechanisms rather than relying on any one of them alone.

Compression's payoff is what makes long-context inference feasible on consumer GPUs at all; the art in every one of these five methods is how much precision, rank, or cross-layer redundancy can be sacrificed before accuracy actually drops (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 2).

## Hybrid Memory Offloading: the tier CLAUDE.md leaves unexplained

The original project brief's §5.2 Storage bullet listed "Hybrid Offloading" as a single word alongside PagedAttention and compression, with nothing behind it explaining what it does or how. The source gives it a full concept of its own: GPU memory is the bottleneck for long contexts — a 1M-token context at FP16 needs roughly 100 GB, past what most single GPUs hold — but CPU memory is abundant, in the terabytes, and disk is larger still. The fix is tiered storage rather than a single memory pool (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 5).

The tiering itself has three levels. The **hot cache** keeps the most recent and most important tokens in GPU memory for fast access. The **warm cache** offloads older tokens to CPU memory — slower to reach, but still accessible without going to disk. The **cold cache** archives tokens to disk or SSD — very slow, but with effectively infinite capacity. Sitting across all three is **predictive prefetching**: anticipating which tokens will be needed soon and transferring them into a faster tier before the request that needs them actually arrives.

The five named strategies each implement that tiering differently. **InfiniGen** pairs CPU storage with predictive prefetching specifically at the layer level: it predicts which KV entries will be critical for the *next* layer's computation and prefetches them while the GPU is still busy processing the *current* layer, hiding transfer latency behind ongoing compute. **LayerKV** offloads at the granularity of whole layers rather than individual tokens — it keeps a subset of layers resident on GPU and offloads the rest to CPU, overlapping the transfer of offloaded layers with computation on the layers that stayed. **INF2** pushes computation itself toward storage rather than just moving data across the bus: it offloads attention computation to accelerators that live on the SSDs themselves — what the source calls CSDs — which reduces how much data has to cross PCIe in the first place, rather than merely compressing what does cross it. **KVPR** overlaps two operations that would otherwise run sequentially: it partially recomputes KV values on the GPU while simultaneously transferring the remaining values from CPU, synchronizing the two so neither has to wait fully on the other. **Oneiros** takes a different resource off the GPU entirely — instead of moving KV cache data around, it remaps the model's own parameters off GPU memory, freeing up room for the KV cache itself to expand.

The trade-off running through all five: GPU memory saved rises together with latency, since CPU and SSD access are both slower than GPU-resident memory. Hybrid offloading's role is to extend the effective context window beyond whatever a single GPU's memory allows, and the art across every one of these strategies is hiding transfer latency behind computation that's already happening anyway (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 5).

## Multi-turn conversation caching: turning linear cost into constant cost

In a twenty-turn conversation, each new turn requires attending to all nineteen turns that came before it, and the KV cache grows with every message. Left unmanaged, each turn gets slower and more memory-hungry than the last — "like adding a new chapter to a book and reprinting the whole thing every time" (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 6). Multi-turn caching fixes this with a turn-by-turn cache stored after each completed turn, incremental append that computes KV only for the new turn's tokens rather than recomputing the whole history, session persistence that survives across separate API calls by staying resident server-side, and selective retention that may summarize or evict older turns once they've aged out of relevance.

The five methods the source names each specialize that general mechanism differently. **RocketKV-MT** retains all KV tokens for future turns while constraining which tokens get selected within the *current* turn — it prioritizes keeping material available for turns not yet asked, at the cost of being more selective about what the present turn contributes. **KVzip** takes a query-agnostic approach to compressed KV reuse, amortizing its overhead across however many different queries eventually get asked against that context, which suits it to diverse future queries rather than a predictable single follow-up. **ShadowKV** — the same method that appears among the compression techniques above — does double duty here by sharing low-rank subspaces between the original sequence and its continuation, so the same low-rank mechanism that shrinks its footprint in the compression role also keeps multi-turn accuracy high, since a continuation isn't rebuilding its representation from scratch. **MemServe** targets disaggregated, cloud-style serving specifically, with an elastic memory pool and context caching built for architectures where serving compute and cache storage don't have to live on the same machine. **SGLang's** approach folds KV reuse into how it executes structured LM programs — reuse happens automatically as part of running a program's control flow, which suits it to complex, multi-step agent workflows rather than a single flat conversation.

The payoff across all five is the same shape: near-O(1) amortized cost per turn instead of cost that grows with every message, a consistent persona since the agent genuinely remembers the full conversation rather than a summarized approximation of it, and lower latency from never having to recompute history that's already been through prefill once (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 6).

## Speculative decoding: drafting ahead and verifying in parallel

Autoregressive generation produces one token at a time, and each one requires a full forward pass through the model — agonizingly slow for long outputs, "like writing a novel one letter at a time, re-reading the entire manuscript after each letter" (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 7). Speculative decoding breaks that one-token-per-pass constraint: a small, fast draft model proposes K candidate tokens, the large target model verifies all K of them in a single forward pass, and the pipeline accepts every token up through the first mismatch before retrying from there. A draft cache keeps the draft model's own KV tensors from being recomputed at every step, so drafting stays cheap.

The math behind the speedup is worth stating plainly: without speculation, producing N tokens costs N forward passes, or O(N²) compute overall; with speculation, it costs roughly N tokens times (N/K plus overhead), or O(N²/K) — a typical effective speedup of 2-3x, and up to 5x with a strong draft model. Because verification runs in parallel across all K candidate positions rather than sequentially, memory bandwidth usage drops too, not just wall-clock latency.

Three variants change where the candidate tokens come from. **Medusa** attaches multiple draft heads directly onto the target model instead of using a wholly separate draft model — its candidate tokens come from those extra prediction heads on the model itself, which avoids the operational cost of hosting and maintaining a second model. **Lookahead Decoding** generates its candidates from an n-gram cache built out of the prior context, rather than from a trained draft model or extra heads at all. **Prompt Lookup Decoding** narrows that idea further still: it reuses tokens straight from the input prompt as its candidates, which works well specifically when the expected output is likely to repeat or closely echo material that's already sitting in the prompt.

Speculative decoding's overall trade is a small amount of extra compute — running the draft model, verifying candidates that sometimes get rejected — in exchange for a large drop in latency, and draft caching is what keeps that extra compute nearly free (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 7).

## PagedAttention and its alternative: vAttention

Traditional KV cache storage assumes memory is contiguous. When sequences share a prefix and then diverge — parallel sampling, beam search — that assumption forces the entire cache to be copied for each new branch, which causes heavy memory fragmentation and waste, "like photocopying an entire book when you only need to annotate one page" (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 4).

PagedAttention solves this the way an operating system solves memory fragmentation: it divides the KV cache into fixed-size blocks, maintains a block table mapping each sequence's logical token positions to physical blocks, lets those blocks live anywhere in GPU memory rather than requiring contiguity, and uses copy-on-write so that blocks shared between diverging sequences stay physically shared and are only copied once one branch actually modifies them. The payoff is memory sharing across parallel sequences that start from the same prompt, no fragmentation since blocks are allocated on demand, efficient beam search because diverging sequences share their common prefix's blocks, and higher achievable batch sizes as a result.

**vAttention** takes the opposite approach: it drops paging entirely, managing memory dynamically without dividing the cache into blocks at all, using contiguous memory with dynamic allocation instead. The source frames it as simpler than PagedAttention for some workloads — it trades away the block-sharing and copy-on-write machinery that PagedAttention relies on for a plainer memory layout, which is a reasonable trade when a workload doesn't actually need extensive cross-request block sharing.

Block-based caching is the foundation modern high-throughput LLM serving is built on; vAttention is the lighter-weight alternative for workloads where that full block-sharing machinery isn't earning its complexity (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 4).

## Alternative attention: the compatibility question, corrected

Every technique covered above is, in the source's own framing, fundamentally a band-aid on one root cause: softmax attention has O(N²) complexity and requires storing every past KV pair. Alternative attention mechanisms change the attention mechanism itself instead, so there's no growing per-token cache to optimize in the first place (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 9). The source names five: Linear Attention (O(N), a constant recurrent state, slightly lower quality), Log-Linear Attention (O(N log N), a reduced cache, moderate quality impact), Local / Sliding Window attention (O(N × W), a window-sized cache, loses long-range dependencies), State Space Models such as Mamba (O(N), hidden state only, a genuinely different architecture), and Kimi Linear (O(N), minimal cache, designed for million-token contexts).

Linear Attention's mechanic makes concrete why these architectures don't produce a conventional cache at all: it replaces softmax with kernel feature maps, so attention becomes `Q × (K^T × V)` instead of `softmax(Q × K^T) × V`. Because `K^T × V` can be computed incrementally, only a cumulative running sum needs to be stored — there's no per-token KV cache to grow, evict from, compress, or page, just a fixed-size state that updates as generation proceeds (`docs/inputs/concepts/advanced_cag_concepts.md`, Concept 9).

The original project brief's §5.2 stated, in its own "CRITICAL" callout, that Alternative Attention (Linear, Mamba, etc.) is incompatible with every cache-based method it covers. ADR-0003 (`docs/decisions/adr/0003-standard-attention-cache-optimization.md`) corrects that claim, and this document states the same corrected split, verbatim:

> Alternative attention is incompatible with four of the eight CAG techniques this project relies on, because those four depend on manipulating a per-token KV cache that alternative-attention architectures simply don't produce: KV Cache Eviction (there are no individual token entries to select for removal), KV Cache Compression (there is no per-token cache to quantize or shrink), PagedAttention (there are no KV blocks to allocate or share), and Speculative Decoding (its verification step assumes standard attention's token-by-token cache dynamics). Alternative attention is compatible with the remaining four techniques, because those operate above the attention mechanism itself — at the scheduling, session, or storage-tiering level — rather than reaching into per-token cache internals: Prefix Caching (still useful for initializing shared state, even if less impactful), Hybrid Offloading (optional rather than necessary, since the recurrent state is already small), Multi-Turn Caching (conceptually replaced by the architecture's own recurrent state, but not in conflict with it), and Cache-Aware Batching (batching logic changes but is not blocked). Alternative attention does not conflict with all cache-based methods, only with the four that directly depend on a per-token KV cache existing.

(`docs/decisions/adr/0003-standard-attention-cache-optimization.md`, Decision)

This project commits to standard attention with cache optimization — Path A — and does not use alternative attention mechanisms, a deliberate architectural choice rather than an oversight: it's what allows prefix caching, PagedAttention, and the rest of the CAG stack described above to function as designed. That commitment isn't free — it means forgoing alternative attention's O(N) or O(N log N) complexity advantages and its effectively unbounded context length, along with the smaller memory footprint alternative attention offers at extreme context sizes. Should a future requirement demand ultra-long contexts beyond what cache optimization on standard attention can economically support, revisiting this decision would mean a genuine architectural fork rather than an incremental change, since the two paths aren't designed to run as a single unified stack (`docs/decisions/adr/0003-standard-attention-cache-optimization.md`, Consequences).

## High-synergy combinations

The original project brief's §5.2 already named three combinations under "Key Combinations (A+ Synergy)" without explaining why each one earned that rating. All three are triple-technique archetypes the source works through in detail (`docs/inputs/concepts/advanced_cag_concepts.md`, §2.3), and the source's own pair-level compatibility matrix backs each one up (§2.2): every pair inside the first two archetypes below scores A+ individually, and two of the three pairs inside the third do — the exception is Eviction + Multi-Turn Caching, scored a still-strong A rather than A+, which doesn't stop the source from naming the triple itself among its "Top 5 Most Impactful Triples" (§4.2, Category 3).

**Prefix Caching + PagedAttention + Cache-Aware Batching** is the source's "High-Throughput Serving" pipeline (Archetype B). Prefix caching stores the shared system prompts and RAG context that many requests have in common; PagedAttention's block table is what makes sharing that stored prefix across requests efficient rather than requiring a copy per request; cache-aware batching is the scheduling layer that actually groups incoming requests by shared prefix so the other two techniques have something to act on. Chained together, one prefill ends up serving hundreds of requests instead of one — the source's own use cases for this archetype are RAG APIs, chatbot platforms, and multi-tenant serving, exactly the workloads where many requests share a prefix by construction.

**Eviction + Compression + Hybrid Offloading** is the source's "Long Context Champion" pipeline (Archetype A), and the three techniques stack in a specific order rather than operating independently: eviction first reduces the token count down to essential heavy hitters, compression then shrinks the per-token size of whatever survived eviction, and hybrid offloading moves what's left — now both fewer tokens and smaller per token — out to CPU or SSD. Each step reduces what the next step has to handle, which is why the source frames this as the path to serving 1M+ token contexts on a single GPU, and names document analysis, code review, and long-form content generation as its target use cases.

**Multi-Turn Caching + Eviction + Compression** is the source's "Real-Time Chat" pipeline (Archetype C). Multi-turn caching stores conversation KV incrementally so each new turn doesn't recompute history; left alone, that cache would still grow without bound across a long conversation, so eviction bounds it by dropping low-importance tokens as turns accumulate, and compression fits more of what remains into the same GPU memory. Together they're what let the fiftieth turn of a conversation run as fast as the first — the source names customer support bots, companion AI, and therapy agents as the use cases where conversations run long enough for this to matter.

All three archetypes share a structure worth naming explicitly: they aren't three independently good ideas bolted together, but a genuine pipeline where each technique's output is smaller or better-organized input for the next one — which is exactly the property that separates an A+ combination from techniques that are merely compatible without reinforcing each other.
