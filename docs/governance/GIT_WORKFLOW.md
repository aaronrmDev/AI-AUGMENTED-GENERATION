# Git Workflow: The Gitflow Branch Model

CLAUDE.md's git-native section fixes what an individual commit and branch look like — Conventional Commits, `feat/123-short-desc` naming — without saying how multiple branches are supposed to relate to each other once more than one is alive at a time. That gap hasn't mattered yet: this repository is still pre-code, and its only branch today is `main` itself, so there has been nothing to relate. It starts to matter the moment real implementation work begins, because a single branch cut from `main` and merged straight back can't hold more than one thing at once — it can't let two features build in parallel, let a release stabilize without blocking the next batch of feature work, or let an urgent production fix land without either branch getting in the other's way. Those are exactly the situations Atlassian's Gitflow model was built to handle, and at the repo owner's explicit request this project has adopted it: five branch types with defined roles — `main`, `develop`, `feature/*`, `release/*`, `hotfix/*` — layered on top of the naming and commit conventions CLAUDE.md already states, not replacing them. This document is that layer: what each branch type is actually for, the deliberate ruling that reconciles Gitflow's traditional merge-commit history with this project's existing squash-merge-to-main convention, how any of it applies to a repository where only `main` exists right now, and where versioning and the existing commit/PR conventions fit in.

## The branch types, and why each one exists

`main` keeps the property it already has today: everything on it is production-ready, and it only ever receives code through a release or a hotfix landing, never through day-to-day work committed straight to it. Its history is meant to read as a release history — walking `main`'s commits back should show the sequence of things that actually shipped, not the full mess of everything anyone tried along the way to shipping them.

`develop` is the branch Gitflow adds underneath `main`: the integration branch where finished feature work accumulates before anyone has decided it's ready to ship. It exists because "production-ready" and "done with the current batch of work" are genuinely different states — `develop` can sit ahead of the last release, carrying several finished features nobody has cut a release for yet, without ever putting `main` in a state that isn't safe to deploy. Nothing deploys from `develop` directly; it is the staging ground `main` gets cut from once a release is actually ready.

`feature/*` branches are where the actual day-to-day work happens. Each one is cut from `develop`, scoped to a single feature or piece of work, and merged back into `develop` — never into `main` directly — once that work is done. They're meant to be short-lived and numerous: several can be in flight from `develop` at once without interfering with each other, which is the entire point of pulling feature work off `main` in the first place. Naming stays exactly what CLAUDE.md's git-native section already establishes (`feat/123-short-desc`); Gitflow doesn't change the naming convention, it only specifies that these branches are cut from and merged back into `develop` rather than `main`.

`release/*` branches exist for the narrow window between "`develop` has enough finished features to ship" and "it's actually shipped." A release branch is cut from `develop` at that point, and nothing new gets built on it — no new features, only the stabilization a release actually needs: bugs surfaced by final testing, documentation fixes, a version-number bump. That isolation is the point: `develop` keeps absorbing the next batch of feature work in parallel while the release branch is held to a stricter "fix only what's broken" standard. Once it's stable, a release branch merges twice — into `main`, where the merge point gets tagged as the new release, and back into `develop`, so any fix made during stabilization isn't silently lost the next time `develop` ships.

`hotfix/*` branches cover the case a release branch can't: a production bug on `main` that needs a fix now, before the next planned release is anywhere near ready. A hotfix branch is cut directly from `main` — not `develop`, since whatever `develop` currently holds may be far from release-ready — carries the minimal fix and nothing else, and merges back into both `main`, tagged as a new patch release, and `develop`, for the same reason a release branch does: without that second merge, the next regular release would silently overwrite the hotfix the moment it shipped.

## Reconciling Gitflow with this repo's squash-merge convention — a ruling, not a given

Atlassian's Gitflow model, as it's commonly documented, doesn't specify squash merging anywhere; the traditional description assumes ordinary merge commits throughout, on the reasoning that Gitflow's own guarantees depend on that merge structure being visible in history. CLAUDE.md's git-native section, independently, names squash-merging into `main` as this project's existing convention. Applied literally everywhere at once, those two defaults conflict, and neither Atlassian's documentation nor this project's prior rules resolve that conflict on their own — so here is the resolution, stated plainly as a deliberate ruling this document makes, not a fact either source already established: `feature/*` branches squash-merge into `develop`, while `release/*` and `hotfix/*` branches merge into `main` and `develop` with real, non-squashed merge commits.

The asymmetry is deliberate, not an oversight. Squashing `feature/*` branches into `develop` extends this project's existing squash convention to the one place it costs nothing to apply — one commit per finished feature in `develop`'s history instead of the full back-and-forth it took to build it, with no downstream branch depending on a feature branch's individual commit structure once it's merged. Real merge commits on `release/*` and `hotfix/*` branches aren't optional in the same way: Gitflow's actual guarantees — being able to look at `main`'s history and tell which release a given hotfix landed in, or trace a tag back to the release branch that produced it — depend on those merge commits existing as distinct, identifiable points in history. Squashing a release or hotfix merge would erase exactly the structure that makes `main`'s tag history worth trusting, which is the one property Gitflow exists to protect in the first place. So this ruling holds `develop` to this project's existing squash convention where nothing is lost by doing so, and holds `main` to Gitflow's traditional merge-commit convention where something real would be lost otherwise — a synthesis of the two sources, not something either one independently already said.

## Where this stands today

This repository has one branch: `main`. There is no `develop` and no `feature/*`, `release/*`, or `hotfix/*` branch anywhere in it, because the project is still pre-code — there has been no feature work yet for any of those branches to hold. Adopting this model in practice means creating `develop` off `main` once real implementation work begins, and cutting the first `feature/*` branch from it at that point; neither has happened yet. Everything this document describes about the branch model in action is design intent, not yet verified against an actual branch history — consistent with how the rest of this repository's governance docs flag forward-looking content until there's a repository state to check it against.

## Versioning and tagging

Releases are tagged on `main` using semantic versioning (`MAJOR.MINOR.PATCH`), at the point a `release/*` branch merges in — that merge is what a tag actually marks, and it's the mechanism that turns `main`'s commit history into a readable sequence of shipped versions rather than an undifferentiated stream of merges. A hotfix that merges into `main` outside the normal release cycle gets its own patch-version tag at that same merge point, for the same reason.

## Commit messages and pull requests

None of this changes how an individual commit or pull request gets written once a branch exists to put them on. Commit format is already specified by the template at [.gitmessage](.gitmessage), and what a pull request has to include before merge is already specified by [.github/PULL_REQUEST_TEMPLATE.md](.github/PULL_REQUEST_TEMPLATE.md); both apply unchanged on every branch type described above, and neither is restated here.
