# Security Model

Real application code sits behind large parts of what follows: FastAPI handlers under `src/api/`, the identity and access logic under `src/identity/`, seven Alembic migrations that define the schema in `alembic/versions/`, and a test suite that already includes security-specific coverage — row-level security enforcement, Argon2id password hashing, JWT issuance and validation, and the Redis-backed rate limiter and refresh-token store. What's still missing is the last mile: a deployed cluster with these controls running in front of real traffic, and the CI-gated scanning — dependency, container, and dynamic application security testing against a live instance — that would keep watching them once they are. This project's non-negotiable 20-point security checklist spans four areas — multi-tenancy, authentication, data protection, and rate limiting — and what follows rewrites each control as an explanation of what it actually prevents, what breaks if it's skipped, and how it's verified: by a real test where one already exists, by the concrete plan for one where it doesn't yet. That distinction matters as much as the rule itself: a checklist item nobody ever checks isn't a control, it's a wish, and every point below says plainly which side of that line it's currently on.

## Secrets stay out of source control, and the supply chain is watched for known holes

An API key or database credential that's committed to a Git repository doesn't stop being a problem when the commit is reverted — Git history keeps it recoverable indefinitely unless the whole history is rewritten — so the practical rule this project follows is that no secret is ever typed into a source file in the first place: production credentials live in HashiCorp Vault, and anything that reaches a running process gets there through an environment variable Vault injects, never through a config file checked into the repo. The concrete way this gets verified is a secret scan run by machine rather than trusted to a human remembering to check before a merge: `.githooks/pre-commit` blocks a commit that stages a `.env` file or adds an API-key-shaped value (`docs/security/SECRETS_MANAGEMENT.md` covers it), and the `secret-scan` job in `.github/workflows/repo-hygiene.yml` checks the changes in every push to `main` or `develop`, and in every pull request into them, against the same patterns, and fails if a `.env` file is tracked. A dedicated scanner such as Trivy's secret detection or gitleaks isn't wired in. A related but distinct failure is a credential that was never mistakenly committed but still ends up compromised some other way — a departing contractor's key, a log line that captured it by accident, a compromised CI runner — and stays valid forever because nothing forces it to change; that's what the documented secrets-rotation policy exists for, and because rotation is a process rather than a piece of application logic, its verification isn't a test but a recurring manual audit confirming the policy is written down and actually being followed on schedule.

The same "don't trust what you can't see" logic applies one layer up, to the third-party code this project depends on rather than the secrets it holds. A vulnerability disclosed in a transitive dependency — a sub-dependency pulled in by FastAPI, LangChain, or any other library in the stack — ships straight to production if nothing is watching upstream security advisories, and by the time anyone notices by accident it may have been exploitable for months. The specific tools this project commits to for that are Snyk or Dependabot scanning the Python dependency tree, and Trivy scanning the built container images for OS-level and package-level vulnerabilities the dependency scanner wouldn't catch because they live below the Python layer. Dependabot alerting is already switched on at the repo-settings level — `.github/workflows/repo-hygiene.yml`'s own header says so rather than stubbing an empty job in to claim it — so a known vulnerability in the dependency tree does surface today; what's still ahead is turning that into a CI gate: both Snyk/Dependabot and Trivy are meant to run as CI gates that fail the build once a vulnerability above a set severity threshold is found — not a one-time audit, but a check that reruns every time a dependency or a base image changes.

## Every query is scoped to a tenant, and every input is treated as hostile until proven otherwise

This system is multi-tenant — one deployment serves many separate customers' data side by side — which means the single worst thing that can happen at the data layer isn't a crash, it's tenant A silently reading or writing tenant B's rows. This system's multi-tenancy rules call for every table to carry a `tenant_id` and for PostgreSQL's row-level security (RLS) to enforce that filter at the database itself, with Qdrant's payload metadata and Redis's key prefixes (`tenant:{tenant_id}:`) carrying the same scoping into the vector store and the hot cache. The reason RLS matters specifically is that it's a second, independent layer of defense underneath the application code: even if a handler forgets a `WHERE` clause — the kind of bug that's easy to introduce and easy to miss in review — the database itself refuses to return or accept rows outside the calling session's tenant, so the mistake fails safely instead of leaking data. `docs/database/DATABASE.md`'s schema walkthrough shows an explicit `tenant_id` column on every one of the ten PostgreSQL tables, with a `tenant_isolation` RLS policy on every table except `Users`; those policies are what make that column hold at query time regardless of which path a row is reached through. Verifying this isn't something a unit test with mocked data can do, because the whole point is a database-level guarantee — it needs an integration test against a real PostgreSQL instance (this project's stated integration-testing approach already calls for TestContainers-backed Postgres) that seeds two tenants, deliberately runs a query missing its application-level tenant filter, and asserts RLS still returns zero cross-tenant rows.

RLS separates tenants, but it doesn't separate users inside one tenant. So a route that takes an object id from the client has to check that the object belongs to the caller (OWASP API1, broken object-level authorization). The session routes do:

- `POST /sessions/{session_id}/answers` looks the session up as the token's user before any embedding, routing, or retrieval (`src/orchestration/application/answer_in_session.py`).
- A session that doesn't exist, belongs to another user, or lives in another tenant returns the same `404 {"detail": "Session not found"}`, so a caller can't learn which session ids exist.
- The tenant and user come only from the verified access token, never from a request body, and the request models refuse fields they don't declare.
- `PostgresSessionBudgetRecorder` repeats the ownership check on its own write.

`tests/integration/test_sessions_endpoints.py` verifies this end to end against real Postgres, Redis, and Qdrant. It attempts another user's session and another tenant's, and asserts the identical 404 and an untouched budget. `test_postgres_chat_session_repository.py` verifies it at the repository level.

`POST /sessions/{session_id}/answers/stream` carries the identical guarantee by construction rather than by a second implementation: it calls the same `AnswerInSession` ownership check the JSON endpoint uses, and that check runs before the response ever becomes a stream — `StreamingResponse` is only constructed after `await answer_in_session.stream(...)` returns successfully, so `SessionNotFound` still produces the plain `404 {"detail": "Session not found"}` JSON response, never a stream that opens and then closes. A failure that happens after the stream has already started (a chat-model error mid-generation, whose HTTP status is by then locked in at `200`) is reported as one SSE `error` event carrying a generic message, never the underlying exception text, with the real exception logged in full server-side instead. `tests/integration/test_sessions_stream_endpoint.py` verifies the cross-tenant and cross-user cases end to end, asserting zero SSE bytes and a `content-type` that never becomes `text/event-stream` for either.

`GET /data-sources/jobs/{task_id}` guards the same object-level-authorization risk with a different mechanism, since a Celery task id carries no tenant or user of its own for a query to filter by. `CeleryIngestionJobDispatcher.status()` (`src/workers/celery_ingestion_dispatcher.py`) checks a `tenant_id:user_id` ownership record in Redis — written by `dispatch()` under `ingestion_job:{task_id}` when the job was first enqueued (`docs/database/DATABASE.md` has the key shape) — before it ever reads Celery's own result backend. A task id that's missing, belongs to another tenant, or belongs to another user all report back the identical `404 {"detail": "Ingestion job not found"}`, the same missing-or-not-yours shape the session routes above use, and the denial logs the same `authz_denied` security event (`src/api/exception_handlers.py`). `tests/integration/test_data_sources_endpoints.py` verifies this end to end against a real Celery worker, Postgres, Qdrant, and Redis.

RLS protects data that's correctly scoped from reaching the wrong query; it does nothing to stop a malicious query from being constructed in the first place, which is what parameterized queries are for. String-interpolating user input directly into SQL is how a single unescaped field turns into an attacker rewriting the query itself — reading other tenants' data, dropping tables, or worse — and it's exactly the failure mode CLAUDE.md's "no raw SQL in handlers" rule closes off by requiring parameterized queries or the ORM everywhere, with no exception carved out for convenience. That rule is checkable two ways: a static check (a linter, or a Bandit-style rule flagging string concatenation or f-strings built into a SQL call) catches the pattern before it ships, and a targeted test that feeds adversarial strings — a stray quote, a `; DROP TABLE`, a union-based probe — through a repository method and asserts the string is treated as inert data rather than executed as SQL catches anything the linter missed.

Input validation and output encoding sit on either side of that same request: one guards what comes in, the other guards what goes back out. Every request this API accepts is meant to pass through a Pydantic model before it touches any business logic, which means a malformed type, an oversized field, or an unexpected nested structure gets rejected with a validation error at the boundary instead of reaching a handler that wasn't written to expect it — the failure mode without this ranges from an unhandled crash to a downstream function silently operating on data it assumed was already clean. Because this project's testing rule requires a spec written before the implementation, verifying this is close to automatic: each endpoint's Pydantic schema is meant to get a test asserting a set of invalid payloads is rejected and a set of valid ones is accepted. The session request bodies have one in the unit suite (`tests/unit/test_session_schemas.py`) and through the running app (`tests/integration/test_sessions_endpoints.py`), and registration's has one in `tests/integration/test_auth_endpoints.py`, while the question limit on `POST /chat` and the `top_k` bound on `POST /documents/search` have no test of their own yet. Output encoding addresses the mirror-image risk on the way out: if something a user typed — a chat message, a fact written into memory — is ever rendered into a future frontend without escaping, that string can carry an executable `<script>` tag into another user's browser session (stored cross-site scripting), potentially reading whatever that user's session has access to, including their own auth token. No frontend framework has been chosen yet; whichever one is, the practical risk comes down to never bypassing that framework's default output escaping on anything user-supplied. It's meant to be verified two ways: a component test that renders a known cross-site-scripting payload and asserts it appears as inert text rather than executing, and the dynamic scan described further down, which would probe the running application from outside for exactly this class of bug — neither of which exists yet, since this repository has no frontend for either check to run against.

## A stolen password or token should be close to worthless to whoever steals it

A database breach is treated in this project's design as a when, not an if, which is why the value of a stolen password depends entirely on how it was stored. A password hashed with Argon2id — the algorithm CLAUDE.md specifies rather than leaving the choice open — is memory-hard, meaning an attacker trying to crack it offline can't just throw commodity GPUs at the problem the way they could against a faster, lighter hash; storing it any other way, or worse, storing it reversibly, turns one database leak into every affected user's password being handed over in practice. Verifying this is a narrow, mechanical test: register a user, read back the stored hash, and assert it carries the `$argon2id$` identifier rather than plaintext or a different algorithm, plus a check that hashing the same password twice produces two different hashes because each carries its own salt.

Session tokens carry a version of the same risk with a different shape: a JWT that stays valid for a long time gives anyone who steals it a long window to use it. This project's answer is short-lived access tokens (15-minute expiry) paired with a longer-lived refresh token (7 days) kept out of reach of any script running on the page by storing it in an httpOnly cookie rather than somewhere JavaScript can read it, with OAuth2 and OpenID Connect layered on top for enterprise single sign-on and separate API keys — rotated through Vault — for service-to-service calls that aren't tied to a human session at all. The WebSocket path adds a wrinkle worth naming explicitly once one exists: this project's planned WebSocket convention would authenticate over a `?token=...` query parameter rather than a header, and query parameters have a way of ending up somewhere a header wouldn't — a server access log, a browser's history, a referrer sent to a third party — so the short access-token lifetime would be doing real work there, not just following convention. No WebSocket route is built yet, so this convention is design intent rather than something to verify today. Verifying the token lifecycle needs two tests: one confirming a token issued more than 15 minutes ago is rejected, and one confirming that using a refresh token invalidates it for reuse — replaying the same refresh token a second time should fail, which is what actually makes rotation meaningful rather than just a longer-lived second secret.

Rate limiting and bot protection both defend against the same underlying risk — one actor consuming a disproportionate, disruptive share of the system's capacity — through different mechanisms aimed at different attackers. An unbounded request stream from a single account or IP can exhaust the vLLM serving layer or the database long before it looks like a deliberate attack; The planned limits are 100 requests per minute per user for chat, a stricter 10 per minute for document uploads (a heavier operation), a 1,000-per-minute ceiling per IP address with tighter limits specifically on authentication endpoints, and `X-RateLimit-*` response headers so a client can see how much room it has left before being throttled.

What's built is a Redis-backed fixed-window limiter (`src/api/rate_limit.py` and `src/identity/infrastructure/redis_rate_limiter.py`):

- 5 requests per minute per client IP, on registration and login;
- 100 per minute per user, shared by `POST /chat` and answering in a session;
- 20 per minute per user, on creating a session;
- 10 per minute per user, on `POST /data-sources`.

A separate global counter closes a gap none of those per-user numbers can: `global_chat_limit()` caps `POST /chat` and answering in a session combined, across every account at once rather than one account at a time, at 10,000 requests per hour by default (`CHAT_RATE_LIMIT_GLOBAL_PER_HOUR`, keyed in Redis under `GLOBAL_CHAT_KEY`, the literal key `global:chat`) — checked right after the per-user limit so an account already rejected on its own quota never spends down the shared one on its way to a 429, which is what stops an attacker from routing around a per-account ceiling by simply registering another account and getting a fresh budget each time. Every limited response carries `X-RateLimit-*` headers. Each request's count and its window's expiry are written in one Redis transaction, so a process that dies mid-check can't leave a counter that never resets. The upload limit and the per-IP ceiling aren't built yet.

That's directly verifiable: an integration test against a real Redis instance fires past each threshold and asserts that the request is rejected with the right status and headers once the limit is crossed. `test_auth_endpoints.py` does that for login, and `test_sessions_endpoints.py` for the shared chat limit, for session creation, and for the global quota — the session-creation and shared-chat cases check status codes alone, while the global-quota tests also confirm the combined ceiling holds across different accounts and that an account already over its own limit never touches the shared counter; the registration limit has no test of its own. Rate limiting alone doesn't stop an attacker who simply spreads the same abuse across many cheaply-created accounts or IPs, though, which is the gap CAPTCHA-style bot protection (reCAPTCHA v3 or hCaptcha) is meant to close at account creation and other high-value endpoints. Because that check depends on an external, live third-party service, it isn't something a unit test can fully simulate; the realistic verification is an end-to-end test confirming the endpoint rejects a request missing a valid challenge token.

`POST /sessions/{session_id}/answers/stream` (the object-level-authorization paragraph above describes its ownership check) needed two more controls past everything above, both recorded as follow-up `#196` against the story that shipped streaming itself, because a fixed-window request-count limiter bounds how many requests start per minute, not how long one that already started is allowed to run or how many can be open at once — a live-probed security review of that story found a streamed answer had neither. Without a deadline, a chat provider trickling one token every few minutes would hold the connection open past any bound the JSON endpoint has, because the HTTP client's own read timeout resets on every byte received rather than firing on total elapsed time; `UnifiedAnswerQuestion._stream_events()` (`src/orchestration/application/unified_answer_question.py`) now wraps the chat model's `stream()` call in an overall wall-clock deadline, `DEFAULT_STREAM_DEADLINE = 90.0` seconds (`STREAM_DEADLINE_SECONDS`, read fresh per call like the rate limits above) — disclosed here explicitly as a reasoned engineering default, not one derived from a measured p95 generation latency this project doesn't have yet, chosen to sit far inside the `anthropic` SDK's own ten-minute read-timeout ceiling while still bounding the worst case the review flagged. A stream that exceeds the deadline ends in one generic SSE `error` event, the same shape a mid-generation chat-model failure already produces, with the real cause logged server-side only, never surfaced to the client. Without a concurrency cap, separately, a client that opens a stream and simply never reads it — confirmed by live probe to go uncancelled by anything else in this stack, since only a genuine socket close triggers cleanup — could hold enough connections open to exhaust the shared upstream provider pool (`anthropic`'s default `max_connections=1000`) well inside the per-user and global chat limits described above. `STREAM_CONCURRENCY_LIMIT_PER_USER` (default 5, `stream_concurrency_limit()` in `src/api/rate_limit.py`) now bounds how many streams one user can hold open at once, shared across every session rather than counted per session, enforced through a new port (`StreamConcurrencyLimiter`, `src/identity/domain/ports.py`) and its Redis adapter (`RedisStreamConcurrencyLimiter`, `src/identity/infrastructure/redis_stream_concurrency_limiter.py`): a Redis sorted set per user where each concurrently-open stream is its own member, scored by its own expiry, so an individual slot self-heals off the count on the very next acquire from anyone even if the process holding it dies without ever calling release — backed by a key-level `EXPIRE` as a second, coarser backstop covering the case where nothing ever touches that key again. The slot's own TTL (`stream_slot_ttl_seconds()`) is deliberately derived from the generation deadline plus a ten-second buffer rather than configured as a separate number, so retuning one follows the other instead of the two silently drifting apart. The router (`src/api/routers/sessions.py`) acquires a slot only after `AnswerInSession.stream()` has already succeeded — after every rate-limit and object-level-authorization check described above, never before them — so a request this document's other controls would already reject never touches a concurrency slot at all, and releases the slot in a `finally` wrapped around the SSE encoder regardless of how the stream ends: completion, the new deadline, a chat-model error, or the client disconnecting. A caller already at the limit gets `429 {"detail": "Too many concurrent streams"}` with an `X-Stream-Concurrency-Limit` header, logged as a `stream_concurrency_limit_exceeded` structured security event alongside the `rate_limit_exceeded` and `authz_denied` events described above. The deadline is unit-tested against a chat-model test double that hangs forever (`tests/unit/test_unified_answer_question.py`), asserting the stream still ends in exactly one error event and that the underlying model was genuinely cancelled rather than abandoned; the Redis adapter's pipeline ordering and self-healing expiry are integration-tested directly against a real Redis instance (`tests/integration/test_redis_stream_concurrency_limiter.py`); and the full concurrency cap is verified end to end through the running app (`tests/integration/test_sessions_stream_endpoint.py`), which drives two genuinely concurrent streams to hold their slots open, confirms a third request for the same user is rejected while they do, and confirms a fourth succeeds once the first two finish and release theirs.

Four more controls close gaps the same review recorded alongside these rate limits, tracked under the same `#193` issue as the others in this section. A request body is now capped before anything tries to parse it: `MaxBodySizeMiddleware` (`src/api/middleware/max_body_size.py`, wired into every request via `src/api/main.py`) rejects a body over 16 KiB by default — checking a declared `Content-Length` up front where the client sends one honestly, and otherwise draining a chunked body itself and bailing the instant the running total crosses the limit — with the two routes that accept a full document body — `POST /documents` and `POST /data-sources`, each matched by its exact path so the distinct `/documents/search` route keeps the default — raised to an 11 MiB ceiling. `tests/unit/test_max_body_size_middleware.py` covers both the `Content-Length` and the chunked path, and `tests/integration/test_sessions_endpoints.py` confirms an oversized session-creation request is rejected before Pydantic ever validates it. The per-IP auth limiter above now keys on `real_client_ip()` (`src/api/client_address.py`) rather than the raw `request.client.host` it used before this task, because that raw address becomes the reverse proxy's own address rather than the caller's once one sits in front of this API; `real_client_ip()` trusts only the rightmost `TRUSTED_PROXY_COUNT` entries of `X-Forwarded-For` and falls back to `request.client.host` for everything else, with `TRUSTED_PROXY_COUNT` defaulting to 0 so a deployment with no proxy in front of it — every environment this project runs in today — never reads the header at all and behaves exactly as before; an operator running behind N real proxies sets `TRUSTED_PROXY_COUNT=N`. `tests/unit/test_client_address.py` covers the zero-, one-, and two-proxy cases along with the fallback when there are fewer forwarded entries than trusted proxies, and `tests/integration/test_auth_endpoints.py` proves the login limiter keys on the forwarded address rather than the shared test-client address once a proxy is trusted. Every response this application's own code produces — successful, a validation failure, a 429, a 413 — now also carries four security headers — `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy: no-referrer` — added by `SecurityHeadersMiddleware` (`src/api/middleware/security_headers.py`) and verified both directly (`tests/unit/test_security_headers_middleware.py`) and through a real request against the running app (`tests/integration/test_security_headers.py`); the one response that never reaches it is a truly unhandled exception, since Starlette's own `ServerErrorMiddleware` builds that response from outside every middleware this app registers. Finally, the session-ownership denial described above and a rate limit being exceeded each now write a structured event through `structlog`, configured once by `configure_security_logging()` (`src/api/security_logging.py`) to render JSON: the same 404 response covering a missing, another user's, or another tenant's session also logs `authz_denied` with the caller's tenant and user id and the denied session id, and a 429 logs `rate_limit_exceeded` with the key that tripped — narrower than, but the first real instance of, the login/logout/token-refresh audit trail this document describes further below as not yet built, and unable to carry a token, an `Authorization` header, or request-body text, since neither handler's inputs ever include any of those. `tests/unit/test_security_logging.py` asserts both event shapes.

## The network boundary is built on the assumption that something inside it is already compromised

The outer edge of this system is protected the ordinary way — HTTPS everywhere, TLS 1.3 specifically, terminated at the Traefik ingress with certificates issued and renewed automatically by cert-manager — because without it, every credential, token, and piece of user data crossing the public internet is readable to anyone positioned on the network path between client and server. That's an infrastructure property more than an application one, so it isn't proven by a unit test; it's confirmed by reviewing the Traefik and cert-manager configuration (ideally as part of the Terraform-managed infrastructure-as-code, so the check happens at the same point the setting is declared) and, once something is actually deployed, by an external TLS scan against the live endpoint confirming weaker protocol versions are refused.

Cross-origin resource sharing (CORS) configuration guards a narrower but easy-to-get-wrong version of the same boundary: browsers block a page on one origin from reading a response from another origin unless that response explicitly grants permission via CORS headers, and an overly permissive `Access-Control-Allow-Origin` setting — a wildcard, or a whitelist that's too generous — removes that protection, letting a page hosted anywhere make an authenticated request against this API using a logged-in victim's own browser session and then actually read what comes back. The check is direct: send a cross-origin request from an origin that isn't on the whitelist and confirm the response doesn't grant it access.

Encryption in transit doesn't stop at the public edge, though, and that's the point of this project's separate requirement for mutual TLS (mTLS) on internal Kubernetes traffic: TLS 1.3 covers the path a browser takes to reach the API, but the API's own calls to vLLM, PostgreSQL, Neo4j, and every other internal service cross the cluster's internal network too, and without mTLS on those hops, anyone who's gained a foothold inside the cluster can read or tamper with that traffic in plaintext even though nothing outside the cluster ever could. Making that foothold hard to get in the first place is exactly what the checklist's deny-all Kubernetes network policy is for: rather than assuming every pod can be trusted to only talk to what it's supposed to, the network policy has to be updated deliberately to allow each specific pod-to-pod path — the API reaching Postgres, the API reaching Redis, and so on — so a pod compromised through some other flaw, a dependency vulnerability from the supply-chain controls above, for instance, doesn't automatically get a clear path to every other service in the cluster. Both mTLS and network policy are infrastructure-configuration properties rather than application behavior, so their realistic verification is a manifest review confirming the deny-all baseline and certificate validation are both actually in place, with an automated policy-as-code check — something like conftest or kube-linter run against the manifests in CI — as the more scalable version of that same review once there are manifests for it to check.

## Data that's unreadable at rest can't be walked back after a breach, and personal data that's already gone can't leak

Every other control in this document assumes the application layer behaves correctly; encryption at rest is what still matters when it doesn't, or when the breach doesn't go through the application at all — a stolen disk, an improperly secured backup, a cloud-storage misconfiguration that exposes a bucket. This project calls for that protection at each store specifically: transparent data encryption on PostgreSQL, field-level encryption on Qdrant, and server-side encryption on the MinIO object store holding uploaded documents. Because this is a storage-configuration property rather than something application code decides at runtime, it's verified by reviewing the infrastructure configuration that provisions each store — again, ideally the Terraform definitions, so the setting is checked at the same place it's declared — rather than by a test that runs against the application.

The other half of data protection is about not holding onto sensitive data longer than the system actually needs it, which matters because data that was never stored — or was stored in redacted form — can't be part of a future breach at all. This project's memory layer is meant to run incoming content through personally identifiable information (PII) redaction, using Presidio or a regex-based fallback, before anything is written into MAG's episodic or semantic stores, so a user's name, contact details, or anything else Presidio's detectors or the regex patterns are tuned to catch doesn't sit in the database or the logs in raw form. The concrete failure mode without this is that a single memory-store or log leak becomes a PII breach by default rather than by exception, since the PII would already be sitting there in the clear. On top of redaction, episodic memories are meant to auto-expire after 90 days unless they've already been consolidated into semantic memory — the process `docs/architecture/MAG.md` describes as transforming raw episodes into distilled, durable facts — which keeps stale personal data from accumulating indefinitely just because no one deleted it. Verifying redaction is a direct unit test: feed a known PII pattern (an email address, a phone number) through the redaction step and assert the stored or logged value no longer contains it in raw form. Verifying the 90-day expiry needs a test against the scheduled consolidation/cleanup job itself, seeding an episodic memory older than the threshold and confirming it's either archived or already consolidated rather than still sitting in its raw form.

## When prevention fails, the system needs to say so — through a log, or through an attack simulation

Every control above this line is aimed at prevention, and prevention eventually fails somewhere — through a bug, a misconfiguration, or a genuinely novel attack nobody anticipated — which is why authentication events specifically get their own audit trail rather than relying on whatever generic request logging already exists. A login, a logout, and a token refresh are each still meant to write a structured log entry (via structlog, the logging library this project's observability stack already commits to elsewhere) carrying who did it, when, and what the outcome was, because without that trail an incident-response investigation after a suspected breach has no way to reconstruct who accessed what — the failure mode isn't the breach itself, it's being unable to answer any question about it afterward. A permission-denied event is no longer only planned: the `authz_denied` event described above is the first real instance of this audit trail rather than still a gap. Verifying this is a unit test per auth-event type: trigger a login, a failed login, and a token refresh, and assert each produced a log entry carrying the fields an investigation would actually need.

The last checklist point is different in kind from everything before it: dynamic application security testing (DAST, via OWASP ZAP — the tool this document names directly) doesn't check a rule at all, it attacks a running instance of the system the way an actual adversary would, looking for the class of vulnerability that only exists once the pieces are assembled and running — the kind that static review and unit tests are structurally unable to see, because there's no running system for them to probe. That makes it the last line of defense for many of the failure modes described throughout this document: a reflected script-injection bug that slipped past output encoding, an authorization check missing on one specific live endpoint, a CORS misconfiguration nobody caught in review. It's meant to run as a CI stage, scanning a deployed test instance of the API and failing the build on findings above a set severity threshold — which, like the CI-gated dependency and container scans described earlier, doesn't exist yet: `.github/workflows/repo-hygiene.yml`, the repository's only workflow, leaves container scanning and DAST out until there's a deployed environment to point them at.

Several of the verification mechanisms described above have actually been run against a real system now, though not all of them — CI runs only the repository hygiene checks in `.github/workflows/repo-hygiene.yml`, and there's still no deployed instance for a dynamic scan to point at. Row-level tenant isolation is tested against a real, RLS-enabled PostgreSQL instance by three dedicated test files (`tests/integration/test_rls_tenant_isolation.py` for Identity's `sessions` table, `test_rag_rls_tenant_isolation.py` for RAG's `chunks` table, `test_mag_rls_tenant_isolation.py` for MAG's memory tables), and again where a repository leaves the tenant filter to RLS alone (`test_postgres_chat_session_repository.py`, `test_postgres_session_budget_recorder.py`) — proving the policy actually refuses cross-tenant access rather than trusting that it would. Argon2id password hashing is unit-tested (`tests/unit/test_argon2_password_hasher.py`), short-lived JWT issuance and rotation are unit-tested (`test_jwt_token_issuer.py`, `test_refresh_access_token.py`, `test_revoke_refresh_token.py`), and rate limiting and refresh-token revocation are integration-tested against a real Redis (`tests/integration/test_redis_rate_limiter.py`, `test_redis_refresh_token_store.py`). Object-level authorization on chat sessions, and the per-user chat and session-creation limits, are integration-tested through the running app (`tests/integration/test_sessions_endpoints.py`); the ingestion job endpoint's own object-level authorization and its 10-per-minute rate limit are integration-tested the same way, against a real Celery worker (`tests/integration/test_data_sources_endpoints.py`). A security review of the session endpoints recorded five gaps as follow-up #193, and all five are now built and tested exactly as the rate-limiting and request-handling paragraphs above describe: the global hourly chat quota, the request-body size ceiling, trusted-proxy-aware rate-limit keys, the security response headers, and structured `authz_denied`/`rate_limit_exceeded` logging. What hasn't happened yet: CI-gated dependency and container scanning — Dependabot alerting is already on at the repo-settings level, per `.github/workflows/repo-hygiene.yml`'s own header comment, but nothing yet fails a build over what it finds — the structured auth-event audit trail, and the OWASP ZAP dynamic scan, which needs a running deployment that doesn't exist yet. This document's commitment for those remaining controls is unchanged: each one has a stated, concrete way it's meant to be checked once there's a deployed system to check it against, rather than a bare rule someone has to trust was followed.
