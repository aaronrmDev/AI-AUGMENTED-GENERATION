# RAG Multi-Query + HyDE + Self-RAG — Design Spec

Compressed process, same as the two prior batches — bounded spec, real code/tests/measurement throughout.

## Why these three together

RAG.md groups Multi-Query Retrieval (#52/#104), HyDE (#65/#111), and Self-RAG (#68/#115) as its own "advanced phase" of the implementation roadmap — "the goal shifts from fixing what retrieval returns to making the system smarter about what it searches for and whether it needs to search at all." Multi-Query and HyDE both compose cleanly as `Retriever` decorators using a trick this project's own prior batches already established (substituting what string an inner retriever embeds as "the query"); Self-RAG doesn't, because its whole point is sometimes skipping retrieval entirely, which no `Retriever` can express (every `Retriever.execute()` returns *some* results). It gets its own `AnswerQuestion` sibling instead, the same shape `UploadDocumentWithParents` used when a technique didn't fit an existing port.

## Multi-Query Retrieval (#52, #104)

`MultiQueryRetriever(Retriever)` wraps an inner `Retriever` and a `ChatModel`. `execute()` asks the chat model to generate `num_queries` (default 4) diverse phrasings of the question — genuinely different angles, not synonyms (RAG.md's own distinction from Query Expansion) — parses them into a list (one per non-empty line of the response), runs the inner retriever against every variant concurrently, and merges the result lists via Reciprocal Rank Fusion — the same RRF math `HybridSearchDocuments` already implements. **Extracted as a shared helper** (`src/rag/infrastructure/_result_fusion.py`, `def reciprocal_rank_fusion(result_lists: list[list[SearchResult]], top_k: int) -> list[SearchResult]`) rather than copied a second time — the prior two batches' final reviews both flagged near-identical logic (`_cosine`) duplicated once already; this is the same lesson applied before it recurs a third time. `HybridSearchDocuments` is refactored to call the shared helper instead of its own inline copy — behavior-preserving, verified by its existing tests staying green.

## HyDE (#65, #111)

`HyDERetriever(Retriever)` wraps an inner `Retriever` and a `ChatModel`. `execute()` asks the chat model to write a short, confident hypothetical answer to the question, then calls the inner retriever with **that generated text as the query string** — not the original question. This works because every `Retriever` in this codebase treats its `query: str` parameter as "the text to embed," with no assumption that it's literally what the user typed; passing a different string through the exact same parameter is the whole mechanic RAG.md describes ("it is *that generated answer's embedding*... that gets used to search"), achieved with zero changes to `SearchDocuments` or any other existing retriever.

## Self-RAG (#68, #115)

`SelfRAGAnswerQuestion` — a new use case, sibling to `AnswerQuestion`, not a `Retriever` decorator (a decorator can't express "skip retrieval and answer from parametric memory instead," since every `Retriever.execute()` contract promises to return search results). Constructor takes the same `(search_documents: Retriever, chat_model: ChatModel, top_k: int)` as `AnswerQuestion`. `execute()` first asks the chat model a YES/NO gating question ("does answering this need external/private/recent information, or can it be answered from general knowledge alone?"), parsed tolerantly (case-insensitive substring match on "yes"/"no" in the first ~10 characters of the response, matching this project's established tolerant-parsing convention from `LLMReranker`). On NO, answers directly with empty context and `sources=[]` — the retrieval cost RAG.md's own "30-50% reduction" figure is about. On YES, behaves exactly like `AnswerQuestion`.

## Measurement — Self-RAG needs a different question mix than the prior batches

The five RAG.md-grounded questions every prior batch has used are all genuine fact-lookups — Self-RAG's gate should say YES on all five, making it behave identically to plain RAG for them (a real, useful confirmation that the gate doesn't false-negative on questions that actually need retrieval). But that alone never exercises the NO branch, which is the technique's whole distinguishing behavior and its own claimed cost saving. This batch's scenario adds **two general-knowledge questions** (RAG.md's own example category — basic arithmetic and a general software-terms question, neither answerable from *this specific document* but both answerable from any capable model's own training) specifically to observe whether Self-RAG's gate correctly says NO and skips retrieval on them. Each general-knowledge question's `success_check` verifies the answer is *correct on its own merits* (works identically whether or not context was used) — the interesting signal for these two isn't task success (both baseline and Self-RAG should nail them), it's whether `SelfRAGAnswerQuestion` actually skipped the retrieval call, which the script prints per-question so the controller can read and report the gate's real decisions honestly, since the existing harness has no field for "was retrieval skipped."

Three comparisons this batch measures, all against the same no-RAG baseline: Multi-Query alone, HyDE alone, Self-RAG (on the 7-question mix described above). Chunker held constant at `FixedSizeChunker`. Same `OllamaJudge`/self-grading-bias caveat, same disclosure discipline the last two batches established (state confounds and limitations explicitly rather than assume none exist) — in particular, Multi-Query and HyDE both make 1 extra LLM call per query before retrieval even runs (query generation), which the prior batch's `rerank-llm` finding already demonstrated can matter a great deal with a reasoning model — disclosed proactively in this batch's reports rather than left for a future review to find.

## Non-goals

No RAG+MAG or RAG+CAG cross-paradigm work — that's later phases entirely. No Multi-Query+HyDE combination in this batch (RAG.md names it as a high-synergy pair, "maximum recall for vague queries" — deferred to the Combinations batch, where it composes for free via `MultiQueryRetriever(inner=HyDERetriever(inner=SearchDocuments))`, same decorator trick as every combination so far). No changes to `UploadDocument`/`Chunker` — chunking is already measured and held constant.
