# MAG Batch G: Combinations — Design Spec

**Scope:** #19/#78 (Living Agent), #22/#79 (Context Wizard), #24/#80 (Self-Improving Agent), #26/#81 (Relationship-Aware Agent) — the "MAG: Combinations" milestone, four story+task pairs, no single parent issue.

## What these four issues actually ask for

Each story's Definition of Done is the same three lines: constituent techniques implemented, combined pipeline built, a real measured result documented against MAG.md's own archetype description. The first line is already true for all four archetypes — every constituent technique (Episodic, Semantic, Consolidation, Procedural, Memory Hierarchy, Retrieval Strategies, Memory Gating, Memory Graphs) was built in an earlier MAG batch (Foundation through Batch F). What these four issues are actually asking for is narrower than "implement four techniques each": prove the *composition* MAG.md describes for each archetype genuinely produces the emergent behavior MAG.md claims for it, not just that the pieces individually work in isolation (which every prior batch's own test suite already established).

## A real choice this spec makes explicitly: MAG's own convention, not RAG's

This project's RAG track ran an analogous "combinations" batch (RAG Batch E, `docs/superpowers/specs/2026-08-26-rag-combinations-design.md`) — a reusable scenario script (`evaluation/scenarios/rag-combinations/run_combinations_comparison.py`) driving the project's standing `RunComparison` harness against real infrastructure, producing a baseline-vs-treatment table with latency percentiles, token counts, and LLM-judge quality scores per combination.

Every MAG batch so far (Foundation through Batch F) has instead followed its own, different convention: a single design spec combining spec-and-plan, a hand-written narrative evaluation report per batch (`evaluation/reports/mag-*.md`) built around live-Ollama verification of a specific worked example from MAG.md rather than a repeated-sample judge-scored table, and a two-round adversarial review cycle. This batch continues that convention rather than importing RAG's, for three reasons: first, MAG.md's own archetype claims are mechanistic ("the loop closes and semantic knowledge grows richer," "relationship-hopping succeeds where similarity search would miss") rather than numeric quality-score claims, which a live worked-example reproduction verifies more directly than a judge's 1-5 rating would; second, six MAG batches deep, switching convention now for the track's own capstone would be a bigger, riskier departure than continuing what every reader of this project's evaluation reports already expects from a MAG batch; third, RAG's own scenario-script harness (`RunComparison`, `OllamaJudge`, `markdown_report.render()`) is genuinely RAG-shaped — built around a shared document corpus and single-turn question answering — and doesn't fit MAG's actual unit of work, which is a multi-turn session accumulating state over time.

**No new production classes**, matching RAG Batch E's own stated principle for the same shape of batch: if an archetype's live verification seems to need a new abstraction, that's a signal the composition itself needs rethinking, not a signal to add a class. The one exception, disclosed below, is Self-Improving Agent, where MAG.md's own claimed mechanism ("Consolidation analyzes which episodes succeeded and which failed, and extracts reusable Procedural memories") genuinely does not exist yet in this codebase — `ConsolidateEpisodes` only ever writes to semantic memory — and building it is what issue #80 is actually asking for, not scope creep past it.

## The four archetypes, what's already wired, and what each one's report needs to prove

### Living Agent (#19/#78) — Episodic + Semantic + Consolidation

Fully wired already: `CaptureEpisode` writes episodic memory every turn; `ConsolidateEpisodes` reads unconsolidated episodes for a session and writes extracted facts via `RecordSemanticFact`. No new code. The report needs to demonstrate the *loop*, not just one pass of it: capture several turns across (at least) two separate sessions for the same user, consolidate after each session, and show semantic memory measurably accumulating — new fact_keys appearing, and (the sharper claim) a fact recorded from session 1 surviving and still being retrievable when session 2's consolidation runs, i.e. knowledge compounding across sessions rather than each session starting cold.

### Context Wizard (#22/#79) — Memory Hierarchy + Retrieval Strategies + Memory Gating

Fully wired already, and wired unusually tightly: `GateMemories` (Batch E) was built to consume exactly `list[ScoredEpisode]`/`list[ScoredFact]`/`list[ActivatedNode]` — the literal return types of Batch C's retrieval strategies and Batch D's spreading activation. "Memory Hierarchy" is the three-tier store split from the Foundation batch (`WorkingMemoryStore` for the context tier, `EpisodicMemoryRepository` for medium-term, `SemanticMemoryRepository` for long-term) — already-existing infrastructure, not something this batch adds to. No new code. The report needs to run retrieval across at least two tiers (e.g. semantic-similarity search over episodic memory plus a semantic-fact search) into one real candidate pool (real `CaptureEpisode`/`RecordSemanticFact` writes, real `search_by_similarity` reads, not hand-built `ScoredEpisode`/`ScoredFact` fixtures) and feed it through `GateMemories`, proving the full retrieval-to-gating chain end to end. `HierarchicalAssembly`'s fact-before-episode ordering (`_SOURCE_TYPE_PRIORITY`) is unconditional regardless of either candidate's raw score — already proven at the unit and Batch E/F integration level — so this doesn't need to force or measure a specific score relationship between the two candidates the way an earlier phrasing of this section implied; reporting the real similarity scores achieved is enough to show the chain ran against genuine retrieved data, and the actual claim under test is source-type ordering surviving the full chain, not a token-budget or score-magnitude comparison. (An earlier draft of the test underlying this section attempted to force one candidate's score above the other's by setting episode content to the query text verbatim, the same trick `RecordSemanticFact` allows for facts; it doesn't transfer to `CaptureEpisode`, which embeds the whole JSON-encoded content dict rather than a bare string. See the batch's evaluation report for the measured scores.)

### Self-Improving Agent (#24/#80) — Episodic + Procedural + Consolidation

**Partially wired.** `CaptureEpisode` (episodic) and `RecordProcedure`/`ProceduralMemoryRepository` (procedural, Foundation batch) both already exist, but `ConsolidateEpisodes`'s own reflection prompt only ever extracts semantic facts — it has no path to procedural memory at all. MAG.md's claimed mechanism for this archetype ("Consolidation analyzes which episodes succeeded and which failed, and extracts reusable Procedural memories") is not implemented by anything in this codebase today. Building that extraction path is this batch's one piece of genuinely new code:

- A new command, `ConsolidateProcedures` (`src/mag/application/commands/consolidate_procedures.py`), structurally mirroring `ConsolidateEpisodes` closely enough to justify not merging the two: same unconsolidated-episode-batch input, same retry/validate/dedupe shape, but a different reflection prompt asking the LLM to identify a *repeated* task pattern across the batch and the workflow steps that made it succeed — MAG.md's own example, five FastAPI deployments distilling into one proven three-step procedure, only makes sense read across multiple episodes at once, not one episode in isolation the way a single fact extraction does. Writes via the existing `RecordProcedure`.
- A new prompt module, `_procedure_consolidation_prompt.py`, parallel to the existing `_consolidation_prompt.py`.
- `ConsolidateEpisodes` itself is not modified — running both `ConsolidateEpisodes` and `ConsolidateProcedures` over the same unconsolidated episode batch is the caller's own composition, matching this project's explicit-parameters, no-hidden-orchestration convention (Batch C's retrieval strategies, Batch E's gating strategies, Batch F's evolution operations all use the same shape: build the primitive, let a caller compose it, rather than baking composition into one mega-command).
- Episode `content` needs an `outcome` signal for "succeeded vs. failed" to be meaningful — `docs/architecture/MAG.md` already lists `outcome` among the fields a captured episode encodes ("input, reasoning trace, tool calls, output, outcome, timestamp, actors, and entities"), so the live-verification scenario just needs to actually populate it in each episode's `content` dict; no schema change needed, since `EpisodicMemory.content` is already unstructured JSON.

The report needs to show: capture several episodes recording the *same* task pattern succeeding via the *same* workflow across multiple sessions, run `ConsolidateProcedures`, and confirm a `ProceduralMemory` row is written with a `workflow` that actually reflects the repeated steps — MAG.md's own claim, reproduced structurally (a real repeated pattern, not a single anecdote).

### Relationship-Aware Agent (#26/#81) — Memory Graphs + Episodic + Semantic

Fully wired already, and the most directly demonstrated of the four: `CaptureEpisode` writes `Episode` nodes plus `PARTICIPATED_IN`/`MENTIONS` edges (Batch D), `RecordSemanticFact` writes `Fact` nodes, and `RetrieveBySpreadingActivation` (wrapping `Neo4jMemoryGraphRepository.spread_activation`) already has a Batch D integration test reproducing MAG.md's own worked example at the repository level (`test_spread_activation_reaches_a_fact_two_hops_from_a_mentioned_entity`). No new code. This batch's job is reproducing that same shape through the actual command layer (`CaptureEpisode` → `ConsolidateEpisodes`/`RecordSemanticFact` → `RetrieveBySpreadingActivation`) rather than constructing graph state by hand against the repository directly, and framing it explicitly as MAG.md's own "what did I book last month" example: an episode mentioning a trip, a fact abstracted from it, and a spreading-activation query from the mentioned entity reaching the fact — succeeding specifically where a same-worded similarity search over the episode's raw text would miss it, since the query never repeats the entity name literally.

## Testing plan

Each archetype gets a real-infrastructure integration test (real Postgres, Qdrant, and — for Relationship-Aware Agent and Self-Improving Agent's consolidation calls — real Neo4j and a live Ollama model) reproducing its own worked example above, plus unit tests for the one new command (`ConsolidateProcedures`) matching `ConsolidateEpisodes`'s own existing unit-test shape (retry/validate/dedupe/malformed-response paths, no procedure written when reflection finds nothing).

## What this batch does not do

- **No new production classes for Living Agent, Context Wizard, or Relationship-Aware Agent** — all three compose already-built primitives exactly as designed to compose.
- **No scenario-script harness, no LLM-judge quality scoring, no latency/token comparison tables** — a deliberate departure from RAG Batch E's convention, explained above.
- **No automatic trigger for when consolidation (of either kind) should run** — matching every prior MAG batch's explicit-parameters convention, a caller decides when to consolidate; this batch doesn't add a scheduler.
- **`ConsolidateProcedures` does not attempt cross-user or cross-tenant pattern generalization** — task-pattern matching for procedural extraction, like `ConsolidateEpisodes`'s fact extraction before it, operates per-user, per-session-batch, not by mining patterns across a tenant's whole user base.
